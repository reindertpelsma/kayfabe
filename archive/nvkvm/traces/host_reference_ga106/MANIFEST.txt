MEASURED, and the reason this reference is worth having
  * 479 of 613 ioctls — 78% of the entire RM control plane for a compute program —
    belong to cuCtxCreate. The divergence surface for "stock driver -> first
    compute" is almost entirely inside that one call.
  * `ce` and `launch` are IDENTICAL: same 613 records, and after canonicalisation
    NOT ONE DIFFERING BYTE. Loading a PTX module, allocating two more buffers,
    launching a kernel and synchronising cost ZERO RM ioctls. The control plane
    genuinely ends at cuCtxCreate; everything after is doorbell/pushbuffer traffic
    that no ioctl trace on either side can see.
  * First ioctl of cuCtxCreate on this host: nvidiactl RM_CONTROL cmd=0x20803601,
    at index 129 (see nvd_selftest.sh's positive control).
  * ★★ EXACTLY ONE ioctl in the whole program returns a non-OK status, and it is
    NOT in cuCtxCreate: record 86, nvidiactl RM_CONTROL cmd=0x2080012f, NV status
    0x56 = NV_ERR_NOT_SUPPORTED (ogkm-580.159.04 .../inc/nvstatuscodes.h:115),
    inside cuInit, and libcuda proceeds. All 479 ioctls of cuCtxCreate return
    NV_OK on real hardware. So on this path "0x56 is the forgiven status" is not a
    heuristic: hardware issues it once, in cuInit, on 0x2080012f, and nowhere else.
    Any OTHER 0x56 our side emits is a divergence from hardware, whatever the
    caller does next.
  * ★ `nvdiff.py replies` answers, per control, whether RM actually WRITES a reply.
    24 of the 64 distinct controls are pure-IN: a non-zero paramsSize whose body RM
    returns completely unaltered (e.g. 0x20810108 hands over 992 bytes and gets 992
    identical bytes back; 0x0080170d 24 bytes x16 calls; 0x20808159 332 bytes).
    Because the body is captured on BOTH sides, "wrote nothing" here is a
    MEASUREMENT — the opposite of the C table's dlen=0 rows, which are unmeasured.
    Smallest reply in the set: 0x20808162, paramsSize=1, the single byte 0x00 -> 0x01.

⊘ WHAT THIS ORACLE CANNOT SEE — read before drawing a conclusion from a green diff
  1. It is an ioctl/mmap trace. Everything after cuCtxCreate is invisible to it (see
     the ce/launch identity above), so a green diff says NOTHING about the doorbell,
     pushbuffer, semaphore or completion planes. It bounds the CONTROL plane only.
  2. It records the userspace boundary. Whatever the guest's kernel driver and the
     GSP do between the ioctl and the hardware is not here.
  3. It is a HOST reference. It says what a real driver on real hardware does; it
     does not say what our emulation is permitted to do differently and still be
     correct. A divergence is a lead, not automatically a defect.
  4. The GSP RPC layer is NOT captured (see the scoping note in the harness).

⊘⊘ TWO CORRECTIONS TO THE PROVENANCE BLOCK ABOVE — both refuted by the captures themselves
   on 2026-08-10, at the first firing of the differential against a live guest. Neither
   invalidates a single reply body; both change how the DIFF must be read.

   ⊘ CORRECTION A — the reference host is a **FIVE-GPU** rig, not the single GPU named above.
     MEASURED from the captures, no re-run needed: record 1 is nvidiactl CARD_INFO, and its
     reply carries FIVE populated nv_ioctl_card_info entries (buses 0xc4, 0x41, 0x02, 0x82,
     0x81; device ids 10de:2504 x2 and 10de:2503 x3). `env_ctx.txt` corroborates it from the
     other side: devnodes = /dev/nvidia0 /dev/nvidia2 /dev/nvidia3 /dev/nvidia4 /dev/nvidia7.
     libcuda then reports `devices=1`, so the workload's own stdout gives no hint of this at
     all — the enumeration is entirely inside cuInit.
     ⇒ CONSEQUENCE, and it is large: a diff against any single-GPU subject shows four extra
     GPUs' worth of enumeration as MISSING calls, and the reference's chosen GPU is minor
     **7**, so `nvidia7:REGISTER_FD` mis-aligns against `nvidia0:REGISTER_FD` on the device
     node's NAME. The FIRST divergence by index is therefore CARD_INFO and it is a property
     of the rented box. ⊘ Rank by kind, not by index.
     ★ The 0x2504 die is still a GA106 and every claim about class/control COVERAGE, reply
     bodies and the single 0x56 stands unchanged. This scopes the reference; it does not
     devalue it — the same shape as the C oracle's FIFTH LIMIT.

   ⊘ CORRECTION B — the reference driver is the **CLOSED** module, not "(open)" as written.
     `env_ctx.txt` records `NVRM version: NVIDIA UNIX x86_64 Kernel Module 580.173.02`. The
     open module announces itself as `NVIDIA UNIX **Open** Kernel Module for x86_64` — which
     is exactly what the Mode-2 guest prints for its 580.159.04. So every host<->guest diff
     is cross-driver (closed 580.173.02 vs open 580.159.04) as well as cross-version, and
     CLAUDE.md's "the open driver is stricter, treat it as canonical" applies to the GUEST
     side of the comparison, not the reference side. A divergence may be a version or
     variant difference; the reference cannot by itself tell you which.
