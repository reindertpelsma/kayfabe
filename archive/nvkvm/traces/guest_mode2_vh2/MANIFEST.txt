★★★ THE WALL, NAMED — first divergence that ends the program
  The two streams run in lockstep to the very last successful call:

      HOST A[344] nvidia7:RM_ALLOC cls=0x0079    GUEST B[309] nvidia0:RM_ALLOC cls=0x0079
           A[345] RM_ALLOC cls=0x003e                 B[310] (same)
           A[346] RM_CONTROL 0x00000d01               B[311] (same)
           A[347] RM_MAP_MEMORY                       B[312] (same)
           A[348] UVM_CREATE_EXTERNAL_RANGE           B[313] (same)
           A[349] UVM_MAP_EXTERNAL_ALLOCATION         B[314] (same)
      ---- and then they part company, permanently ----
           A[350] RM_ALLOC cls=0x0040             B[315] RM_CONTROL 0x20801702  x175 -> killed
                  (NV01_MEMORY_LOCAL_USER)               (NV2080_CTRL_CMD_MC_SERVICE_INTERRUPTS,
                                                          engines=0xFFFFFFFF, one thread, forever)

  KIND: **EXTRA calls**, not missing, not a wrong value, and NOT a size mismatch.
  ⚠ 0x20801702 is called **0 times on real hardware in the entire 613-record program** and
  **175 times by us**, all from the single thread that was inside cuCtxCreate. It is the
  documented "service interrupts for the specified engines" escape hatch — i.e. libcuda
  waiting for a completion that never signalled and falling back to polling. This is the
  LOST WAKEUP, and the oracle gives it an index and an id rather than an inference.

  Progress measure: cuCtxCreate's first ioctl is A[129] on the host and B[94] here (the dev

★★ THE 0x56 CENSUS — the census the host reference makes possible
  Hardware issues exactly ONE non-OK status in the whole program: 0x2080012f
  (NV2080_CTRL_CMD_GPU_QUERY_ECC_STATUS) = 0x56, in cuInit. Subtract it and every
  remaining 0x56 we emit is a measured divergence. Ours (ctx_r1, all 490 records):

    id           name                                 guest   hardware   verdict
    0x2080012f   GPU_QUERY_ECC_STATUS                 0x56    0x56       ✓ the forgiven one
    0x20810108   (class 0x2081 NV2081_BINAPI)         0x56    NV_OK      ✗ DIVERGENCE, in cuInit
    0x2080200a   PERF_BOOST                           0x56    NV_OK      ✗ DIVERGENCE, in cuCtxCreate

  THREE 0x56 total, ONE of them legitimate. TWO-ITEM WORKLIST, and both are ranked:
    * 0x20810108 — guest B[41], host A[77]. paramsSize 992 on both sides. Host `replies`
      classes it PURE-IN: 992 bytes in, 992 identical bytes back. So NV_OK on a body RM
      does not touch — cheap to satisfy, and it is the FIRST status divergence in the
      whole stream. Not in ogkm's ctrl2081 headers (NV2081_BINAPI is a binary-API
      passthrough class), so its meaning must be recovered from the capture, not a header.
    * 0x2080200a PERF_BOOST — guest B[95], host A[130]. This is the **second ioctl of
      cuCtxCreate on both sides**, params `12000000 ffffffff`, 8 bytes. Hardware calls it
      TWICE (A[130] entering, A[478] leaving); we refuse the first and never reach the second.

  ⊘ SCOPE, and it matters: this is a **userspace** census. The same guest's kernel emits
  293 NVRM lines, saturated with `status=0x00000056` from `rpcRmApiFree_GSP` /
  `GspRmAlloc` — the RM<->GSP RPC plane, which this instrument cannot see at all. "Three
  0x56" is true of the ioctl boundary and false of the driver.

★ ONE MORE NON-ENVIRONMENTAL DIVERGENCE, and it is a ship milestone
  0x20800110 = NV2080_CTRL_CMD_GPU_GET_NAME_STRING, host A[114] / guest B[78], NV_OK both
  sides, same paramsSize. Host reply body @0x4 = "NVIDIA GeForce RTX 3060"; ours = 23 zero
  bytes. That is exactly why the workload prints `name=` (empty) and why `nvidia-smi`
  prints `ERR!` in the Name column. An NV_OK with an empty body — the "A WALL THAT CAN
  CARRY NO NAME" shape, here literally about a name.

⊘⊘ WHAT IS **NOT** A DEFECT — read before mining the diff further
  The raw `nvdiff.py diff` reports 1005 divergences and names CARD_INFO at A[1] as the
  first. ★ That first one is ENVIRONMENTAL and so are the great majority. See the ⊘
  CORRECTIONS appended to traces/host_reference_ga106/MANIFEST.txt: the reference host is a
  FIVE-GPU rig running the CLOSED driver, not the single-GPU open-driver box its provenance
  block described. Consequences you will hit immediately:
    * CARD_INFO returns 5 populated card entries there and 1 here.
    * A[18:22] four RM_CONTROL 0x215, A[28:60] thirty-two more, A[68:71] three more — all
      per-GPU enumeration of the four GPUs we do not have.
    * The reference's GPU is minor 7, so `nvidia7:REGISTER_FD` vs `nvidia0:REGISTER_FD`
      mis-aligns four blocks purely on the device node's NAME.
    * `hdr_post@0x4(hObject) 07 vs 03`, `params_post 00c4 vs 0300` — GPU instance and PCI
      bus leaking into handles and reply bodies.
  ⇒ Rank by KIND and by whether the field can depend on the rig, never by index alone.
