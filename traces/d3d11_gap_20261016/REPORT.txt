10. RANKED NEXT STEPS (evidence)
=====================================================================================================================
1. Lift user_lazy.rs (must_observe + PutCache) into the production relay: +52 % D3D11 in scratch, tests and mutation table exist. Choose N from the ladder (4/16/64) first.
2. Batch several GP entries per turn (one PUT/doorbell and one set of admissions per batch): the per-entry cost is 3.05 us of which ~half survives the lazy rules; the relay is still ~1.1 cores at 299 fps.
3. Cut the guest-USERD accessor cost (memory_list lookup + admission per access; 12-20 % of worker samples) with a cached lease for the relay's own USERD.
4. Remove per-entry allocation (Segment, snapshot Vec, receipts Vec in Fetch::observe): 12-15 % of worker samples; FAST_SEG removed only part.
5. Re-test worker pinning (involuntary switches 1,100-1,700/s per worker with no affinity) and the display cursor path (kf3-display 5 % of samples, cuMemcpyHtoD per 60 Hz tick).
6. Exercise mode 2 beyond Heaven (TLB-invalidate and context triggers, GravityMark growth, back-to-back registrations) before any lifecycle claim.

Resource costs seen (candidates for a later reduction, NOT changed): VRAM held by qemu ~9.0 GB (dmon fb 9,003-9,012 MB with the guest idle: 8 GiB declared framebuffer + store); BAR1 request 8 GiB, bar2 32 MiB (the guest sees BAR1 used 9,080 MB); the private ring storage is 1 MiB of device memory per USER channel
(2 MiB in my scratch layout; ~36 USER channels were live in Heaven) with 512 slots of which only ~1 is in flight on average; per-channel staging cells (512 KB) unused after 5080; 16 GiB guest RAM memfd on a 30 GB host (no headroom with swap off for a second guest);
the 60 Hz cursor/scanout path costs 0.08 core.
