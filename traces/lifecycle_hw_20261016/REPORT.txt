STATUS: RESEARCH, 2026-10-16. Measured on root@172.22.1.20 (RTX 4070 AD104, host driver 595.91.07 open modules, kernel 7.0.0-34,

Labels: MEASURED = observed in a command of this task, with its evidence file. INFERRED = reasoned, not observed.
Scope: LINUX ONLY. No Windows guest was started. The lifecycle must never be entered by a Linux channel; this report tests that and
the absence of any Linux regression against the base 0a7461173.

VERDICT IN ONE PARAGRAPH
H1 holds. e1e9947cc behaves for Linux guests exactly as 0a7461173 does: GPU-free tests 1,561 passed / 0 failed / 3 ignored; gates 9/9 +
gate 10 PASS with 12/12 USER births (the gate logs are identical to the base after stripping numbers); the 30-arm fast suite 30/30 in
all three runs (and the base 30/30 in both of its runs), with summed client time -0.46 % against the base (inside the noise); 161 channel
births per suite, all PRIVILEGED_CHANNEL=0 privilege=USER, identical per arm to the base and to the rootless audit; the only host Xids are
the five Xid 31 per suite that the frozen grader provokes on purpose (same five on the base); and no lifecycle line of any kind (0 of 150
suite QEMU logs, 0 of 10 broker-lane QEMU logs). The Linux display-broker lane with the Cinnamon guest boots, brings up KMS and Cinnamon,
runs glxgears at ~60 fps and shuts down cleanly when the guest is asked to power off, on both revisions. Three things are worth the owner's
attention and none is a regression: (1) the first suite run after the build was 10 to 45 % slower on eight arms (wall +14 %; a first-run effect: two later
runs of the same binary are at the base's level); (2) the ACPI power button does not power off the Cinnamon guest (same on the base);
(3) the host's dmesg Xid count is a saturated ring-buffer count, so "84 before and after" is not evidence of "no new Xid"
(also true of the rootless audit's statement). No falsifier fired.

6. HOST Xid AND KERNEL LOG (MEASURED; l2/xidmap_*.txt, l2/xid_journal_*.txt, l3/xidmap_*.txt)
 Journal Xid lines from 20:35 to 21:25: 25 in total, all "Xid 31, MMU Fault, CE0 HUBCLIENT_CE1", each mapped by PID to the QEMU in the
 sampler record: per suite exactly 5, four of them to --defer-liveness (FAULT_PTE ACCESS_TYPE_VIRT_READ at 0x60_00010000, 0x62_00010000 twice,
 0x64_00010000) and one to --missing-page-fault (FAULT_PDE VIRT_WRITE at 0xa_11000000); XID_UNMAPPED=0 in every suite. The base shows the same
 five. No Xid during the gates (either revision) or in any of the 10 broker-lane runs. Other host kernel lines: no BUG, oops, call trace, hung
 task or lockup; the NVRM warning counts are equal between the first e1e9947c suite and the first base suite (80 and 80).
 SURPRISE: the dmesg Xid count is not a counter. The kernel ring buffer here is full (1,799 lines), so it holds the newest 84 Xid lines and
 drops the oldest as new ones arrive: "84 before, 84 after" while 5 new Xids were logged (l2/xid_new_lc1b.txt shows the 5 rolled-out and the 5 new
 lines), and it later fell to 62 as other lines pushed Xid lines out. The rootless audit's "Xid count 84 before and after" and this task's own
 pre-registered baseline "84" are saturated. The journal (journalctl -k --since) is the right counter and is what the verdicts above use.
 Host state before and after: nvidia 15 modules refcount, nvidia_uvm 0, vfio_pci 0, kvm 1, GPU memory 10 MiB, no QEMU, lock free
 (l2/state_*.txt, l3/state_*.txt).

8. THINGS TO KNOW (FINDINGS)
 1. The first suite after a build can be 10 to 45 % slower on eight arms (A1; suite wall +14 %); two later runs of the same binary are not. Repeat before reading a
    single post-build suite as a regression. Cause not established.
 2. dmesg Xid counts saturate; use the journal and a PID map (scripts/bench/lifecycle_hw/xid_map.sh).
 3. scripts/bench/display/broker_lane.sh is stale for the current host (plasmashell, X11); interactive.sh is the working launcher.
 4. The ACPI power button does not shut the Cinnamon test guest down (new and base); interactive.sh stop waits 60 s and kills.
    The same guest's own poweroff takes 6 s to about 70 s.
 5. The product binary does not carry its revision (only the path and the build log do); a "bench claim carries its revision" rule rests on the
    directory name and the sha256 recorded here.
 6. Side effects on the shared host: build_kf3.sh re-linked the shared build dir /var/lib/kf-windows-20261005/qemu-build-kf3 (its
    qemu-system-x86_64 and libkf_qemu.a are now e1e9947c's) and copied this revision's kf3 overlay into the shared QEMU source tree
    qemu-10.2.4/hw/misc/kf3; this is the build script's standing behaviour, and the per-revision binary kf3-bins/e1e9947c is left in place on
    purpose (task step L1). The pre-existing kf3-bins/0a746117 is unchanged (same sha256).
 7. A window "kayfabe guest" was shown on the host's live desktop for 10 short periods (section 5).

9. NOT DONE / LIMITS
