## Findings (bucket: 1 documented limitation, 2 app/harness bug confirmed by a control, 3 our own config/script error, G kayfabe gap)
- F1 windows_apps, **bucket G (kayfabe-infra)**, release blocker on `next`: the pinned public bundle (`bundle.pin`, built 2026-11-08 from 38bbbb2e9) no longer matches the tree's recipe inputs. MEASURED: the ISO downloads and equals the pin's sha256, then `verify_image` raises `embedded recipe input identity mismatch` (derived b8694b93..., embedded ed2ddea1...); recomputing with `appmatrix/apps.json` and `appmatrix/guest/py/win_cuda_equiv.py` at their 38bbbb2e9 versions gives ed2ddea1... exactly, with only `apps.json` reverted it does not; those two inputs changed through #470, #471 and #475 (the union). MISLEADING CLASS (finding): a deterministic pin drift is graded `WINAPPS_RETRY class=MEDIA rerun-on-a-fresh-box` and the cause is swallowed by a generic `except`. Nothing in CI compared `bundle.pin` with the tree (`bundle-publish.yml` is manual and master-only). Fixes: #529 (republish, new pin), #530 (offline `RepoPin` test, drift refused before the first request and before the 2.7 GB ISO, closed reason set RECIPE_INPUT_DRIFT / PIN_MISMATCH / NETWORK / OTHER, non-retry class). Evidence: `w/final/workspace/diag_winapps_fetch_bundle.txt`, `w/final/workspace/payload_stdout_WW1.log`.
- F2 apps_discovery, **bucket 3 (our own stage environment) plus one known kayfabe gap**: first run (`a/latest`, 1570 s): `discovery_not_run:nvml_dcgm,vllm,tensorrt,jax`. Root causes (independent triage of the box logs): (a) the STAGE BOOTED THE BASE GUEST IMAGE: `apps_discovery_stage.py` never sets `KF_GUEST_IMG` (the apps stage uses `guest_apps.qcow2`); MEASURED: the boots say `image=/workspace/bench/guest.qcow2` and `tee: /opt/apps/bundle/run_apps.sh: No such file or directory`; the base image was also WRITTEN by the six boots (new mtime); this made nvcodec_matrix `HANG rc=ssh127`, nvml_dcgm `rc=127` (no `/opt/apps/venv`), vkcts `CONFIG ... notrun=291` (INFERRED: no libvulkan1 in the base); (b) the wedge rule printed `boot wedged` after every boot (false positive when the sample binary is absent); (c) vllm: `python3-dev` is in neither the recipe nor `setup_side.sh` (`python_h:false`); (d) tensorrt and jax: the host `mlrows.py setup` refused `python_too_old: 3.10 < 3.12` (stock Ubuntu 22.04; nothing in provision installs 3.12), the stage booted those rows anyway; (e) grading holes: a HANG without a result and a CONFIG failure counted as rows that ran. CONTROL on the same box and tree with the apps image selected through `KF_GUEST_IMG` (leg WA3, `a/final/workspace/diag_apps_discovery_control.txt`): nvml_dcgm PASS, vkcts PASS (291 cases: 200 pass, 89 not supported, 0 fail, 0 crash, 2 timeout), nvcodec_matrix FAIL (first failing case `enc_av1_420_8_1080p expect=SUPPORTED rc=234`: needs the host control, which is absent on a payload box: bucket open), vllm NOT_RUN (python3-dev), tensorrt and jax NOT_RUN (python 3.10). The two vkcts timeouts are exactly the known sparse residency cases (`storage_texel_buffer_read_size_2_24_r32ui`, `multisampled_image_sparse_residency.rgba16ui.samples_4`) and the host logged two `Xid 109 CTX SWITCH TIMEOUT` (channel 0x31, Info 0x6c022) at their times, so the xid-watch voided the control (`rc=6 host_xid`): the documented sparse-residency gap (finding ledger 3, `unmapped-reads-zero` mitigation), reproduced on 7fb1c98a0 on a 4090: bucket G (known). Fixes: #533 (test first: apps image set and refused otherwise by name, throwaway overlay instead of the base image, NOT_RUN grading, pre-boot refusal of rows the host setup refused, python3-dev); OPEN design decision: where Python 3.12 comes from on a 22.04 host.
- F3 specviewperf, **bucket 3 / G**: `SPECVIEWPERF_STAGE_RETRY class=TIME`, 9 of 9 rows NOT_RUN: the stream of the 42 GB bundle into the guest (`stream_url | zstd -d --long=31 | tarfilter | ssh tar`) hit the hard-coded `timeout "$(cap 4200)"` of `specviewperf_stage.sh` line 633 (copy aborted after 73 min, `abort class=TIME stage=copy`). MEASURED: 5 MB/s at the box's rx counter (four samples) while a ranged GET of the same object from the same box ran at 10 MB/s, so the link is not the limit; the earlier box (Ryzen 9 5950X) needed 51 min for the same step (13.7 MB/s). INFERRED: the single ssh stream through the guest's user-mode network is host-single-thread-bound (EPYC 7B13 VM against 5950X); not separated. Evidence: `b/final/workspace/diag_spec_stage.log`. Fix in wave 1b: a budget knob derived from the bundle size and a measured rate, with copy-progress notes (PR below); rerun on a high single-thread-clock box.
- F4 offer RAM rule, **bucket 3**: the pick_offer default (96 GB listed) was calibrated on 24 GB dies; the RTX 4090 48 GB variant at 125 GB listed (103.6 GB MemTotal) cannot run `managed_oversub` (needs MemAvailable of at least 1.25 x VRAM / 0.6; a KVM box shows 75 to 83 percent of the listed RAM). Closed in wave 1 by box K (24 GB die, 205 GB): 6/6. Fix: PR below (offer policy constraint derived from the offer's own VRAM).
- F5 (backlog design item for the owner, not built): the SPEC copy transport. Streaming 42 GB through `ssh tar` over the guest's user-mode network is single-thread-bound and takes 50 to 140 minutes depending on the host CPU. A prepared disk image or ISO of the lane tree built on the host (zstd decompress and tarfilter on the host at disk speed) and attached to the guest as a second drive would remove the transport from the critical path and from the budget; needs the lane's file list, a read-only attach, and a check that the guest-side copy is a local `robocopy`. Not designed further here.
