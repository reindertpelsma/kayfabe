NATIVE WINDOWS HEAVEN 4.0 REFERENCE ON A VAST GPU (D3D11 vs OpenGL) - REPORT
Branch claude/native-vast-20261016. Written 2026-10-17T00:35Z. Owner pause received: no further measurement; boxes torn down.

SHORT ANSWER
The one box that worked (RTX 4070 Ti Super, 4 vCPU) is CPU-BOUND in both APIs: Heaven's main render thread sits at 98-103% of one core
(MEASURED, per-thread sampling), the GPU is 35-40% busy, D3D11 and OpenGL both give about 133 fps. So it does NOT reproduce the "native D3D11
about 330 fps, GPU-bound" reference, and absolute fps, watts, W/util and J/frame from it must not be compared with kayfabe's GPU-bound runs.
What does transfer is the shape per API (ratios). Kayfabe's D3D11 is slow in a way native D3D11 is not:
  GPU-busy time per frame, D3D11 / OpenGL:  native 0.88   kayfabe scan-off 1.78   (kayfabe/native double ratio 2.0)   [MEASURED, ratios]
  fps D3D11 / OpenGL:                        native 1.00   kayfabe scan-off 0.56
  J/frame D3D11 / OpenGL:                    native 0.96   kayfabe scan-off 1.25
  PCIe MB/frame D3D11 / OpenGL:              native 0.96   kayfabe 1.57 (D3D11 scan-off vs GL scan-on; see limits)
Native D3D11 costs about the same GPU time per frame as native OpenGL; kayfabe's D3D11 costs about twice as much GPU time per frame relative to its
OpenGL, while OpenGL matches. That points at GPU-side work inflated by running under kayfabe (INFERRED: the open list already in the lifecycle
report: 4 KiB PTEs, no compression, ...), not at relay latency or power. A GPU-bound native run on a fast-CPU box is still missing (see RESUME).

HYPOTHESES (PREREG.md, ratio-form addendum; MEASURED vs INFERRED marked)
 HN1r held on its face, NOT interpretable. Native W per sm% (D3D11) is 2.77 vs kayfabe 1.30 (2.1x, falsifier "within 15%" not hit). But the native GPU is 35%
   busy: power is not proportional to sm% (idle floor, clocks, memory activity), so W/sm% is not comparable between a 35% and a 94% busy GPU. Secondary
   prediction "J/frame about equal": native 0.722 vs kayfabe 0.647 (+12%, inside 25%) for D3D11, but native GL 0.749 vs kayfabe GL 0.517; the native J/frame
   here is inflated by waiting for the CPU. r_E says kayfabe's D3D11 spends 25% more energy per frame than its GL, native 4% less.
 HN2 mostly held: native r_P = 0.96, inside [0.5, 2]. The kayfabe half ("differs, outside the band") is NOT supported: its r_P is 1.57, inside, with the
   mixed scan state. Absolute PCIe per frame is the clearer signal: kayfabe moves 2.3-3.7x the bytes per frame that native does (INFERRED: partly the
   host-side relay's own traffic, partly the card's x16 vs x8 link; not separated here).
 HN3r not falsified but uninformative: native r_fps = 1.00 (band 0.92-1.02), falsifier "< 0.9" not hit; however both APIs are capped by one CPU thread, so
   this says nothing on whether 330/342 fps was setup-local. A GPU-bound native run is required to judge it.
 HN4 NOT RUN (a HAGS/Game Mode/power plan A/B on a CPU-bound box would measure nothing).
SKU-versus-kayfabe confounds (all INFERRED): 66 vs 46 SMs, 256-bit vs 192-bit, 285 W vs 200 W limit, x8 link, 4 slow vCPUs vs a fast desktop CPU, the QEMU VM
around the native Windows (kvm exits for BAR0 etc. are cheap here because nothing is trapped but it is still a VM), Defender on, 60 Hz virtual display.
The GPU-busy-time ratio is the least SKU-sensitive number, and it is the one that separates kayfabe from native (2.0x).

LIMITS (read before quoting)
- 2 runs per API, not 3; one warm-up. - GPU util (sm%) is "any kernel running", so under CPU starvation it overstates work; use it for ratios only.
- No GPU-bound native datapoint; the 330/342 fps local figures remain inherited, not re-measured. - Box 2 (4080 Super, fast CPU) never became reachable.
- kayfabe GL PCIe is scan-on (no complete scan-off GL run has the PCIe columns).
