ROOTLESS AUDIT: does kayfabe run as an unprivileged user with only /dev/kvm?

STATUS: RESEARCH, 2026-10-16 (measured on the trusted host: one revision, one GPU, one distro).
Claim under test (owner): "kayfabe runs as an unprivileged user with only /dev/kvm access: no root, no VFIO rebind, no kernel
module or driver install, the host keeps its GPU and desktop, and uninstalling is deleting one folder."
Labels: MEASURED = observed in a run of this audit. INFERRED = reasoned, not run.

VERDICT IN ONE PARAGRAPH
The claim, never tested before, holds on the tested configuration. A throwaway user with groups "kfrootless, kvm" and nothing else
(CapEff = 0, RLIMIT_MEMLOCK = 8 MiB, no sudo) ran the kf3 Linux fast suite 30/30, the nine kf-gate binaries plus gate 10 (9/9 and
PASS), and a Windows 11 guest on the stock Windows driver through Unigine Heaven D3D11: 94.05 and 91.05 fps against 92.90 and
93.27 fps for root with the same binary and flags (-0.6 % on the mean, inside a 3.3 % run-to-run spread). The product asked for no
capability: the only host-log lines that differ between the root and the user runs are the "cap_sys_admin=cleared-for-call /
not-held" note itself. Nothing was left on the host outside the user's home. Three qualifiers: (1) "only /dev/kvm" is true because
NVIDIA's stock install makes /dev/nvidia* mode 0666 (measured here, inferred for other distros); (2) the host desktop here renders
on the AMD iGPU, so "the desktop keeps the NVIDIA GPU" was NOT tested; (3) a real desktop window needs the desktop user itself,
which no other uid can reach (measured EACCES). Seven small defects/dependencies were found (section 4); none needs root at run time.

SETUP (MEASURED)
Host root@172.22.1.20, Ubuntu 26.04, kernel 7.0.0-34, stock nvidia-dkms-595-open 595.91.07, RTX 4070 (AD104); every run printed
"kf-host: host tier: stock". Product = qemu-system-x86_64 of kf3 revision 0a746117 (sha256 0445f3d69d3a5d43...f128c5a8, byte-identical to
kf3-bins/0a746117), installed read-only in one folder (/data/claude-rootless/inst: bin/qemu-system-x86_64, bin/nvkvm-display-broker,
share/qemu/, 104 MB). User: useradd -m -G kvm kfrootless (uid 1002), started with setpriv --reuid --regid --groups=kvm env -i, so no
root environment leaks in. Pre-registration: PREREG.md (written after the read-only recon R0, before any run).

2. WHAT WAS RUN
R0 recon (read-only). r0/r0_recon_before.txt: /dev/kvm root:kvm 0660 + ACL; /dev/nvidia* 0666; /dev/udmabuf root:kvm 0660 from the
stock rule 50-udev-default.rules:125; /dev/userfaultfd 0600 root; /dev/dri/* video/render 0660; RLIMIT_MEMLOCK 8 MiB
(DefaultLimitMEMLOCK=8388608); vm.unprivileged_userfaultfd=0; io_uring and user namespaces open to an ordinary user
(r0/probe_unpriv.txt); hugepages 0; fs.protected_regular=2.
strace -f of a root fast guest (r0/root_strace_summary.txt): the QEMU opens /dev/kvm, /dev/nvidiactl (25x), /dev/nvidia0 (13x),
/dev/nvidia-uvm (2x), reads /proc/driver/nvidia/* and /sys/bus/pci/devices/0000:01:00.0/{class,device,resource,...}, opens
$HOME/.nv/ComputeCache (libcuda) and memfds. RM calls are the stock escapes on /dev/nvidiactl and /dev/nvidia0: NV_ESC_RM_CONTROL
0x2a (349x in the --timer arm), RM_ALLOC 0x2b, RM_FREE 0x29, RM_MAP_MEMORY_DMA 0x57, RM_UNMAP_MEMORY_DMA 0x58 (names as in
crates/kf-linux-raw), plus 0x4e, 0x4f, 0x27 and 0xc8..0xf0 (not decoded here) and the UVM escapes. No CAP_ check is visible outside
RM. The process calls capget/capset (the CAP_SYS_ADMIN bracket around channel births) and raises RLIMIT_NOFILE soft to hard
(1024 -> 524288). It never calls userfaultfd, io_uring_setup, perf_event_open, bpf, mount, unshare or mlock*, and maps nothing
MAP_LOCKED or hugetlb.

R1 Linux, as kfrootless.
- Smallest lane (--timer) PASS in 5 s. fast_suite.sh us1 180: 30 PASS, 0 FAIL, 0 CRASH, 0 NOTRUN in 3 min 52 s
  (r1/fast_suite_user.out). Same suite as root, same binary: 30/30 (r1/fast_suite_root.out). Summed raw client time 67.3 s (user)
  vs 66.6 s (root); per arm within about 1 s (largest: ce-client-guest-ram 20.78 s vs 20.15 s).
- Privilege record per arm (r1/cmp_root_vs_user_suite.txt): 175 channel births over the suite, all PRIVILEGED_CHANNEL=0
  privilege=USER; the set of REFUSED / "refused by" / PRIVILEGED lines is identical for root and user in all 30 arms. So the root runs
  the project always did were not hiding a privileged control: the host controls the product asks are all unprivileged (the one
  known privileged control, GR_GET_PHYS_GPC_MASK 0x20801232, is by design not asked; traces/real_ad104 measured it refused 0x1b to a
  client without CAP_SYS_ADMIN, in 2026-09-26).
- strace -f of five arms as root and as user (r1/*_strace2_summary.txt): same open set, same failing-ioctl set, 0 EPERM/EACCES as user.
- v3_gates.sh: root and user both "pass=9 fail=0 gate10=PASS", births 12/12 USER, refused 0 (r1/v3_gates_*.log; normalised
  comparison r1/gates_normalized_*.txt: only the cap note differs). The user run needed a stub cargo (F4).
- RLIMIT_MEMLOCK did not matter: during --ce-client-guest-ram and --guest-ram-pin (2 GiB guest RAM pinned through the nvidia
  driver) VmLck = 0 kB and VmPin = 0 kB over 24 samples (r1/pinwatch.txt) and both arms PASS. The limit is live: a 64 MiB MAP_LOCKED
  mmap returns EAGAIN for this user (r0/probe_unpriv.txt).

R2 Windows, as kfrootless. scripts/bench/rootless/win_launch.sh replicates the production QEMU line of windows_broker.sh (production
flag list, 8 vCPU, 16 GiB, fb 8192 MiB, BAR1 8 GiB, hv_* CPU) and starts the display broker as the same uid with --backend test (no
compositor needed). Image: overlay of win11-full-b/windows11.qcow2 in the user's home; Heaven was installed once through the kfagent
channel (the guest sees no CD-ROM in this image, so the installer was served over the slirp loopback) into a staged overlay u0;
every run uses a fresh overlay backed by u0. Runs alternate user, root, user, root:

 run  uid   CapEff  Heaven D3D11 FPS   min     max     score
 u1   1002   0       94.05              17.61   212.41  2369.20
 r1   0      full    92.90              20.81   173.93  2340.26
 u2   1002   0       91.05              20.11   177.00  2293.58
 r2   0      full    93.27              21.11   179.23  2349.37
 mean: user 92.55, root 93.09 (-0.6 %); spread over the four runs 3.3 %.

All four ran the full in-app benchmark (260.6 s of benchmark time, about 288 s wall). 76 channel births per run, all USER; the REFUSED
line sets of u1/r1 and u2/r2 are identical except the cap note (r2/*/norm_*.txt). The expected ~100 fps was not reproduced (about 93 for
both uids); it is the same binary and flags for both, so the root-vs-user comparison stands, and the cause (revision, test-backend
broker, cold first launch per fresh overlay) was not investigated. The broker received 17 246 attach/commit frames in u1; the user
QEMU opened /dev/udmabuf and sent LINEAR dma-bufs ("kf3: broker: /dev/udmabuf opened"), which works with group kvm only. The guest
sees the RTX 4070, driver 580.88, 8192 MiB.
Display broker / desktop session, unprivileged: not needed for the test backend. For a real window the broker must run in the desktop
session: /run/user/1000 is 0700 and /tmp/.X11-unix/X0 is srwxrwxr-x ubuntu:ubuntu; as kfrootless connect() to the Wayland socket and to
both X sockets returns EACCES (MEASURED). The natural unprivileged deployment is the desktop user itself running QEMU and broker
(the peer policy admits QEMU's effective uid, V3_DISPLAY.md 8.5, so same-uid needs no extra property); a different uid needs a
desktop-side grant (an ACL on the runtime dir), a user action, not a root install. A real Wayland window as the desktop user was NOT
run (it would put a window on the owner's screen).

backend, not a window, and no PresentMon.
