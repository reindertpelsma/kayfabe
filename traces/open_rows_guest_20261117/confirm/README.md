**H-A held.** On the fixed kf3 the DGC case passes alone and there is no Xid; on the control, in the same box and the same kind of boot, it fails alone with the same Xid 13 as before (V1, V1b, V2 of the parent run: now a fifth reproduction, and the first pair that differs in one source file). Falsifier (Xid 13 on the fixed kf3) not observed.

**H-B, direction held, mechanism not shown.** The residency cases hang with Xid 109; the fully bound cases pass before and after the fault, so the hang is not left-over state. Two corrections to the brief: (1) the named twin `texel_buffers.sparse_binding.storage_texel_buffer_read_size_2_24_r32ui` does not exist in vulkan-cts-1.4.7.1 (`mustpass/main/vk-default/sparse-resources.txt` has only `texel_buffers.sparse_residency.*`, 36 cases); the texel-buffer test binds every second 64 KiB slot (`sparseBindNdx += 2`) with `MemoryRequirement::Any` memory and dispatches one workgroup per texel over the WHOLE buffer, so `size_2_10` and `size_2_16` (one slot) are fully bound variants of the same shader but 256 to 16384 times smaller, size is confounded with residency; (2) the size-matched pair is the image one (`multisampled_image_sparse_binding` against `..._residency`, same format and samples), which separates the two the way the brief wanted. Falsifier ("the twin also times out or raises Xid 109") not observed in either pair. The kf3 logs show no kayfabe-visible per-case signal that tells the pairs apart (`REFUSED` leaf lines occur in passing rows too: 15 in A1, B1 `t16a` and C1 `msbind_a`, 0 in the second passes, 4 in the residency cases; no fault or park line), so this run does not show that "kf-mem never writes sparse page-table entries": it shows that a shader that reads non-resident parts of a sparse resource stalls the GR context until the host's context-switch watchdog fires, in the guest only (the host passes the same cases).
