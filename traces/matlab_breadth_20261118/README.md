# MATLAB breadth rows on the Linux proprietary image, first hardware run (2026-11-18)

Run: one rented KVM box with an RTX 3090 (GA102, 24 GiB, Ampere), AMD EPYC host, nested KVM; the first box rented (RTX 4090) never started ("GPU error, unable to start instance") and was destroyed unused. Host driver swapped by `provision_host_driver.sh` from 575.51.03 to 580.159.04 (open module); QEMU 10.2.4 kf3 built from `dfba3346` (no kf3 code differs from the branch head). Guest: image C (sealed 2026-11-17, MATLAB R2026b, Parallel Computing Toolbox, Deep Learning Toolbox), offline clone, 2 vCPU, **4 GiB RAM**, `fb-mb=4096`, guest driver 590.48.01 (public installer, NVIDIA's own checksum). Runner: `matlab_rows.py run --dir ... --isolation shared` (the payload stage was not used). Row scripts: run1 at `dfba33467`, run2 at `97ab1bbd` (`run2/` contains the rows re-run after fixing three authoring errors).
Local patches on the box only, not in git: the preamble's guest-memory check disabled in both runs (see Finding 1: it fails by itself, `run0_preamble/`); in run2 the `matlab_examples` time-box 900 s, `example_max` 8 and the training environments reduced to cpu, gpu and auto. The guest has no `matlab` on its PATH: `--matlab /home/<user>/MATLAB/R2026b/bin/matlab` was needed (a stage default of `matlab` fails with rc 127: our configuration).
Falsifier of the whole exercise, stated before the run: "every new row runs to the end under kf3 and passes against its CPU oracle; any FAIL is a kayfabe gap, an application or authoring bug (with a control), or our configuration".

## Findings

1. **VRAM size: MATLAB reports 3.97 GB on a 24 GB die** (`run0_preamble/`: `TOTAL_MEMORY_OUT_OF_RANGE guest=3968073728 host_mib=24576`). Known gap #2 of the GPU-PV list confirmed on GA102 under kf3; the guest framebuffer is `fb-mb=4096`. The preamble correctly refuses to continue; both runs bypassed that one check on the box.
2. **The host `mem` engine cannot show use under kf3**: host `memory.used` went 4664 to 4674 or 4675 MiB (baseline taken after the guest started) in rows that allocate tens to hundreds of MiB, so every row that requires `mem` FAILS `GPU_NOT_USED` although the same window shows 955 to 9624 GPFIFO submissions. INFERRED mechanism: the 4 GiB framebuffer is carved out when the VM starts. Consequence applied: the new rows require only `gpu`; the first eight rows still require `mem` and will fail the same way (not changed here).
3. Numerics: 93 of the 97 required numeric checks of the nine rows that completed and passed their authoring fixes agree with the CPU at the host's tolerances; the three single-precision misses (rmsprop parameters 1.17e-4, a single-precision convolution gradient 2.5e-4, a 2048-image predict 1.7e-4) are 1.2 to 2.5 times the 1e-4 tolerance, all have a passing double-precision or smaller-batch twin, and the pattern (cuDNN reduced-precision paths, accumulation order) is the rule (3) case of the design: tolerance, not a kayfabe finding, until a native run on the same die shows a different size.
4. **No Xid, no refused or unserviced op** in any window of either run; a launch-heavy row (about 350 000 launches) completed in 28 s with 1025 submissions counted: the census is a floor of use, not a launch counter (doorbell writes are not trapped).
5. **Feature sweep, `methods('gpuArray')`**: 216 unary methods tested, 196 pass (90.7 percent), 4 differ (`isgpuarray`, `sprand`, `sprandn`, `sprandsym`: by design, added to the skip list), 9 throw on the GPU where the CPU works: `acosh`, `acoth`, `acsc`, `acscd`, `asec`, `asecd` (the documented rule that a complex result needs a complex input), `condest`, `issorted`, `lu` (not explained: the next run should record the identifiers). 157 methods need more than one argument (not testable by this sweep), 7 non-numeric, 25 skipped.
6. **Layer sweep**: 31 constructors tested, 30 pass, 1 differs (`selfAttentionLayer`), 3 constructors failed on the CPU too (`resize2dLayer`, `depthToSpace2dLayer`, `maxPooling1dLayer`: argument or release naming, our configuration). Training matrix, 12 cells (cpu, gpu, auto by 4 solvers): 9 pass, 3 `lbfgs` cells threw `nnet_cnn:trainingOptions:InvalidTrainingOptions` (authoring error: lbfgs takes no mini-batch options; fixed after the run, unverified).
7. **Error paths** (identifiers recorded): inner-dimension mismatch `MATLAB:innerdim` on both; out of memory `parallel:gpu:array:OOM`; a cell given to `gpuArray` `parallel:gpu:array:UnsupportedInputType`; a non-PTX file given to `CUDAKernel` `parallel:gpu:kernel:InvalidInputArgument`; an out-of-range index is `MATLAB:badsubscript` on the CPU and `parallel:array:SubsrefSubscriptExceedsDim` on the GPU (different classes; the host table now expects the GPU family only). No native reference was run, so "same as the host" is NOT established: only that the errors are raised and are MATLAB's own.
8. **Shipped examples are not in the offline image**: `<matlab root>/examples` does not exist and the install holds two live scripts (`toolbox/matlab/demos`), the HPC Challenge benchmark scripts (`toolbox/parallel/examples/benchmark`) and the neural-network sample data sets (`toolbox/nnet/nndemos/nndatasets`); the documentation examples come with the documentation, which the image lacks (`help` is 32 MB). The row's discovery found 0 examples (`examples_discovered` 0, MEASURED). Fix for the owner: install the offline documentation (checklist section 4), then the row discovers them.
9. **The `matlab_examples` row did not finish**: the guest has 4 GiB RAM and ran out (3883 of 3911 MB used, `kswapd` busy) while the training matrix with parallel environments (run1, 24 cells) and again in the reduced run2 messy variants; run1's row was stopped by hand after 28 minutes with the guest swapping, run2's hit its 900 s box. Parts 4 (messy variants: memory pressure, odd shapes, reset, killed worker, soak) and 5 (CPU control) are therefore NOT MEASURED. Our configuration (guest RAM), not a finding about kayfabe; the row now writes a partial document after each part.
10. Lead, not chased: after the host driver swap on the first box that started (575.51.03 to 580.159.04, RTX 3090, Vast KVM), the host driver failed to initialise the GPU (`NV_ERR_TIMEOUT` waiting for GFW boot, "the GPU may be in a bad state and may need to be reset") until the VM was rebooted once; this was before any guest started and is a box or Vast matter until shown otherwise.

## Not proven

No native-Linux control of any row (no row has a bare-metal reference); one die; one guest driver; the gpuArray and layer sweeps ran once; rows were run in one shared boot (a failure of one row could have influenced the next, none crashed); the fixes to `gpu_sparse` (nnz check), `kf_enum_train` (lbfgs options) and the example discovery were made AFTER the run and have not run; the kf3 binary was built from `dfba3346` while the rows are from `dfba33467` and `97ab1bbd` (script changes only).
