WHAT WAS NEWLY MEASURED (all on open 580.159.04, unprivileged userspace RM client)
--------------------------------------------------------------------------------
[A] ARCHITECTURE CONFIRMED FROM SOURCE — the module CANNOT allocate a compute
    (GR) channel via the exported UVM interface. nvUvmInterfaceTsgAllocate /
    ChannelAllocate reject every engineType except CE and SEC2:
      nv_gpu_ops.c:6371-6372  if (engineType != CE && engineType != SEC2)
                                  return NV_ERR_INVALID_ARGUMENT;
      nv_gpu_ops.c:6390 comment "nvGpuOps only allocates channels/TSGs for CE
                                  and SEC2 engine types."
    => The userspace-RM-client split of design correction (2) is MANDATORY, not
       just preferable: the faulting compute channel MUST be created by an
       unprivileged userspace client and adopted by the module (Dup/Retain).

[B] ***KEY RESULT*** Unprivileged userspace CAN create the N4 fault-capable VAS.
    FERMI_VASPACE_A with flags = ENABLE_PAGE_FAULTING(BIT6) | IS_EXTERNALLY_OWNED(BIT3)
    = 0x48  -> RM status 0x0 (NV_OK).  (nvos.h:3170,3173; vaspace_api.c:611-619
    grants these flags with no privilege gate.)  This was previously only a
    source reading in V3_UVM_DEMAND_PAGING §12.3.1(2); it is now measured.
    (see box_out/rmlaunch_run.txt line "[S1] VAS FAULTING status=0x0")

BLOCKER (exact call + status + source)
--------------------------------------------------------------------------------
Blocked while wiring the userspace RM client's memory mapping (needed before any
channel/QMD work). A 64 KiB NV01_MEMORY_SYSTEM object allocates OK, but:

  1. CPU map: NV_ESC_RM_MAP_MEMORY (0x4E) — SOLVED the ABI (needs the
     nv_ioctl_nvos33_parameters_with_fd wrapper {NVOS33_PARAMETERS; int fd;},
     is NV_CTL_DEVICE_ONLY so issued on ctlfd with fd=devfd; escape.c:507-534) —
     the ioctl now succeeds (r=0) but RM returns status 0x1F = NV_ERR_INVALID_ARGUMENT
     for BOTH hDevice and hSubdevice as the map handle. serverMap_Prologue
     (mapping_cpu.c:876-958) passes for this case, so 0x1F arises in the map body
     or rm_create_mmap_context (not fully root-caused in budget).

  2. GPU-VA map: NV_ESC_RM_MAP_MEMORY_DMA (0x57, NVOS46, CTL_DEVICE_ONLY, hDma=VAS)
     -> RM status 0x33 = NV_ERR_INVALID_OBJECT_HANDLE. Source: the map-dma path
     hits "pSrcMemDesc != NULL -> NV_ERR_INVALID_OBJECT_HANDLE" (mapping.c:152) —
     the source memory descriptor resolves NULL in the DMA-map context. Likely a
     wrong-parent / needs-virtual-reservation issue (NV01_MEMORY_VIRTUAL) not
     resolved in budget.
