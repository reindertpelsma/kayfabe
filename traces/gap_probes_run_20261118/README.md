# GPU-PV gap probes and Vulkan CTS groups, host against kf3 guest (2026-11-18)

**STATUS: EVIDENCE, 2026-11-18.** MEASURED, one run on one box, text only (UUIDs, PCI addresses and IP addresses scrubbed). The reading of it is in `docs/design/V3_GPUPV_GAP_MATRIX.md` sections 3.4 and 3.5. Nothing here is a claim about another die, driver or day.

- **Box**: one Vast KVM VM, RTX 3090 (GA102, 24 GB), Xeon W-2133 as a VM with 11 vCPU and 98 GB RAM, Ubuntu 22.04, host and guest driver 580.159.04 (`box_facts.txt`). Rented about 02:16 UTC, destroyed by its own id at about 05:50 UTC and verified absent; about 3.6 h.
- **kf3 revisions**: `4065c82a` (the crates are byte-identical to `claude/accept-final-tree-20261118` `2fab69396`, PR 480 absent) and `8aa94098-dirty` (the same crates plus the diff of PR 480's commits `e0e6b15d1` and `fa87599a6`, `kf-mem/src/apply.rs` only). Probe code revisions are in the matrix document (3.4): `a41eaaa2`, `a8545da3`, `6345785b`, `8aa94098`.
- **Layout**
  - `gap/`: the `gap_probes` row. `H1` host first probe version, `H1c` host control with the fixed probes, `H2`, `H3`, `H4` host reruns (corrected cases, Vulkan dump, global priority); `G1` to `G7` guest runs (`G2` life_reset, `G3` busy power-off, `G4` kill probes, `G5` rerun with the host-state watcher, `G6` Vulkan dump, `G7` global priority). `*.log` holds the harness blocks (`results.tsv`, `kv.tsv`, `summary.txt`, `vk_leaves.tsv`) between `@@FILE` markers; `*.res` is the matrix line of the run with the kf3 census; `compare_*.txt` are `gap_probes.py compare` outputs (`compare_host_H1_vs_H1c.txt` is the host-against-host noise floor); `hoststate_G5.*` the host control-state watcher (four fields); `census_rows.tsv` the per-run census.
  - `cts/`: `caselist.tsv`, `chunk*.tsv` (sample 1), `b*.tsv` (sample 2), `sample_notes.txt`, `b_notes.txt`, `pins_cts.json` (90 s per case on the host; the guest runs used 60 s and a 2500 s budget per boot, the box tree's `pins.json`); `host*.log` host results blocks; `guest1_without_pr480.log`, `guest1_with_pr480.log`, `guest2_with_pr480.log`, `guest3_with_pr480.log`, `guestb*_with_pr480.log` guest results blocks; `report_*.txt` the per-group counts and the differing cases (`cts_report.py`, known limits applied); `flips_pr480.txt` the cases whose class changes with PR 480. The third sample was not run.
  - `confirm/`: the cases still different with PR 480, each alone in a fresh guest boot (`guestF1.log` to `guestF6.log`, 240 s per case), the host control twice (`confh1.log`, `confh2.log`), the neighbour boot with the two info cases only (`guestN1_info_only.log`) and `kf3_refused_delta.txt` (the refused RM controls of each failing boot that the neighbour lacks).
  - `host_xid_lines.txt`: every host Xid line of the box with its ISO time; `steps/`: the chain logs with box timestamps.
- **Known slips of this run** (kept, not hidden): the first run of the fault and persistenced probes failed on the host control (harness defects, fixed); the first host-state watcher read a live clock (fixed); the second CTS sample repeats 301 cases of the first (a trailing newline in my deduplication); the first attempt of the PR 480 control run started before the binary existed and was killed and restarted (it is not in the evidence); the tools Nsight Compute and Nsight Systems were not pushed into the guest.
