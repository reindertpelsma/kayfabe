0. HARNESS FINDINGS THAT CHANGE HOW "ACCEPTED" IS READ (MEASURED)
 * The channel stays alive after a legal sequence and dies after a faulting one: after a fault the later semaphore releases never
   arrive, the channel error notifier carries the RC code (13 = graphics exception, 32 = PBDMA error) and the host journal has an
   "NVRM: Xid ... pid=<probe pid>, name=setobj_probe" line.
 * A fault caused by a SOFTWARE method / software-subchannel SET_OBJECT is ASYNCHRONOUS to the semaphore in the SAME pushbuffer:
   in c_badsw and in every S3 case the semaphore right after the offending method still arrived (ne=0 at that moment) and the notifier
   showed the error 250 ms later. A semaphore alone is therefore NOT a fault detector; the verdicts below use D1 (later semaphores
   incl. the final tail after 1.5 s) + D2 (notifier, read at once and +250 ms) + D3 (journal Xid for the probe's pid) together.
 * Positive controls (3 reps each unless noted) all behaved as pre-registered, so a "no error" below is a real reading:
     c_ok          SO(1,compute) + compute report-semaphore on sub 1: engine semaphore 0xc0de0001 lands, no fault          3/3
     c_badclass    SO(2,0xdead): Xid 13 pid, notifier 13, no later semaphore                                                   3/3
     c_badsw       A bound on 6, then software method 0x300 (outside the 0x5080 table): Xid 32 (intr 00800000), notifier 32   3/3
   Oracle self-test r0 (3/3): register H1 and H2 on A, send 0x200=H1: REMOVE_API(H1) -> 0xffff (entry gone = executed),
   REMOVE_API(H2) -> 0x0 (still present). The registration control (0x50800101, DMA_INVALIDATE_TLB, DELETE_IMPLICIT) was accepted from
   this root process (status 0) and executes. "executed_by=X" below = REMOVE_API fails only on object X.
 * Software object numbering (MEASURED): GET_CLASS_ENGINEID (0x906f0101) of the first 0x5080 child = classEngineID 0x1 (engineID 0x22);
   the second = 0x2, also when the first was FREED before the second was allocated (s2b): the per-channel counter is never rolled back.

4. VERDICTS (plain)
   S1  : ACCEPTED. A second identical SET_OBJECT on a software subchannel is accepted by hardware/RM/GSP, no error (3/3), and a deferred
         trigger sent after it reaches the same object (3/3). The hardware allows a RE-SEND; the question whether the driver does it stays
         with the app-matrix counters.
   S2  : ACCEPTED (rebind to a LATER-allocated object on the same software subchannel, after the channel executed work). RM status of the
         later alloc: NV_OK (0x0) 3/3; the later object takes the next classID (2). The rebind is EFFECTIVE: a 0x200 trigger on that subchannel
         is executed by the new object (B) and not by the old one (A) 3/3. => "a rebind is impossible by construction" is FALSE at the
         RM/hardware layer; the kayfabe relay's assumption "the 5080 object cannot be allocated after the first publication" is also
         FALSE for the host RM (the alloc succeeds after the channel ran work, also after freeing the first object).
   S2b : ACCEPTED (free A, alloc B, bind B; id 2, not reused), effective, 3/3.
   S2c : ACCEPTED (B on a different software subchannel 5 or 7 while A stays on 6); each subchannel's 0x200 reaches its own object, 3/3.
   S2d : ACCEPTED (B allocated before the first submission, bound later), effective, 3/3.
   S2e : ACCEPTED (acceptance only): the same object bound on a second software subchannel (5 or 7) raises no fault, 4/4 each. Whether a
         0x200 on the SECOND subchannel is executed by A is NOT MEASURED (harness bug found afterwards, fixed in source, not run). INFERRED
         (not evidence): yes, because S2c shows each software subchannel dispatches to the object bound on it. So a Pointer-mode relay
         that has seen one binding cannot assume a trigger arrives only on that subchannel.
   S3  : REJECTED by hardware/GSP (1 rep per subchannel 5/6/7 and 3D on 6): SET_OBJECT of a compute/3D class on a software subchannel
         kills the channel (Xid 32, notifier 32), no engine work. A software subchannel accepts only software-object ids.
   Not measured (the owner pause stopped the queue): S3 reps 2-3, SET_OBJECT of a stale id (A freed, then SO(6,A)) and of a nonexistent id
         (SO(6,99)), the S2e trigger-reach, S2e-hw / hwsub repetitions. See RESUME.txt.
