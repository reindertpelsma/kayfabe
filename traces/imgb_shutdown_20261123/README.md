# H4: why a guest crash looks like "the guest powered itself off"
- MEASURED (source): `propimage.py` puts `hv-crash` in the image's CPU flags (`hv_flags`), and `build_argv` sets no `-action`. In QEMU 10.2.4 (the version in `scripts/bench/qemu.pin`), `system/runstate-action.c:18` sets `PanicAction panic_action = PANIC_ACTION_SHUTDOWN`. In `system/runstate.c:635-639` a guest panic under that action becomes `qemu_system_shutdown_request(SHUTDOWN_CAUSE_GUEST_PANIC)`. Only `exit-failure` changes the exit status (`runstate.c:859`). The only text, "Guest crashed" and the Hyper-V crash parameters, goes to `qemu_log_mask(LOG_GUEST_ERROR, ...)` (`runstate.c:621`), which prints nothing without `-d guest_errors`. A Windows bugcheck reported through the Hyper-V crash MSRs therefore ends QEMU with status 0 and a normal device teardown (the broker detaches), and Windows never reboots. That matches the g1 description.
- MEASURED precedent, other run: Windows on kf3 does report bugchecks this way. `traces/die_coverage_20261104/blackwell/README.md` records `GUEST_PANICKED` (Hyper-V crash MSRs) with arg1 `0x113` (win_vm.sh records QMP events; propimage_check.py did not).
- MEASURED in this image's own System log: the boot of 2026-11-21 20:51:27Z (pc add-on session) ended without any 1074 or 6006. The next boot logged Kernel-Power 41 (BugcheckCode 0) and EventLog 6008 ("unexpected shutdown" at 21:42:34). Per the pc RCA note of that night, QEMU exited with status 0 after a LiveKernelEvent 141 storm and a WATCHDOG dump. A Windows shutdown, whether a process asks for it or the ACPI power button starts it, logs 1074 or 6006. 41 plus 6008 with neither is a crash or a power cut. The same image also holds one earlier 41 plus 6008 (2026-11-15 19:43, cause not recorded). The image holds no Minidump, as expected when the VM ends during the bugcheck. TDR settings: `TdrLevel=3` (recover), `TdrDelay=8`, so repeated timeouts can escalate to a TDR bugcheck (0x116/0x117). That escalation is INFERRED; its limits are Windows defaults.
- g1 (2026-11-22, from the run's README): `nvlddmkm` event 153 bursts every 4 to 5 minutes, Defender and System CPU load, no host Xid, a clean teardown. INFERRED: g1 ended in a guest bugcheck after GPU timeouts (a TDR escalation), and QEMU's default panic action turned it into a status-0 exit. It was not an evaluation timer: this image has none. The bugcheck code of g1 is unknown because the overlay and the g1 log were not kept.

# The fix (this PR, harness only; the sealed image is not touched)
`scripts/bench/windows/propimage_check.py`:
1. The QEMU argv gets a second QMP socket, `<work>/run/qmp-ev.sock`. A recorder thread appends the lifecycle events SHUTDOWN, GUEST_PANICKED, GUEST_CRASHLOADED, RESET, POWERDOWN and STOP to `<out>/qmp_events.jsonl`. It keeps at most 200 events, because the guest can raise events at will.
2. `hold_for_release` returns `qemu-exited` as soon as QEMU is gone. Before this change it kept waiting up to 3 h. The run then ends.
3. When QEMU exited before the harness stopped it, the run gets a `qemu-exit` FAIL row with the cause: `guest bugcheck: GUEST_PANICKED type=hyper-v args=0x116 ...` (arg1 is the bugcheck code), or the SHUTDOWN reason (`guest-shutdown`, `host-signal`, ...), or "no event recorded". The harness then skips the guest clock read and `Stop-Computer`, which would only time out on a dead guest.
QEMU's panic behaviour is unchanged on purpose, so a crash still ends the boot and is now named. Tests (`scripts/ci/test_propimage_check.py`, 8 new): on the tree before the fix (`KF_PROPIMAGE_CHECK_UNDER_TEST` pointed at it), 6 error and 2 fail; in the pipeline test, the pre-fix harness ignores the dead QEMU, is released and runs the app. All 8 pass after the fix. `test_propimage_check`, `test_gpu_diag`, `test_propimage_apps*`, `test_propimage_images` and `test_clocknet_assert` pass, and so do the mutant suites that patch the harness.
