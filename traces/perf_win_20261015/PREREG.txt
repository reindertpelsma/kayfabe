PREREG, Windows 11 GPU benchmarks, kayfabe vs VFIO native. Written 2026-10-15 ~17:50 CEST, BEFORE any run of mine.
(Read first, not run: the task file, the VFIO harnesses, the launcher chain (launch3.sh -> windows_broker_claude_oglw.sh), the Blender bench scripts and the
earlier Blender results (kayfabe, 5.3-5.9 s OptiX 128 spp, 7.6 s CUDA, 148 s CPU), the appmatrix manifest/commands, harvest.sh. The other agent still holds the VM.)

Configurations (same overlay base win11-full-b/windows11.qcow2, own qcow2 overlay + own OVMF_VARS copy per configuration; same -smp 8, 16384 MB, same -cpu flags
incl. hv_*, same SMBIOS/UUID/MAC, same net, same tools+virtio CDs, kfapps.iso as a third CD):
  K  = kayfabe production build kf3 666ea966 + its broker, NO KF3_* measurement flags, display=on (virtual head, broker window).
  K+ = same with KF3_PROF=1 (and in a separate run KF3_USER_RING_STAGES=1) - ONLY for the "where does the time go" repeat of a benchmark with gap > 10 %.
  V  = vfio-pci of the 4070 (01:00.0 + 01:00.1), stock KVM irqfd/ioeventfd (NOT the reference harness's x-no-kvm-* / x-gsp-observer / trace flags, which add
       overhead and would make V slower than a real native guest), std VGA as the second adapter (the host monitor is on the iGPU), same CPU/RAM.
Rules: 1 warm-up run discarded + 3 timed reps per benchmark and configuration; report median and (max-min)/median spread. Gap = K/V (time) or V/K (rate), so >1 = kayfabe slower.
A gap counts as REAL only if it exceeds 10 % AND 2x the larger of the two spreads. Otherwise it is "within noise".
Guest load (Processor % total) noted before each run; a run with > 10 % background load is repeated once.

Benchmark order: (1) Blender Cycles OptiX and CUDA, 1080p, 128 spp, the scene of /data/claude-blender (sub 9, 3 objs, 8 tex 4096) ; render_s from its own result.json.
(2) GravityMark 1.89 d3d12/vk/d3d11/gl, 1920x1080, DEFAULT asteroid count, -benchmark 1 -close 1 -times. (3) vkpeak / clpeak (+ FurMark if time). (4) cup8bench
(many small kernels). (5) Heaven / Minecraft only if all above are done. No PresentMon.

HYPOTHESES (each with its falsifier; "measured" = a number from a run, "inferred" = reasoning)

H7  none: kayfabe is within noise of native on the GPU-bound compute benchmarks (Blender OptiX/CUDA, vkpeak/clpeak throughput).
    Falsifier: any of Blender OptiX, Blender CUDA, vkpeak fp32 or clpeak global bandwidth has a REAL gap (>10 % and > 2x spread) on K vs V.
    Expectation stated beforehand (not evidence): the earlier agent's 5.3-5.9 s OptiX was run on kayfabe only; I have no native number, so I do not know whether it is close. I expect
    compute to be near native (device compute does not trap) and the gaps, if any, to show in many-small-submission and presentation paths.

H3  GPU power state / clocks are lower under kayfabe for the same work (the GPU is not busy enough or is boosted less).
    Measured by host nvidia-smi dmon (K only; the host owns the GPU) AND guest nvidia-smi (both; note the guest reports util [N/A] under kayfabe).
    Falsifier: during the timed phase of the largest-gap benchmark the median SM clock and pstate under K are within 5 % / equal to V's guest-side reading, AND
    GPU util under K is >= 95 % of the run (host dmon sm%), i.e. the GPU is saturated at full clock: then the gap is not power state.
    If K shows util well below V's while runtime is longer: latency-bound (H1/H2/H4), not H3. If equal util/clock and longer time: the GPU work itself is slower (inferred: translation of
    work or memory placement H6).

H1  trap cost per BAR0 write / doorbell is a material share of wall time.
    Counts from the PROF census (bar0_handler count, handler time, max, p99) in the K+ repeat. Falsifier: cumulative trapped-write time < 2 % of the benchmark wall AND the
    worst single trap < 1 ms, in the window of the benchmark. Then H1 is refuted as the main cost (it may still dominate cup8bench-style tiny-kernel loops; judged on that test separately:
    falsifier there = cup8bench per-launch time K within 10 % of V).

H2  completion / interrupt delivery latency (MSI path, user-ring-loop wake, 50 ms backstop) inflates short synchronous work.
    Falsifier: USER_RING_LOOP SUMMARY shows backstop-firing count ~0 (< 1 % of wakes) and drainer wake latency p99 < 1 ms during the run, AND cup8bench sync/launch-to-completion
    latency on K is within 10 % of V. Blender (long kernels) is not sensitive to H2; do not use Blender for H2.

H4  the display present/copy path (broker window, flip/vsync) costs GPU time or caps fps.
    Falsifier: GravityMark fps at 1080p on K (display=on) is within 10 % of V AND the K host dmon shows no display-copy engine activity; or: run the same GravityMark on K with the window minimized /
    display off and the fps does not rise > 10 %. CONFOUND recorded with every graphics number: V has no display on the 4070 (headless secondary adapter + std VGA head), so every V frame is
    presented through a cross-adapter copy that K does not do. A K slower than V therefore cannot be explained by "presentation" alone, a K faster than V proves nothing about kayfabe.

H5  host CPU contention / scheduling (governor, SMT sibling, qemu thread placement).
    Falsifier: perf stat/sched during the benchmark shows no qemu/kayfabe thread (vCPU, drainer, broker) with > 90 % of a core while the vCPU threads wait, and the guest-visible CPU benchmark
    (Blender CPU is too slow; use the guest's own `Processor %`/a short CPU-bound loop) is within 10 % K vs V; max sched delay (perf sched latency) of kayfabe threads < 5 ms.

H6  PCIe BAR1 / IOMMU (DMA-FQ vs identity) mapping limits H2D/D2H bandwidth.
    Falsifier: clpeak transfer bandwidth (enqueueWriteBuffer / ReadBuffer) K within 10 % of V.

Where-does-the-time-go outputs required for each benchmark with a real gap (K+ repeat, one run each with KF3_PROF=1; a separate one with KF3_USER_RING_STAGES=1):
worst single trap (max), cumulative trap time % of wall, doorbell delay (from the user-ring-stages counters if present), host CPU by thread (perf stat per thread), off-CPU stacks
(OFFCPU=1) vs on-CPU, GPU util/clock/pstate/power (host dmon). Measured and inferred kept apart in the doc.

Failure policy: a crash/TDR is a result (guest events + host Xid + ring REFUSED lines recorded), at most one retry, then move on.
Valid-run condition: guest GPU healthy at start (no nvlddmkm 153/4101 in the last 2 minutes), no other VM, host lock held, VFIO side restored to nvidia at the end.
