# Apply the existing v3 context and ZBC policies to Windows

**STATUS: RESEARCH, 2026-10-04. Source-policy comparison, not a successful Windows replay.**

The implementation inspected is `v3-windows` at
`c50fad9ac485f53d45d4ea77a21cb7206267c65a`. The existing policies already solve
the hardware-context problem in the intended architecture. A missing native
command handler is not automatically a missing GPU implementation.

## Established decisions

- [Owner ruling B](../../../../../docs/OWNER_RULINGS.md): GPU_PROMOTE_CTX is a
  stub because the host twin owns the real context. The guest's golden buffer
  is not the context loaded by physical hardware.
- [Headless graphics §2 and §6.2](../../../../../docs/design/V3_HEADLESS_GRAPHICS.md)
  implements that ruling for graphics, including promotion before engine-object
  allocation: the twin can be pending, and the following host engine allocation
  creates its real context. Guest context bytes are not copied or executed.
- [ZBC policy](../../../../../crates/kf-rm/src/zbc.rs) maintains a per-VM table.
  Host mappings use uncompressed kinds, so guest ZBC indices are not used for
  physical compressed surfaces. The host supplies table-size ranges; guest
  SET/GET operations do not mutate the GPU-global host table. Real compression
  would require reconsidering that policy. This is already implemented for Linux.
- [Non-GSP research](../../../../../docs/design/V3_NON_GSP_CTX.md) separately
  discusses emulating the generation protocol without GSP. It does not make
  physical golden-image generation a requirement for the Windows GSP path.

The local nvkvm-pv tree also records a historical ZBC-family gap in
`docs/audit/release-blockers-2026-09-02.md` (checkout `368d2db`). That older
project's allowlist problem is not evidence of a missing v3 local ZBC table.

## What the Windows bytes show

[context-shapes.json](context-shapes.json) is regenerated by
`tools/windows-gsp-trace/audit/context_shapes.py`. It uses public OGKM 580.65.06
`ctrl2080gpu.h`/`ctrl5080.h` field offsets, the retained capture hash, and exact
length checks. Queue sequence and export line identify every request.

| Observed path | Count | Shape | Consequence for the existing implementation |
|---|---:|---|---|
| Direct `GPU_PROMOTE_CTX` | 11 | GR engine 1; 560 bytes; entry arrays of 3, 4 or 8; legacy handle/address/size fields zero | Uses the existing descriptor form. A real matching twin and correct resource lifetime still matter. No golden-image generation is implied. |
| Deferred `GPU_INITIALIZE_CTX` | 4 | Inside 584-byte `50800101`; GR engine 1; wrapper flags zero; context size 901888 in this capture | Needs resource/protocol handling consistent with the twin policy. The observed size is evidence, not a portable sizing constant. |
| Deferred `GPU_PROMOTE_CTX` | 4 | Same wrapper; GR engine 1; entryCount zero; nonzero VA and size; hVirtMemory zero | **Concrete uncovered form:** the current descriptor decoder rejects legacy VA/size, and its fallback accepts only video engines. Even extracting the nested payload would not pass that decoder. |
| `GF100_ZBC_CLEAR` allocations | 6 requests / 6 replies | Class 9096, no parameters | An existing graph node/local table, not a new GPU engine to emulate. No `9096xxxx` control occurs in the retained window. |

The direct descriptor entries use published MAIN/PATCH/bundle/pagepool/
attribute/RTV/FECS-event/unrestricted-access-map IDs. Their presence does not
imply Kayfabe must fill those guest buffers with NVIDIA's physical images.

**Working conclusion:** reuse the established twin-satisfied policy for Windows
GSP. These observations do not contradict it. They identify a legacy GR form
and deferred registration/lifetime handling, not a new golden-buffer algorithm.
The capture contains no CPU memory-read trace, and its channel allocation
bodies are missing, so it cannot prove the proprietary Windows CPU driver never
reads a context buffer or identify each target as a kernel/user channel. Test
those assumptions in the Windows boot/workload loop; do not turn them into a
prerequisite to implementing source-understood control behavior.

OGKM's `src/nvidia/src/kernel/gpu/deferred_api.c` supplies the registration,
handle validation, saved caller privilege, removal and TLB-wait bookkeeping;
`ctrl5080.h` describes a later software-method trigger. The observed wrapper
flags are zero, but the wrapper reply only acknowledges registration. Reuse
that source contract where applicable. It does not authorize forwarding nested
guest pointers or returning a fabricated GPU completion.

**Passthrough UMD channel methods remain hardware-executed.** This catalogue
does not request an interpreter for their command streams. Deferred resource
integration must respect the actual channel route; the missing allocation
bodies prevent deciding that route from this capture alone.

## Host-query inventory is not a forwarding security policy

At the same implementation pin, `kf-abi/src/hostabi.rs::HOST_CONTROLS` has **58
IDs**: 52 public-layout entries and six opaque GSS IDs. Four GSS IDs are queried
at VM creation using five fixed request forms; two are NVENC session
acquire/release verbs with explicit lifetime accounting. These are not 58
generic guest RPC forwarding routes.

In particular, `HostAbi::control_carry` accepts unlisted IDs on its encoded
580.x interval. This is ABI adaptation for authored internal callers, **not a
strict deny-by-default security allowlist**. Any new guest-facing forwarding
path needs its own explicit audited command and parameter policy. The native
[ordinary-user proof](../../2026-10-04-ga106-unprivileged-575.51.03/README.md)
establishes candidate host verbs, not authorization to pass guest bytes through.
