## Findings that change where to resume

**Apps:** the latest published measurement is **60/65 apps**, all six stream
probes passing, and 100/100 sequential processes in one boot at code revision
`4c48ca0c`. Persistence mode does not change that result. Four remaining app
failures involve managed-memory demand paging; `cdpSimpleQuicksort` is the fifth.
See `design/V3_APP_MATRIX.md`'s R3 correction and its evidence.

**CDP (CUDA dynamic parallelism):** the uncommitted bisect finished after the
last GitHub update. `cdpSimpleQuicksort` passes at `0667b784` but times out at
its next commit `56032c46` (the MC_SERVICE_INTERRUPTS completion fix). This is
not evidence that reverting that fix is correct: the dedicated probe on the
older revision reports successful synchronization with `child_ran=0`, zero
output and `RESULT ... BAD`. The same probe on bare metal executes the child
and returns the expected data. At `56032c46`, the parent runs but the child does
not, and synchronization reaches the watchdog. Start from these traces; find
why the child work never executes, and keep real completion semantics.
[Last bisect/probe log](../traces/recovery_20260928/53004208-cdp4.log.txt),
[bare-metal control](../traces/recovery_20260928/53004208-cdp-host.log.txt).
Runs after a poisoned CUDA context report error 999; use fresh boots for controls.
The app harness also printed a missing `guest_isolated.res` warning on single-app
runs, so use per-app/probe verdicts, not just the runner's exit code.

**Turing:** substantially further along than the published handoff. At original
head `d4ff6be8` (GTX 1660 SUPER/TU116, host 580.159.04), recovered completed logs
record gates **9/9**, bare-metal raw suite **30/30**, thin guest **30/30**, and
guest CUDA ladder **4/4**. The missing commits fix family-specific GR/memsys
assumptions, preserve per-query GR refusals, emit the Turing V2 FWSEC descriptor,
and retarget the ladder PTX below SM 8.6. The earlier FWSEC-stop note predates
these passes. A full crate-test run on this final combined source is not in the
recovered record, so this is not yet a promotion-ready merge-bar claim.
[Thin suite](../traces/recovery_20260928/53080587-thin-suite.log.txt),
[CUDA ladder](../traces/recovery_20260928/53080587-cuda-ladder.log.txt).

**Driver matrix:** at `826ef957` on the second RTX 3060, guest 570.148.08 still
fails the thin failure-point probe and cup2; guest 575.57.08 passes cup2.
The scan found no NULL-pointer/`intrInit` signature in that 570 thin run. The
first logged refusal is not by itself a root cause. Both runs completed and
were recovered. The new sweep harness exists, but a complete host × guest ×
architecture campaign has not run. Its own estimate is about 12 hours per
architecture; do a representative smoke first.
[Driver check](../traces/recovery_20260928/53091825-driver-check.log.txt).

**Display:** M0 is on master, default off, and reaches KernelDisplay but remains
displayless. Step 1 on the Claude branch wires 36 display controls and has
unit-test evidence, but has not been exercised in a guest. It does not yet
provide scanout or a desktop. `design/V3_DISPLAY.md` documents the next hardware

## Ordered resumption plan

1. Review and integrate the recovered Turing line with `826ef957` on a fresh
   candidate branch. Resolve by meaning; leave the 535/545 allowlist out.
   Run all `kf-*` crate tests, gates, exact-revision kf3 build and thin suite;
   exercise both retained Ampere and Turing boxes, then the CUDA ladder.
   Promote only the verified candidate, not a convenient older test revision.
2. Diagnose CDP child execution using the recovered minimal CUDA probe and
   fresh-boot host/guest controls. Require correct child output and completion,
   then retest quicksort and the app matrix. Do not restore the earlier false
   completion to regain a PASS label.
3. Run display step 1 with `display=on`; inspect the NVKMS refusal ledger.
   Continue BAR0 routing/channel execution, then GPU scanout and pixel-exact
   grading, then the Mint desktop. Retain default-off regression coverage.
4. Resume the 570 first-channel investigation, then smoke the sweep harness
   before the full driver × GPU-family matrix. Reuse one box serially per
   architecture; record exact source and loaded-driver revisions for every cell.
5. Continue the UVM E6″ experiment and doorbell-performance track once their
   choices below are settled. Windows guest support remains later in the roadmap.

Steps 1–4 have useful work available without another owner decision. This turn
was recovery and planning; it did not start these implementation/test campaigns.

## Questions still open to the owner

1. **535/545 policy:** approve or reject `a50265f8`'s capability surface after
   review? The reviewed table is in that commit's `V3_DRIVER_MATRIX.md` change.
   Existing 550+ support and the immediate plan do not depend on approving it.
2. **UVM:** continue the separate N4 host-module route, or maintain a patch to
   NVIDIA UVM? The documented preference is N4. Recommend the bounded E6″ proof
   first: actual compute fault delivery, correct replay, scoped cancellation,
   negative control and median/p99 latency, without promoting a product route
   before those results. Phase 0 is already done; the final brief remains open.
3. **Doorbells:** build the approved optional guest helper, use an optional
   paravirtual guest-driver interface, or first measure/cheapen host exits on
   non-nested hardware? Recommend establishing the non-nested baseline before
   making nested-box speed the product's performance target.
4. **Cloud execd credentials:** the earlier cloud session left a question about
   box-scoped HMAC keys and sharing them across boxes/sessions. This recovery
   used direct SSH with agent forwarding disabled and sent no GitHub/Vast
   credentials. Direct SSH needs no decision here. If execd remains necessary
   for future cloud chats, recommend a separate disposable key per box, never
   a shared account credential; that policy still needs the owner's answer.

is private under `/data/recovery-2026-09-28/`. No existing projects, caches or
VMs were deleted to make space. The source patch was checked for allowed paths,
