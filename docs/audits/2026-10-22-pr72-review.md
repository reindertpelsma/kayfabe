**STATUS: LIVE, 2026-10-22.** Independent review of `origin/codex/install-flags-20261022` at
`53ae58d9c10beb09153ca89ef4b9377f273188f2` (verified with `git ls-remote origin`; base `e64b8e5f6`).
GPU-free, read-only on product code, no hardware. Evidence tags: CODE READ, MEASURED (ran or

`broker_gap_io.sh`, and the `command.json` of runs 3439 and 3440 (rev `89fc8a222`), all read-only.

## Verdict

NOT merge-ready. Two blockers (B1 red claims gate, B2 the `KF3_DISPLAY_SDR_COLOR` flip is not
shown identical to production for non-Windows-4070 paths and lands on open gap G05), plus six
important findings. The `LUT_MIRROR` / `ILUT_OFFSET_256` flips, the dead-flag removals and the
diagnostic de-defaulting are sound.

## What the production runs actually set (MEASURED)

`command.json` of 3439 and 3440 carries 15 channel/probe flags, `KF3_DISPLAY_SDR_COLOR=1`,
`KF3_DISPLAY_CAPS_PROBE=1`, `KF3_DISPLAY_LUT_MIRROR=1`, `KF3_DISPLAY_ILUT_OFFSET_256=1`, plus
`KF3_LIFECYCLE_COUNT=1`, `KF3_LIFECYCLE_PERIOD_S=5`, `KF3_TSG_MIRROR=0`, `KF3_DIAG_PROGRESS=1000`
(3439 also `KF3_PROF=1`). No `KF3_RPC_TRACE`, `BAR0_TRACE`, `MAPLOG`, `DISPLAY_METHOD_TRACE`.
Guest-visible: `guest-driver=580.65.06`, explicit `gpu-uuid`, `bar1-size=8 GiB`, `fb-mb=8192`,
`pc` machine, Hyper-V enlightenments.

## (a) Default flips

| Flag | New default | Production | Same on all paths? | Off-switch |
|---|---|---|---|---|
| `KF3_DISPLAY_LUT_MIRROR` | on (`!= "0"`) | 1 | Yes in practice (see A1) | `=0` |
| `KF3_DISPLAY_ILUT_OFFSET_256` | on | 1 | Yes in practice (see A1) | `=0` |
| `KF3_DISPLAY_SDR_COLOR` | on | 1 **together with CAPS_PROBE=1** | **No** (B2) | `=0` |

A1 (sound, CODE READ). MIRROR and the 256-byte ILUT unit are only reached when SDR_COLOR is on
(`display.rs:2169-2172`). `color.rs:54-70` records that NVKMS and nouveau never set MIRROR and that
NVKMS writes ILUT offset 0, so neither flip changes what the Linux drivers program. The Windows
value `0x21` is measured (runs 98/99). Keep these two flips.

### Findings

**B2 (blocking, CODE READ + MEASURED): `KF3_DISPLAY_SDR_COLOR` default-on is not production
behaviour for any path except Windows/AD104 with CAPS_PROBE, and it changes every Linux display guest.**
- Production runs SDR_COLOR **with** `KF3_DISPLAY_CAPS_PROBE=1`, which discards the authored
  `sdr_page` and publishes the measured AD104 page (`display.rs:2179-2205`; the feature-gap table
  H29 says the same: "its page is discarded under CAPS_PROBE"). The new default publishes the
  authored `sdr_page` to every `display=on` guest. That combination (authored SDR page plus
  MIRROR plus OFFSET_256, no CAPS_PROBE) has no hardware run in the repo: runs 98/99 (the MIRROR/OFFSET evidence) set `KF3_DISPLAY_CAPS_PROBE=1`
  (`traces/display_reply_diff_20261008/run9[89]-command.json`), and run 97 predates the fix. The PR text admits "hardware compatibility
  of new default combinations remains unverified".
- Linux: every Linux display lane (`scripts/bench/display/interactive.sh:131`,
  `run_fast_guest.sh`, `boot_nvkvm.sh`) sets no colour flag, so they ran with the plain `caps::page`.
  The only Linux SDR evidence is product `2aa8b92d` (old), borrowed AD104, Weston and Sway
  (`STATUS_AND_HANDOFF.md:1871-1880`). The flip now advertises ILUT/OLUT/TMO capability to every
  Linux desktop on every die, and the strict TMO Linux test is recorded as FAIL in the same
  place. The owner's standing rule (memory: retest the Linux guest with the broker after any
  display change) has not been honoured: no `broker_lane.sh` / `interactive.sh` run.
- G05 (`V3_FEATURE_GAPS.md:64`, still open): a colour program the decoder refuses halts every guest
  display channel for the VM's life. Before the flip a Linux guest could not hit it because no LUT
  caps were advertised; after it, any compositor gamma/CTM/HDR program outside the SDR subset can.
- Other dies on Windows: only AD104 was ever run with the colour path. INFERRED extra GPU work per
  frame for every display guest (colour kernels), not measured.
- Fix: land MIRROR and OFFSET_256 default-on now; keep SDR_COLOR opt-in until either G05/H01 is
  closed or hardware evidence exists on the reduced configuration: `fast_suite.sh` 30/30,
  `broker_lane.sh` and `interactive.sh` (Linux), the Windows AD104 reduced launch without
  `SDR_COLOR`, and at least one non-AD104 die. If it is kept on, say in the doc that production
  also needs CAPS_PROBE and that the authored-page default is new.

**B1 (blocking, MEASURED): CI is red on the claims gate.** `python3 scripts/ci/debt.py claims`
reproduces locally: `existing-debt=3758 new=12`. Sites: 3 in
`docs/design/V3_FLAG_INVENTORY_20261022.md` (the QEMU 10.2.4 `pci.c` paragraph, the "measurement
enable switches default off" paragraph, the "39 properties" paragraph) and 9 in
`traces/install_flags_20261018/README.md` (broker `make check`, the mutant accounting paragraphs,
clippy, the credential scan, the 16 argument cases, the patched build, the removed-assignment
mutants). The GitHub run (39698250699, same head) shows that as its only `##[error]`; build, test,
clippy and fmt steps ran before it. Fix: attribute each claim to a file/command per
`scripts/claim_ledger.py` rules (do not `--record` them as debt).

**I-A (important, CODE READ): constructor-probe research arms now fail at realize.**
`display.rs:2174-2178` returns `Err("SDR processing cannot be combined with constructor-only probes")`
and the new default makes SDR_COLOR true, so any of `KF3_DISPLAY_{TMO,TMO_SURFACE,ILUT,OLUT}_CONSTRUCTOR_PROBE=1`
alone is refused. Callers that set only the probe: `scripts/bench/windows/pc_pool_experiment.py:91`,
`host_tools/runners/boundary-tools/pc_boundary_experiment.py:139-143`, and the four READMEs under
`tools/display-*-constructor-probe/`. The PR's own design table says probes "must explicitly select
`KF3_DISPLAY_SDR_COLOR=0`" but touches none of these. This is the situation THE_CONSTRAINTS §42(a)
warns about (an unreachable configuration fails at realize). Fix: derive `sdr_color = sdr_color_on() &&
!constructor_probe` with a loud note, or update the scripts and READMEs; add a test either way.

**I-B (important, CODE READ): the launcher change silently disables a harness.**
`scripts/bench/windows/winpass_cycle.sh:33-34` (`wait_stall`) greps `qemu.log` for `cmd=0x00730108`,
which only exists with `KF3_RPC_TRACE=1`, formerly forced by `windows_broker.sh`. Its default
`WIN_FLAGS` (line 17) does not include it, so after this PR the wait loop runs its full 600 x 0.5 s
and moves on. Fix: add `KF3_RPC_TRACE=1` to that default, and say in the PR which other readers
(`abort_point.py`, `rpc_diff.py`, `wr-run.sh`) now need `WIN_FLAGS`. Minor sibling: `wr-run.sh:67`
counts `EXPERIMENT KF3_DISPLAY_LUT_MIRROR=1` log lines that this PR rewords, so it reports 0.

**I-C (important, CODE READ): stale "default off" text not corrected where it lives** (CLAUDE.md doc
hygiene: supersession is recorded in the superseded text). Still say off/opt-in:
`V3_SDR_COLOR.md:4` (and its "ILUT offsets are bytes" line), `V3_TMO_COLOR.md:5`,
`STATUS_AND_HANDOFF.md:1468,1871`, `V3_FLAG_INVENTORY.md` rows for the three flags,
`v3_constant_inventory.tsv:107`, and the doc comment on `kf_disp::color::Experiments`
(`color.rs:54`, "Default-off experiments"). `Experiments::default()` is still all-off (correctly),
the product default is now on; say so there.

## (c) docs/INSTALL.md

Checked OK: every `kf3-gpu` property used exists in `kf3.c:1937-1993`; the Windows KF3 env list equals
the 3440 flag set minus the colour defaults and the dead/diagnostic extras; `build_kf3.sh` argument
order and the `kf3-bins/<8-char rev>/qemu-system-x86_64` path match (a dirty tree adds `-dirty`);
QEMU 10.2.4 tarball URL returns 200 (MEASURED); QEMU 10.2 guard matches `kf3.c:93`; broker flags
`--socket --backend auto --persist` exist; `memory-backend-memfd,share=on`, `pci-hole64-size`,
`smm=on`, `guest-driver=580.65.06` for Windows 580.88 match production; all relative links resolve;
no README edit; STATUS lines present; no IP addresses, host paths, credentials or the owner's
addresses in the diff (grep of all added lines; the only `.sock` is the user-chosen
`$XDG_RUNTIME_DIR` path).

**I-D (important, CODE READ): Linux template is wrong for most hosts.** `display=on` needs derived
display classes, and `kf_disp::class::for_version` only has `580.159.04` and `580.65.06`
(`class.rs:178-194`; `display.rs:2136-2146` refuses others by name). The text "use the same version
as the host to omit `guest-driver`" and the list of other measured versions (575.57.08, 590, 595,
610) imply the display template works there; on the owner's own 595.91.07 host it refuses at realize.
State that `display=on` currently supports guest driver 580.65.06 / 580.159.04 only and that the
guest must run the same version; headless CUDA is the path for the others.

**I-E (important, CODE READ): "No guest helper or patched kernel is required" is stronger than the
evidence.** `interactive.sh:227-262` records, as `[measured 2026-10-08, run proof-p2]`, that the
measured desktop needs `nvidia-drm.modeset=1 nvidia-drm.fbdev=1`, `nvidia_drm` loaded at boot, and
an `xorg.conf` with `Driver "nvidia"` and the device's `BusID` (without it X picks modesetting and
lightdm loops). The template also uses `-machine pc` with the default 256 MiB BAR1, whereas every
measured Linux lane uses `q35` (`interactive.sh:124`, `run_fast_guest.sh:203`) and 128 MiB or more
via explicit sizes; the `BusID` changes with the machine type. Mark the machine type and the guest
configuration as required-or-unverified.

**I-F (important, CODE READ + INFERRED): the Windows template differs from the production command
beyond the KF3 environment, and the doc only says so for the environment.** Missing relative to
3440: `-cpu` `+invtsc,migratable=off,hv_*` enlightenments, `-rtc base=utc,driftfix=slew`, `-global
kvm-pit.lost_tick_policy=discard`, `-action reboot=reset,panic=none`, virtio `disable-modern=on`,
the disk iothread and `l2-cache-size`, fixed PCI addresses, explicit `gpu-uuid`. Whether any is
required is unknown; list them as unverified deltas. Also: the apt list omits `meson`, `flex`,
`bison`, `python3-pip`, `python3-tomli` that `provision_bench_tree.sh:74` installs (INFERRED
irrelevant for the QEMU 10.2.4 tarball, not tested), there is no rustup install step, and
`git checkout 33f7a1703` pins a commit on this PR branch (it can disappear on a squash merge) and
calls it "audited" although the only checks are the author's own GPU-free ones.

## (d) Tests and mutants

Reviewed CODE READ; CI ran the Rust suite green up to the claims step; I did not re-run it (the
shared cargo lock was held by another job's whole-workspace test and I stopped waiting).

- Rust (`display_defaults_tests.rs`): meaningful, not source pins. They call the real
  `sdr_color_on()` and `color_experiments()` in a child process with controlled env, and decode
  real LUT/offset programs through `kf_disp::color` for Turing and Ada class tables. The
  EXPECTED RED commit, six failing on old defaults, and per-flag mutants are credible.
- **I-G (important, INFERRED from code, not run):** the wiring at `display.rs:2169`
  (`let sdr_color = sdr_color_on();`) is not covered. Replacing that line with the old inline
  `== Ok("1")` leaves all eight new tests green because they never go through `DisplayPlane::build`.
  No test covers the constructor-probe plus default error path (I-A) or the default-plus-CAPS_PROBE
  combination. Fix: extract the `(sdr_color, constructor_probe, caps)` selection into a pure
  function used by `build` and test it.
- Python launcher tests: they execute the real `FLAGS=` and `ENV=(` lines under bash, so the
  mutants are real; but they rely on those being single lines and are not wired into CI
  (`ci.yml:279` discovers only `scripts/ci`), so they will rot. Minor: add them to the discover
  path or a documented command.
