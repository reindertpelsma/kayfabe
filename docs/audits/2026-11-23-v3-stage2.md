## 3. Findings

### S2-01 · blocker · USER host channels refusing physical-mode work: evidence from one family only (S1-20)

- **Threat.** Guest userspace's GPU work runs unparsed on a passthrough twin. If a copy-engine method with a
  physical-aperture operand (`LAUNCH_DMA` `SRC/DST_TYPE=PHYSICAL`) were honoured on that channel, the guest
  would address host VRAM or host RAM by physical address: a host breakout and a cross-tenant read/write.
- **Code paths.**
  - Every production birth requests `DENY_PHYSICAL_MODE_CE` (`crates/kf-host/src/channel.rs:575-577`,
    `:609-633`); the belt is a type, `PhysicalCeBelt` (`:584-597`), and only the oracle may name `Off`
    (`crates/kf-host/tests/channel_birth_bound.rs:428`).
  - RM's reply is read and a privileged channel is freed and refused (`crates/kf-host/src/birth.rs:146-193`,
    `PRIVILEGED_CHANNEL_REFUSED`).
  - Enforcement of the DENY bit and of the USER privilege level is in closed GSP firmware and hardware
    (`ogkm-580: src/common/sdk/nvidia/inc/alloc/alloc_channel.h:158-170`, no open-RM consumer; stage 1).
- **Who can reach it.** Guest userspace (its own pushbuffers), guest root (Translated work is rewritten, so
  only an operand that escapes the rewriter). Not a supply-chain path.
- **Status of the evidence.**
  - MEASURED (2026-11-23, `4f376f3db`, GPU-free): `cargo test -p kf-host --lib birth` 11 passed;
    `cargo test -p kf-host --test channel_birth_bound` 6 passed. They prove kayfabe *asks* for USER and the
    belt and refuses a privileged reply; they say nothing about what the hardware does.
  - READ, not part of stage 1's record: `traces/phys_operand_oracle_20261008/README.md` (RTX 4070, AD104, host
    driver 595.91.07, source `a5e0ebf1`, 2026-10-08). A native USER channel from `kf-harness kf-phys-oracle`:
    physical source (LOCAL_FB, COHERENT_SYSMEM) and physical destination were refused with Xid 32 on two CE
    instances, with and without the belt; the virtual control delivered. The 3D, compute and video classes have
    no physical-operand method (a header reading, not a run).
  - Not measured anywhere in git: Turing, Ampere, Hopper, Blackwell; the same test from inside a guest, through
    a twin; privileged host methods other than CE physical mode; the root-VMM arm (`CAP_SYS_ADMIN` cleared
    around births only; S1-22 still open for the other kf-host RM calls); recovery of the shared engine after
    the RC (the oracle's README lists it as unresolved).
- **Severity.** Blocker (stage 1, unchanged): every "other tenants" and "host memory" row of the model rests on
  it.
- **Fix or residual.** No code defect found. To close it (READ, stage 1's check): T-PHYS-CE on every family of
  the release, both arms, recording euid/CapEff. My suggestion for the cheapest route: run the existing
  `kf-phys-oracle` arms (`virt`, `phys_fb`, `phys_sysmem`, `phys_dst_fb`, deny 0/1) natively on one box per
  family of the first release; that is a host-process USER channel, the same object a twin is. The guest-twin
  form needs a guest-side probe that is not written. **Owner decision:** whether the native per-family oracle
  is enough to close the blocker, or the guest-twin form is required.
- **Regression test.** The belt and the reply check are held by the two test sets above; the hardware property
  cannot be tested GPU-free.

### S2-02 · blocker (until its box step runs) · No identity window in any twin (S1-21)

> **Update 2026-11-25 (release candidate 1, TENTATIVE; the owner has not ruled).** The release candidate implements
> option C of decision A3: every `KF3_NEGCTL_*` read (including `KF3_NEGCTL_TWIN_WINDOW`) is compiled in only by the
> cargo feature `negctl` of `kf-qemu` (forwarded to `kf-host`), which the release kit does not set, so a release
> binary built by the kit has no such switch. Bench builds (`scripts/bench/build_kf3.sh`) keep them. The residual
> paragraph below, which says the switch ships, describes the tree before this change. This is a pending default,
> not a closed finding: the owner may instead ship the switches (feature on in the kit) or compile out only
> `KF3_NEGCTL_TWIN_WINDOW`, and the finding stays open until that ruling and the box step named above.

- **Threat.** Store and guest-RAM windows in a guest user process's twin let unprivileged guest GPU work read
  and write the guest kernel's memory, including its GPU page tables (in-guest isolation A.9). It stays inside
  the VM.
- **Code paths.** A twin and a prewarmed spare map a window only when `negctl` is set
  (`crates/kf-qemu/src/mem.rs:3784-3803` `tmode_twin`, `:3805-3824` `tmode_spare`); `negctl` is
  `negctl_twin_window()` (`:3763-3772`), which reads the environment variable `KF3_NEGCTL_TWIN_WINDOW`. The
  only window-holding space is the per-VM T-space (OWNER_RULINGS §AB; `KF3_TSPACE` was hardwired on
  2026-10-10, `crates/kf-qemu/src/device.rs:850`).
- **Who can reach it.** Guest userspace, if a window were present. The environment switch is reachable only by
  whoever starts QEMU (the host operator), not by a guest.
- **Evidence.**
  - MEASURED (2026-11-23, `4f376f3db`, GPU-free): `cargo test -p kf-qemu --lib no_tmode_twin_path_maps_a_window
    owner_invariant_check_catches_a_planted_window`, 2 passed (create, prewarm and recycle paths against a host
    that counts window maps; the second test plants a window and must catch it).
  - READ: 110 committed `kf_line_census.txt`-style files under `traces/` contain `windows=none` (MEASURED count,
    grep), e.g. `traces/blackwell_validation4_20261022/arms/off_c/kf_line_census.txt`. They show the mirrors were
    logged without windows, not that user work cannot reach memory.
  - Not measured: T-WINDOW-USER (the probe is not written, `docs/design/V3_P1P2_TSPACE.md:223`), and no app has
    been recorded as an *unprivileged* guest user under the census.
- **Severity.** Blocker until T-WINDOW-USER runs (stage 1). My suggestion: once it passes on one family, minor,
  because the code property is held by GPU-free tests.
- **Residual the owner must accept or remove.** The product binary still carries the switch that re-creates
  S1-21 (`KF3_NEGCTL_TWIN_WINDOW`). It is in the env-read gate's debt list
  (`scripts/ci/env-allowlist-debt.json:38`), so a new switch cannot be added, but this one ships. My suggestion:
  compile it out of the release build (a cargo feature the release kit does not set), keeping the box control
  arm. Not done here: it changes the box control runs, which other branches own.

### S2-03 · major (blocker for a Hopper or Blackwell release) · VER3 stale 4 KiB PTEs under an unmapped big PTE (S1-60)

- **Threat.** On VER3 tables a big PTE with `VALID=0, PCF=NO_VALID_4KB_PAGE` hides the 4 KiB PTEs under it.
  If the walker published those stale small PTEs, a host twin would keep translations to pages the guest
  kernel unmapped and may reassign (in-guest stale translation, model R1.1). Not a host breakout: every leaf is
  still contained.
- **Code paths.** `cuda/walk/kf_walk.cu:463-473` (`kf_big_pte_unmapped`: VER3 now returns true for
  `PCF == KF_VER3_PTE_PCF_NO_VALID_4KB_PAGE`), `:475-494` (the big PTE owns its slot); the CPU harness's VER3
  cases `cuda/walk/kf_cpu_walk.cpp:246-318`, run from `:770`.
- **Who can reach it.** Guest userspace with a stock guest kernel (stock UVM writes the state; stage 1).
- **Evidence.**
  - MEASURED (2026-11-23, `4f376f3db`, GPU-free): `make -C cuda/walk kf_cpu_walk && ./kf_cpu_walk` prints
    `kf_cpu_walk: ok`, including the VER3 cases (unmapped big PTE hides 16 stale leaves; mixed slots; sparse
    big half with PCF 1 and 3; a valid big PTE; the non-vetoing controls).
  - MEASURED falsifier, same run: with line 471 replaced by `return false;` (the pre-#386 VER3 behaviour) in a
    scratch copy, `kf_cpu_walk` fails at `kf_cpu_walk.cpp:255` ("32 leaves, want the 16 of slot 1 only") and
    `:257` (stale leaf `va=600000` published), exit 1.
  - READ: CI job `ptx` (`.github/workflows/ci.yml:2912`, "shipped GPU programs rebuild byte for byte; the walker
    source on a CPU") runs `make -C cuda/walk check-invariants check-cpu` (`:2950`) and rebuilds the committed
    PTX from the `.cu` byte for byte (`:2941`); it was green on `4f376f3db` (`gh run` 45236342768, 2026-11-23,
    MEASURED with `gh run view`). So the shipped PTX carries the fix.
  - Not measured: any VER3 table on a Hopper or Blackwell card (the project has none of the former; no
    VER3-specific box run is cited by #386). Related open item on the same family: PR #505 (GB10X 256 GiB PD2
    page read as a PDE; "needs hardware smoke").
- **Status.** Fixed in source by #386, with a failing-first CPU test held in CI. **Residual:** hardware
  confirmation on a VER3 card before a Hopper or Blackwell release, and #505. Owner decision: whether a
  Blackwell release waits for #505.

#### S2-04a · minor · Bench guests' ssh forward listened on every interface — **fixed in this PR**

- **Threat.** `-netdev user,hostfwd=tcp::2222-:22` binds INADDR_ANY: the guest's sshd (user `ubuntu`,
  key-only; READ: the provisioning scripts run `sudo` over that ssh with no password) is reachable from every network the host is on. On a rented
  box that is whatever the provider exposes; on an owned machine, the LAN.
- **Code paths (before).** `scripts/bench/provision_bench_tree.sh:209`, `scripts/bench/provision_guest_llm.sh:31`,
  `scripts/bench/provision_guest_display.sh:25`, `scripts/bench/provision_guest_gfx.sh:40`,
  `scripts/bench/gfxset/provision.sh:46`, `scripts/apps/provision_guest_apps.sh:16`,
  `scripts/drivermatrix/stage_fat_guest.sh:52`, `scripts/bench/windows/host_tools/misc/root_home/runmint.sh:9`,
  `runmint-diff.sh:9`. Every one connects to `127.0.0.1` (MEASURED, read), so loopback loses nothing.
- **Who can reach it.** A network attacker next to the bench host. Not a guest, not the shipped binary.
- **Fix.** All nine bind `127.0.0.1`. `scripts/ci/test_hostfwd_loopback.py` scans `scripts/`, `tools/`, `ci/`,
  `qemu/` and `crates/` for a forward with an empty, `0.0.0.0` or `*` host address (fixture files under
  `scripts/ci` excepted) and has matcher self-tests. MEASURED (2026-11-23): before the fix it fails with the nine
  sites; after, 4 tests pass. It runs in CI through the `scripts/ci` unittest shards.

#### S2-04b · minor · The kf3 closure gate missed the embedded firmware and display programs and did not pin third-party crates — **fixed in this PR**

- **Threat.** Supply chain and licence: code compiled or run while building the kf3 binary that no gate sees.
  (1) `kf-gop-image`'s build script builds `firmware/kf-gop` (its own workspace and `Cargo.lock`) and the binary
  embeds the result (`crates/kf-gop-image/src/lib.rs:31`); kf-cuda embeds `cuda/display/*.ptx`
  (`crates/kf-cuda/src/display.rs:22`, `:31`, `:42`). `scripts/ci/qemu_license_closure.py` scanned only
  `qemu/hw/misc/kf3` and `cuda/walk` (`EXTRA_DIRS`, line 27 at `4f376f3db`). (2) The closure followed only normal
  edges (line 69), so a crate reached only through a build dependency (code that runs on the build machine) was
  invisible. (3) Any third-party crate with an acceptable licence passed: the set was not pinned (stage 1 S1-14).
- **Who can reach it.** A dependency author or a contributor whose added crate is not noticed in review. Not a
  guest.
- **Fix.** `EXTRA_DIRS` adds `cuda/display` and `firmware/kf-gop` (line 33); build edges are followed (line 40,
  81); `NESTED_LOCKS` reads `firmware/kf-gop/Cargo.lock` (line 36, `nested_lock_externals` at 86); every
  third-party crate must be in `EXTERNAL_PINNED = {"libc"}` (line 38, `unpinned` at 97, applied at 163).
  MEASURED (2026-11-23): the gate is clean (19 workspace crates, 769 files, one external crate `libc 0.2.189`);
  with `EXTERNAL_PINNED` emptied it fails (`rc 1`). `scripts/ci/test_qemu_license_closure.py`: 5 tests; against
  the gate as it was at `4f376f3db` 2 fail and 3 error, after the fix all pass.
