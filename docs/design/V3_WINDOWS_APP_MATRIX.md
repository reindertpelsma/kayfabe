## 1. How a run is driven

```
 host (root, holds the GPU lock)                              Windows guest (kf3-gpu, production flags)
 ─────────────────────────────────                            ───────────────────────────────────────────
 run_windows_apps.sh ─ preflight (no QEMU running, iso sha256)
   winapps.py
     BrokerVm.launch  ── windows_broker_prod2.sh run N ─────▶  fresh overlay of the sealed baseline boots
     Qga.ping  ◀──────────── virtio-serial qga.sock ────────▶  qemu-ga answers
     sign-in (BOOTSTRAP ONLY): QGA `net user vast <pw>`, then QMP send-key  space, <pw>, ret   (as tdr-run.sh does)
     QMP blockdev-add + device_add usb-bot/scsi-cd (read-only) ▶ drive E: label KFAPPS appears
     QGA guest-file-write  guest/*.ps1, py/*.py, web/*.html, stage.json ▶ C:\kf\
     QGA exec kf_guest_setup.ps1 ▶ KFSETUP {cd, DXGI adapters+LUIDs, nvidia-smi, user}  → C:\kf\adapters.json
     for each app:
        QGA exec kf_stage.ps1 -Pkg …  ▶ unpack the packages the app needs from E:\pkg\ into C:\kfapps
        QGA file-write C:\kf\apps\ID.ps1 + ID.json (token, timeout, …)
        QGA exec kf_launch.ps1 -Id ID -Mode service|interactive ▶ one-shot scheduled task (SYSTEM / the signed-in user)
                                                                   kf_run_app.ps1: start marker, child `powershell -File ID.ps1`,
        poll  QGA file-exists C:\kf\results\ID.json  ◀──────────    GPU Engine counters + nvidia-smi sampling, timeout kill,
        QMP screendump at screenshot_s and on failure               event-log counts, writes FACTS json last (= exit line)
        QGA file-read facts + log;  verdict.py decides;  APPRES line
        QGA exec kf_cleanup.ps1, kf_health.ps1 -Since boot ▶ TDR/WER counts, display problem code, nvidia-smi
        restart rule (§2.6) → this guest ends, the rest continues in a fresh one
     BrokerVm.stop (ACPI → QGA shutdown → QMP quit)
   phase 2: every non-PASS app again, alone, in its own fresh guest      → win_isolated.res
   summarize.py → summary.md
```

### 1.1 Why QGA + a detached supervisor, and not keystrokes

* **The only keystrokes are the sign-in** (the lock screen has no other way in without a reboot; an in-guest reboot was
  measured to bring the NVIDIA adapter back in Code 43, `windows_broker_prod2.sh` comments). Everything else goes through the
  guest agent, which the production harness already relies on (`tdr-run.sh`, `qga_run_ps.py`). The sign-in retries three times and
  then fails the guest (`BOOT_FAIL`), with screenshots.
* **No long QGA exec.** The agent cannot kill what it started and a TDR can stall the guest for a while, so a long `guest-exec`
  would pin the channel. Each app is instead a *scheduled task* (`kf_launch.ps1`) that returns at once; the host polls for the
  result file with cheap `guest-file-open` calls. A hung app is killed by the supervisor (`taskkill /T /F`) at its timeout; a
  hung *supervisor* is caught by the host deadline (timeout + 90 s).
* **Two session types.** `service` apps run as SYSTEM in session 0 (compute, CLI tools, headless DXGI/D3D). `interactive`
  apps (OpenGL/Vulkan windows, Edge) run in the signed-in console user's desktop through a task with an Interactive logon
  principal, so they have a real window station — and DWM composition, which is exactly the path that TDRs.
* **The password** is the throwaway test guest's (`KF_GUEST_PW`, as in `tdr-run.sh`); it is never logged, never written to
  the run directory (a unit test greps for it) and never committed.

## 2. Contracts

### 2.1 App delivery without guest internet

A read-only secondary disk, hot-plugged by QMP (`blockdev-add` read-only raw + `device_add usb-bot` on the broker's existing
`xhci.0` + `scsi-cd`, fallback `usb-storage`). It is a **CD-ROM on a USB bus** on purpose: the inbox Windows drivers handle it
(no virtio driver, no reboot), it is read-only by construction and the volume label `KFAPPS` lets the guest find it. The
broker needs no change. (An alternative is a broker `WIN_EXTRA_ARGS` hook that puts the drive on the command line.)

Layout of `kfapps.iso`: `pkg/<package>/<archive>` (the downloads, byte-identical), `tools/*.exe` (the mingw-built test programs),
`guest/` (a copy of the guest scripts; the driver pushes the repository's own copy by QGA, so a script fix needs no new image),
`apps.json`, `KFAPPS.ID` (the image *identity*: sha256 over the sorted file records; `kf_guest_setup.ps1` reports it and the driver
compares it with `manifest.json`). Packages are unpacked in the guest on first use (`kf_stage.ps1`: `tar -xf` for zips and
wheels, `msiexec /a` for GravityMark, `7zr` for hashcat, silent Inno/Qt/VC++ installers for Heaven, Valley, the Vulkan SDK
and the Visual C++ runtime). The Python environment (embeddable CPython 3.12 + the wheels: torch 2.8.0+cu126, torchvision,
numpy, cupy-cuda12x, onnxruntime-directml, onnx) lives under `C:\kfapps\py`; nothing is installed system-wide.
`appdisk.py` can instead pre-extract that tree into the image (`image_form: tree`): it costs ~2 GB more disk and a CD-ROM
read per DLL, so it is off.

**Build and verify** (`build_appdisk.sh`): `fetch` does `curl -I` (recorded as `http`/`head_length`/`verified_utc`) and a full
download per file, pins the sha256 on first fetch and refuses a mismatch afterwards; `build` re-hashes every download, refuses
tampering, assembles the tree from symlinks and runs `genisoimage -udf -J -joliet-long -R -iso-level 3`; `verify-image --mount`
reads every file back out of the finished image and compares it with `manifest.json` (all 67 files and the identity matched on
2026-10-10; `isoinfo` cannot read files over 2 GiB, hence `--mount`).

**Space.** `/var/lib` on the trusted host must keep >100 GB free; it had 129 GB when this started and the TDR hunt's overlays and
dumps took the rest (89 GB at the end). Therefore the image was built in `/dev/shm` (RAM; no transient disk use), the 11 downloads
over 40 MB were deleted once the image held byte-identical copies, and the hard-linked wheel cache was removed: the lane holds
**6.4 GB image + 0.25 GB small downloads**. `build_appdisk.sh` refuses to run when the estimate would cross the floor and has `--out`
for exactly this case. The big downloads come back with `build_appdisk.sh` (pinned hashes). Delete `appmatrix/image/` if the disk
is needed; nothing else depends on it.

**Licences.** No paid or cracked software. Redistribution is *not* granted for GravityMark, FurMark, GpuTest, Unigine Heaven/Valley
(free to download and use): the image is for internal test use on the owner's host and must not be published. The NVIDIA
redistributables, llama.cpp, FFmpeg (GPL build), Blender, hashcat, clpeak, 7-Zip, Python and the wheels are redistributable under
their own licences (column "licence / redistribution" in §3).

### 2.2 Result protocol (per app)

Everything the supervisor writes is under `C:\kf` in the guest and is pulled by the driver into `<run>/apps/`:

| file | meaning |
|---|---|
| `results\ID.start` | **start marker**, written before the app starts: `{app, token, start_utc, boot_utc, pid, session}` |
| `logs\ID.log` | the app's stdout+stderr; first line `=== ID start=… boot=… timeout=…`, last line `=== end rc=… secs=… <utc>` (**exit line**) |
| `results\ID.json` | the **facts**, written last and atomically: `rc`, `secs`, `quiet` (seconds since the output last grew, to tell a slow app from a hung one — as in the Linux harness), `timed_out`, `boot_utc_start/end`, `pdh` (max utilisation per GPU engine type on the NVIDIA LUID and on every other LUID, sampled every 2 s over the process tree), `smi` (peak utilisation, peak memory), `events` (§2.4), `gpu_devices`, `log_tail`, `digests`, `out_files`, `token` |
| `apps/ID.verdict.json` (host) | the verdict with the restart decision and the guest tag |

A start marker without facts after the deadline means the *supervisor* died with the guest: the host books a FAIL whose note
says `guest-rebooted (bugcheck?)` (boot time changed), `agent-lost` / `guest unresponsive` (QGA gone) or `qemu-exited`.
A killed job and a running job do not look alike: `session.log` has `START` and `EXIT rc=` lines, and a run directory without `EXIT`
died. The per-app token prevents a stale result of an earlier attempt from being accepted.

**Verdict** (`verdict.py`, pure, unit-tested) — the Linux vocabulary and predicate: **PASS** = rc 0 *and* the app's success string
*and* no `^CHECK .*FAIL` (or the app's own fail pattern) *and* a GPU-use proof *and* no engine activity on a non-NVIDIA adapter;
**FAIL**; **TIMEOUT** (killed at the app's timeout, rc 124); **NOTRUN** (a precondition is missing: package stage failed, binary
absent — never a statement about the GPU); **BOOT_FAIL** (the guest did not come up; booked on the first app of that boot, as the
Linux harness does); **PASS\*** (output digest differs from a reference). The `APPRES` line is the Linux one plus `guest_tdr=`,
`wer=`, `gsp_cycles=`, `proof=`, `tier=`, `cat=`, so the Linux `summarize.py` regex reads it unchanged.

### 2.3 GPU-use proof (WARP does not pass)

An app passes only if at least one of its declared proofs holds, and a software adapter is a failure even then:

* `out:<regex>` — the app's own output names the NVIDIA device (`deviceQuery`'s device line, `Renderer model: …NVIDIA`, the
  WebGL unmasked renderer, WebGPU `vendor: nvidia`, llama.cpp's `Device 0: NVIDIA`, `KFDX selected "NVIDIA …"`);
* `pdh:<engine regex>` — the `\GPU Engine(pid_*_luid_*_engtype_*)\Utilization Percentage` counters of the app's process tree show
  >0.5 % on a matching engine type (`3D`, `Compute_0`, `Cuda`, `Copy`, `VideoEncode`, `VideoDecode`) **on the NVIDIA adapter's LUID**
  (taken from DXGI by `kf_guest_setup.ps1`);
* `smi` — `nvidia-smi` utilisation ≥1 % or ≥64 MB of memory above the pre-app level during the run;
* the **adapter exclusion**: any activity above 1 % on a non-NVIDIA LUID (the Microsoft Basic Render Driver / WARP) fails an app
  (`non-NVIDIA-adapter:<engine>`), and `kf_dxprobe`/`kf_glgears` refuse any adapter that is not NVIDIA hardware by construction.

### 2.4 Crash and TDR accounting per app

* **Guest side**, per app (events since the app's start, System log): `nvlddmkm` 153 (the TDR record: `Resetting / Restarting TDR`),
  `Display` 4101, WER 1001 reports of LiveKernelEvent codes 117/141/116 (`VIDEO_TDR_TIMEOUT_DETECTED` / `VIDEO_ENGINE_TIMEOUT`) and
  bugchecks, `Kernel-Power` 41, 6008, other `nvlddmkm` events, and the first 16 lines of them. `APPRES guest_tdr=` = 153 + 4101,
  `wer=` = WER reports.
* **kayfabe side**: the number of `GSP phase Running -> Suspending` lines in the run's `qemu.log` before and after the app
  (`gsp_cycles=`; the TDR hunt's counter — note that in run 263 it counted 7 resets while the guest log held 3 events and a 0x116
  bugcheck, so both are recorded).
* A TDR does not change a PASS (the app finished and proved GPU use) but is visible in every row and in the summary.

### 2.5 Watchdog and recovery — a TDR must not poison the rest of the run

After each app the driver runs `kf_cleanup.ps1` (kills leftovers of the app and its Edge profile) and `kf_health.ps1 -Since <guest boot>`
(boot time, NVIDIA display device problem code, a 15 s-bounded `nvidia-smi`, interactive user, TDR/WER counts since the guest started).
**The guest ends and the remaining apps continue in a fresh guest** (a new overlay of the baseline, a new `boundary-kayfabe-N`) when:
the boot time changed (bugcheck/reboot); the agent is unreachable for `recover_wait` (180 s); the QEMU process exited; the NVIDIA device
reports a problem (Code 43) or `nvidia-smi` fails; the supervisor missed its deadline; or the guest has had **`--max-tdr` (default 3)**
TDR events (the default `TdrLimitCount=5 / TdrLimitTime=60 s` rule turned a cluster of 5 into the 0x116 of run 263, so 3 keeps a guest
clear of it). Further limits: `--per-guest` (default 8) apps per guest, as `APPS_PER_BOOT` bounds contamination on Linux; three
consecutive guests that do not come up abort the run (exit 3); at most 200 guests. **Phase 2** re-runs every FAIL/TIMEOUT/BOOT_FAIL
app alone in its own fresh guest, and that verdict is the final one (the batched one is shown beside it), exactly as the Linux
`guest_isolated.res` works. `--resume` skips apps already in `win.res`.

### 2.6 Summary format

`summarize.py RUN… [--linux-ref DIR] [--digest-ref FILE]` prints, per run, `| app | linux guest | win (batched) | win (alone) | detail |`
(`linux guest` = the worst Linux verdict among the rows the app stands for, from a Linux run directory's `guest.res` /
`guest_isolated.res`; `detail` carries rc/secs/quiet/note of a non-PASS, `N guest TDR`, `WER`, `gsp_cycles`, the proof of a PASS and
digest comparisons), then counts per verdict and category, TDR totals, and the Linux rows with no Windows equivalent.

Where a Linux row is a CUDA *sample* (no prebuilt Windows binary exists, and the guest has neither `nvcc` nor MSVC), the counterpart runs the same
class of computation with PyTorch/CuPy/NVRTC against a CPU reference (`guest/py/win_cuda_equiv.py`, `cupy_nvrtc.py`); the 17 pure-math tests were
run against the CPU in place of the GPU to check the test logic, and the SHA-256 kernel was compiled as plain C and compared with `hashlib`. The CUDA
toolkit's own prebuilt `demo_suite` (deviceQuery, bandwidthTest, vectorAdd, nbody, oceanFFT, randomFog) is used for the rows it covers; `busGrind.exe` is
staged inside it but not run (it imports `VCOMP110.DLL`). The CUDA driver-API ladder (cup2/cup3/cup8) is cross-built with mingw from the same sources as
the Linux ladder (`scripts/bench/windows/cuda/build_cup_win.sh`).

#### 4.3.1 `overlay_yuv_*` — the forced YUV overlay (MPO) probe

`tools\kf_overlayprobe.exe` (source `scripts/bench/windows/appmatrix/tools/src/kf_overlayprobe.cpp`, mingw static, built by `build_tools.sh`) exists so the overlay
path cannot silently fall back: Edge/DWM are free to choose composition, this program is not. It opens a window, creates a D3D11 device on the NVIDIA adapter
(WARP/Basic Render refused, adapter name printed), checks `IDXGIOutput3::CheckOverlaySupport` for NV12/YUY2/P010, creates a flip-model YUV swap chain
(`CreateSwapChainForComposition` + a DirectComposition visual with a scale transform, `DXGI_SWAP_CHAIN_FLAG_YUV_VIDEO`; `--mode hwnd`, `--flags yuv+fsv`,
`--format yuy2|p010` are the variants) and presents a known pattern at a fixed rate with `Present1` (SMPTE-like 75% bars in exact BT.709 limited-range
YUV, a marker moving 8 px/frame, a 16-bit binary frame counter; all three are decoded back in the host unit test). **Proof** is
`IDXGISwapChainMedia::GetFrameStatisticsMedia().CompositionMode == DXGI_FRAME_PRESENTATION_MODE_OVERLAY`, sampled after every present.

* Exit codes: 0 PASS; 2 NEVER_OVERLAY (not reached within `--require-overlay-within`, default 10 s; the run ends then); 3 LOST (a non-overlay present after the first
  overlay outside the scenario's declared grace windows, or less than 80% overlay in the last 2 s; `--tolerate N` allows N); 4 STUCK (a watchdog thread saw no
  heartbeat for 3 s: a `Present1` or window call did not return; the result is written by the watchdog with the phase); 5 SETUP (no NVIDIA adapter, no output,
  no `DXGI_OVERLAY_SUPPORT_FLAG_DIRECT` for the format unless `--ignore-support`, device or swap chain creation failed); 6 USAGE; 7 TOO_FEW_FRAMES (< 50% of the
  expected presents); 8 DEVICE_LOST (`DXGI_ERROR_DEVICE_REMOVED/RESET`, i.e. a TDR during the run).
* Output: `KFOVL <key> <value>` lines, `KFOVL JSON {...}` and the last line `KFOVL RESULT PASS|<NAME> <why> (code=N)`; the same JSON goes to `--out`. JSON: adapter,
  `overlay_support` (flags per format), config, frames presented/expected, worst present latency, worst frame gap, `mode_totals`, `per_second` counts of
  composed/overlay/none/composition_failure/stats_error, every `transitions` entry, the scenario `events` with their times, verdict and code.
* Scenarios (`--scenario`, or 1..8): `steady` (30 s, `--duration`), `move` (the window crosses the screen for 20 s), `resize` (resize, maximise, restore),
  `fullscreen` (borderless toggle x3), `occlude` (a topmost window over a third of the video for 5 s: the overlay may demote, presents must keep completing and the
  overlay must return), `hide` (hide/show, minimise/restore), `recreate` (ResizeBuffers and a new swap chain with new surfaces every 2 s), `soak` (all of them in
  rotation, `--duration`, default 60 s, 1200 for 20 min). Demotion is tolerated only inside the grace windows each event declares (`--grace-ms` adds to them);
  steady and move have none.
* Matrix wiring: `overlay_yuv_probe` (steady, tier 1, interactive session), `overlay_yuv_{move,resize,fullscreen,occlude,hide,recreate}` (tier 2) and `overlay_yuv_soak`
  (tier 3); success = `^KFOVL RESULT PASS`, proof = `out:KFOVL adapter "NVIDIA` or the GPU Engine counters. Run by hand in the guest:
  `kf_overlayprobe.exe --scenario occlude --out C:\kf\out\overlay.json` (the app disk carries it as `<drive>:\tools\kf_overlayprobe.exe`; the lane copies tools to `C:\kfapps\tools`).
* Tested: the pure logic (YUV values, fill/decode round trip for NV12/P010/YUY2, tracker, verdict, scenario timelines, JSON) in `tests/test_overlayprobe_logic.py`;
  the PE builds and runs under Wine up to the SETUP exit (Wine has no NVIDIA adapter), which exercises the JSON path. **Not tested on Windows**: swap chain creation with
  `YUV_VIDEO`, staging-texture `Map` on NV12, whether `GetFrameStatisticsMedia` reports OVERLAY on the kayfabe display, every scenario's timing.

## 5. Running the lane once Windows is stable

Gate: the production harness (`tdr-run.sh` style) holds the desktop for the whole length of the longest app (the 15-minute torch AI bench and the 60 s
stress rows) without a TDR, or the owner accepts TDR-bearing results. Then, on the trusted host, with nothing else on the GPU:

```sh
cd /var/lib/kf-windows-20261005/kayfabe-win-<rev>      # a checkout of branch claude/windows-appmatrix-20261010 merged into the Windows integration branch
python3 scripts/bench/windows/appmatrix/appdisk.py verify-image --manifest /var/lib/kf-windows-20261005/appmatrix/manifest.json \
        --iso /var/lib/kf-windows-20261005/appmatrix/image/kfapps.iso --mount            # optional: re-check the image (needs root)
export KF_GUEST_PW='<the throwaway test-guest password>'      # account `vast`, as in tdr-run.sh
# dry run first: validates the manifest/inventory, runs the tests and the whole driver against the mock guest
bash scripts/bench/windows/appmatrix/run_windows_apps.sh --dry-run
# the real run (the production flags are the broker's own list; add measurement flags with WIN_FLAGS)
setsid bash -c 'flock -o /tmp/kayfabe-fastguest.lock env KF_LOCKED=1 \
   WIN_PRE_GUEST_CMD="bash /var/lib/kf-windows-20261005/pti-iommu_nogdm.sh identity" \
   WIN_POST_GUEST_CMD="bash /var/lib/kf-windows-20261005/pti-iommu_nogdm.sh DMA-FQ" \
   bash scripts/bench/windows/appmatrix/run_windows_apps.sh \
     --run-dir /var/lib/kf-windows-20261005/appmatrix/runs/w1 --kf3-rev 459da55d --run-base 300 \
     --iso /var/lib/kf-windows-20261005/appmatrix/image/kfapps.iso \
     --broker /var/lib/kf-windows-20261005/kayfabe-win-6fafcc6e/scripts/bench/windows/windows_broker_prod2.sh \
```

## 7. Risks and decisions

* **Baseline.** The Linux matrix has a bare-metal host column. Windows has none on this host; the equivalent is the **VFIO Windows arm** (the same baseline disk, the same
  app disk, the real GPU passed through), which `pc_boundary_experiment.py --arm vfio` already boots for research. The driver is launcher-agnostic (`--broker` takes any
  script with `run N` / `stop N` and the broker's state file); a VFIO launcher with that contract does not exist in git. Without it, a Windows FAIL cannot be told apart
  from "this app does not work on Windows at all". Owner decision: build that launcher, or accept Linux-guest verdicts as the only reference.
* **Production flags and networking.** The lane uses the broker's flag list unchanged. `windows_broker_prod2.sh` gives the guest user-mode networking with `restrict=off`; the lane
  never uses it, but a run that must prove "no internet" needs `restrict=on` (a broker change; `win_vm.sh` already does it).
* **Defender.** `kf_guest_setup.ps1` excludes `C:\kf`/`C:\kfapps` and tries to turn real-time scanning off (hashcat is flagged); under Tamper Protection that fails and is recorded.
* **Edge on LTSC** is assumed to be installed (the production harness double-clicks it); HEVC and AV1 Edge decode need extensions and are not claimed.
* **Time.** A full tier-1 pass is roughly 40 guests' worth of apps at ≤8 per guest; guest boot to desktop on the nested-free 4070 host took minutes in the recorded runs, and the
  first stage of the Python environment unpacks ~5 GB per fresh guest. Estimate, not measured.
* **Doc hygiene.** This document's tables are generated; edit `gen_apps.py` / `manifest.json` and run `gen_apps.py` then `gen_doc.py` (tests fail on drift).
