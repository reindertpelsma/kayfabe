## Open-source contract

CODE READ (public ogkm 580.65.06, commit `307159f2623d3bf45feb9177bd2da52ffbc5ddf9`, `ctrl2080internal.h:3993–4030`): INIT has 16 bytes, input `NvBool bInit` at0 and input `NvU64 physAddr` at8; no output fields. It initializes/destroys physical RM's mapping of the kernel RM User Shared Data region. `bInit=0,physAddr=0` tears down. Generated `g_subdevice_nvoc.c:4735–4758` names `subdeviceCtrlCmdInternalInitUserSharedData_IMPL`, flags `0xc0 = INTERNAL | ROUTE_TO_PHYSICAL`. `rmapi/control.c:799–803` refuses non-internal callers: this is kernel-internal protocol, not an unprivileged host verb to forward.

CODE READ (same pin, `gpu_user_shared_data.c:220–315`, `mem_mgr.c:733`, `g_gpu_nvoc.h:1407`, `gpu_shared_data_map.h:38`): kernel RM allocates cached contiguous system memory with `MEMDESC_FLAGS_USER_READ_ONLY`, maps/zeroes it and sends its GPU-visible physical/DMA address to physical RM. `OBJGPU.userSharedData` owns its descriptor, kernel map, polling state and refresh bookkeeping. The create HAL is common to GA104/GB202/GB205; only T234D/T264D select a no-op. The public tree declares/routes the physical INIT handler but does not supply its body. Mapping semantics come from the header/caller; native status comes from the recorded interface, not firmware inspection.

CODE READ (same pin, `gpu_user_shared_data.c:233–244,307–315,350–416`): `_gpushareddataInitGsp` returns an error on failed INIT, but `gpuCreateRusdMemory_IMPL` discards that return and the initial poll-frequency return, then returns0. Later class0xde allocations with nonzero poll masks can propagate poll errors. Destroy unregisters then unmaps/frees the local region. These are public Linux paths; Windows 580.88's proprietary failure policy was not inspected.

CODE READ (same pin, `cl00de.h:37–89,350–414`): zero timestamps are invalid. Readers require stable sequence/timestamp values around a complete record. Kernel RM also writes BAR1/PMA fields (`kern_bus.c:1234`, `mem_mgr.c:3223`); a GSP publisher must not overwrite them. A valid `perfDevUtil` record contains GPU, memory and four video-engine metrics together. Valid zeros for unavailable members are not justified. [SDK layout compilation](../../traces/bw9_20261018/rusd_layout.c) yields [2600 bytes, perf offset1976](../../traces/bw9_20261018/rusd_layout.txt) for this pin; this is not a branch-independent layout assumption.

## Proposed derived behavior and decisions

INFERRED design: install a single per-VM, epoch-bound registration for the entire validated guest system-RAM DMA span, resolved through current IOMMU/RAM authority. The guest kernel owns the RAM and read-only userspace mapping. The VMM owns only a checked lease and publisher bookkeeping; no host RUSD region, new GPU mapping, host pointer from the guest, privileged verb or vCPU work is needed. Worker publication uses existing checked guest-RAM access. The handle-based `memory_access::Lease` is a useful lifetime seam, but raw `physAddr` needs its own valid topology/life witness rather than bypassing that authority.

INFERRED design: success means real registration/publication obligations are met; preserve input params and set envelope/control status0. Implement INIT/POLL together. A supported requested group publishes complete authoritative VM data; unsupported groups stay invalid/refused. Mask0 stops polling. Destroy/reset/unload revoke queued writers before acknowledgement; failed reinit preserves old state. Use versioned source-derived layouts, proper release/acquire ordering, a guest-compatible timebase, bounds/overflow/holes checks and one bounded registration per VM. No host-wide utilisation, valid zero filler, fabricated GPU completion, timeout adjustment or captured address/table is involved.

CODE READ decision (`OWNER_RULINGS.md` §W, §S, §Q): production success is parked. The existing set does not establish accurate VM GPU residency/busy accounting, memory/video members or Windows behavior under partial support. Event arrival/submission latency alone is not a utilisation meter. The owner already requested own-VM read-only utilisation, so this is a semantic/data-source gap, not a request to forward privileged controls.

Owner decisions, with recommendations:

1. Prioritize the missing-completion discriminator below; RUSD is not established as the GB202 cause.
2. Define accurate complete per-VM utilisation semantics/source, or approve NON_POLLING-only support with invalid polled data pending a real meter. Preserve refusal until the selected publisher exists.
3. If partial support is chosen, approve and validate its supported-feature/poll-mask fallback contract on Windows before shipping success.
