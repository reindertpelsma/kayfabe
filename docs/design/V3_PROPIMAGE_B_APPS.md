# Application rows for the second proprietary image

Same image format, same runner, same state file as the first image (`propimage.py`, `propimage_check.py`); only the application list differs. `propimage_check.py --app-set b --data-iso FILE` selects it (`a`, the default, is unchanged). The applications are creative tools (raster, vector, layout, motion, video, photo, 3D, document, animation). Open test material comes from a read-only data volume labelled KFDATA that the harness attaches on the AHCI cd port (`propimage.build_argv(..., data_iso=...)`); the volume is built by `scripts/bench/assets/build_test_assets.py` from public sources whose licences were read on the source pages (`scripts/bench/assets/test_assets.json`, `README.md` there). Nothing proprietary is needed as input: the After Effects project is generated by a script, the InDesign document and the Illustrator art are generated, the Animate document is generated by a JSFL script.

## How a row works

1. `propimage_apps_b.run_check` writes one PowerShell script (`scripts/bench/windows/apps_b/lib.ps1` plus the row's script) and starts it in the logged-in desktop session through a scheduled task at the user's normal integrity level. The applications' automation interfaces refuse an elevated caller (measured on the image B runs of 2026-11-16, `traces/imageb_apps_20261116/`: `CO_E_SERVER_EXEC_FAILURE` from an elevated task, success from a normal one), so this differs from the first image's task wrapper on purpose.
2. The script handles first-run dialogs by UI Automation (a fixed list of harmless button names; sign-in, purchase and trial buttons are never pressed), drives the application through its own automation (COM + ExtendScript, a command-line script, `aerender`, a plugin the application loads from its per-user folder), writes the outputs and `result.json` into `C:\kfapps\<run>\<app>`, quits the application and records whether the exit was clean.
3. The host pulls only the file names the guest lists (safe names, bounded size) and grades the files themselves (`media_check.py`: PNG decode with pixel statistics, JPEG/PSD headers, PDF page count, MP4 duration/codec/size). No screenshot is taken or stored; the application windows show account details.
4. A row that is meant to use the GPU runs inside `gpu_assert.assert_gpu_used`: the guest samples `nvidia-smi` (query and dmon) while the operation runs; an engine that stayed idle FAILS the row and the sampled numbers are written to `<app>_gpu.json` (text). A row that only proves a launch is PASS_LIMITED and says so; it never claims GPU use.

A row that is meant to use the GPU asserts it from the HOST's nvidia-smi (`gpu_assert.py`); rows marked "sampled" record the numbers and assert nothing. Disabled rows say why and are skipped by default (`--apps` can still name them).

## Driver facts that cost time (MEASURED 2026-11-16, kf3 on a Vast RTX 4090 and no-GPU clones on the pc)

- Automation interfaces (COM) fail from an elevated task (`CO_E_SERVER_EXEC_FAILURE`); the rows run at the user's normal integrity level.
- Dialogs are found by UI Automation two levels deep only: a full subtree walk of Premiere's or After Effects' window blocks for minutes. Some dialogs (After Effects, the no-GPU Photoshop notice) expose no buttons; the keyboard fallback (`Press-Key`) closes them. Without a GPU, Photoshop's graphics notice blocks COM until it is closed.
- After Effects: scripts that write files are refused until the per-user preference `Pref_SCRIPTING_FILE_NETWORK_SECURITY` is 1 (the lib sets it in the user's Prefs.txt while the application is not running); a script handed to AE at the cold start is ignored about half the time, so the lib starts AE, waits, and hands the script to the idle instance. `aerender` redirected output makes `Process.HasExited` unreliable: wait with `WaitForExit`.
- Photoshop: 100 full-size duplicate layers at 8K exceed the guest's 8 GB RAM; the row pastes 1536x1024 patches instead. Quitting after an 8K session takes longer than 40 s.
- Animate: `Animate.exe script.jsfl` shows an "Open JSFL File" dialog and no keyboard route ran the script; the three Animate rows are disabled with that reason. Lightroom Classic did not load a plugin from the per-user Modules folder; its launch row remains.
- GPU use is judged from the HOST nvidia-smi: the guest's utilisation counters are `[N/A]` under kf3 (a GSP RPC, function 76, is not served).
- The guest-visible VRAM is the device's `fb-mb` (4096 by default): applications report 3.8 GB. The After Effects rows were run with `--fb-mb 8192`.
- Second pass (2026-11-16, `traces/imageb_apps_20261116/second_pass/README.md`): the stage's GPU step failed on 3 of 3 fresh stage boots while 5 of 5 boots started from the dev wrapper passed with an identical QEMU command line (unresolved); no gate row has a stage verdict. Premiere's project calls hang behind the "No output device" window (no audio device in the guest).
- A phantom PnP instance of the build host's GPU makes the harness's device restart fail on any other die (fixed in `propimage_check.py`).

- ExtendScript hosts (After Effects, Premiere Pro, Media Encoder): `AfterFX.exe -r script` is unreliable (ignored in about half the cold starts); every host runs the `*.jsx` files of its `Scripts\Startup` folder, so the harness installs (elevated, once per row) a stub there that reads `C:\kfhw\<app>_job.txt` and runs the script named in it after a short `$.sleep`; `app.scheduleTask` never fired. The row writes a marker as its last act; the lib retries a start without a marker (3 attempts, recorded).
- After Effects: `aerender -reuse` hangs at start (0 CPU seconds, no child process); without `-reuse` it renders in-process. A guest with less RAM than the vendor minimum shows a "System Compatibility Report" window that blocks quitting: Enter closes it, UI Automation does not see its buttons. The "Show Tip of the Day" preference is switched off in the user's Prefs.txt together with the file-access one.
- PowerShell traps that cost hours: variable names are case-insensitive, so `$r = ...` at the top of a row script replaced the result table `$R`; `Get-Content -Raw` assigned to a result field serialises the drive and path objects too (a 47 MB result.json); `-PassThru` processes with redirected output need polling by id (`Wait-Proc`), not `WaitForExit`. Tests pin the first two.
- Crash evidence: the harness sets WER LocalDumps (minidump, `C:\kfapps\dumps`) elevated before each row; `Finish` writes `app_events.txt` (Application log 1000/1001/1002 entries since the row started, dump names and sizes).
- Reference compare: every row writes `output_stats.json` (sha256 and PNG pixel statistics of each pulled output); with `KF_REFERENCE_DIR/<row>.json` from another platform the statistics are compared within a tolerance and the result is recorded as `reference` (only `KF_REFERENCE_STRICT=1` makes a mismatch fail the row).

## Built-in and third-party suites

Verified offline in the image: the sniffers above (`gpudiag`). Not driven: Photoshop's Help menu GPU pages (their data is the same as `app.systemInformation`, which the `photoshop` row reads), Premiere and After Effects renderer settings (set in the generated project: `app.project.gpuAccelType`), Lightroom's System Info (a window). PugetBench for Creators: Puget's end-user licence forbids transferring the software to third parties, restricts the free licence to personal non-commercial use, and ties command-line automation and local result logging to a paid licence (checked on Puget's pages on 2026-11-16: https://www.pugetsystems.com/pugetbench/creators/puget-bench-end-user-license-agreement/ and the download page). It is therefore not bundled and not run. If the owner supplies a licensed package it would be a pinned private object like the first image's SPEC zips, row `pugetbench`: NOT RUN, package not pinned.

## Stage selection and the report (2026-11-16)

CODE READ, GPU-free tested (`scripts/ci/test_propimage_apps_b_stage.py`: classes `Run`, `Report`, `PayloadWiring`); not run on a box.

Selection. `propimage_apps_b` is a manual-only payload stage like `propimage_apps` (`MANUAL_ONLY_STAGES` in `vast_payload.py`, flag `PROPIMAGE_APPS_B_IN_LARGE = False`): it is planned only in the large tier and only when named by `--only propimage_apps_b`. No instruction field and no schema change; `--only propimage_apps` does not select it and the instruction's `propimages` list (the generic runner, image A's stage) does not either. Its place in the plan is right after `propimage_apps` and before the SPEC lane. It has its own prefix (`/workspace/kf-propimage-b`), record (`propimage_apps_b.json`), evidence directory (`propimage_apps_b/`, text only), time floor (240 minutes remaining) and soft-deadline margin (300 s). The stage row is `propimage_apps_b`: it passes only on exit 0 and a `KF_PROPIMAGE_APPS_B_RESULT` record whose verdict is PASS and whose `sha` is the run's; a red record is kept in the result file under `propimage_apps_b` either way. The image-set choice is the stage, not a flag of the generic runner: the generic runner (`propimage_images.py`) has no data volume, `PASS_LIMITED`, GPU assertion record or per-row census, so image B keeps its own stage and shares only `propimage_apps.py`'s helpers.

Lanes. The lane of a row comes from `propimage_apps_b.CHECKS`, never from the guest's `verdict.json` (the stage sets it; `vast_report.PROPIMAGE_B_ROWS` repeats the table and a test pins the two equal). ONLY gate rows decide the verdict: the stage is PASS when every gate row is PASS or PASS_LIMITED, FAIL (`APP_FAIL:<row>`) when one failed, RETRY (`HARNESS:<row>`) when a gate row has no verdict. A discovery row of any verdict never fails the stage.

The report (`vast_report.validate_propimage_apps_b`, read by `read_result_file`; strict and bounded: fixed key sets, printable-ASCII strings of at most 200 characters, at most 8 Xid lines and 8 census ids per row, at most 49152 bytes; the stage shrinks evidence lists, Xid lines and census ids to fit):

- A PASS record needs every enabled gate row present and PASS or PASS_LIMITED, an empty `failed` list, every boot proven offline, and every disabled row listed in `not_run`. A payload that says PASS over a FAIL or RETRY record is refused.
- Discovery rows are listed separately as the known-breakages table, `breakages`: one entry per discovery row that did not pass, `{row, verdict, class, census}` with `class` one of CRASH, HANG, TDR, XID, ASSERT, OUTPUT_MISMATCH (the generic runner's classes; derived from the harness exit, the host Xid window and the kf3 census) and `census` the line count and the counts per keyword (`unserviced`, `foreign_class`, `refused`, `dead_channel`, `walk`, `derived_miss`, `xid`, `tdr`). The validator refuses a table that hides a failing discovery row, lists a gate row, or disagrees with the rows' verdicts. The stream prints one `KF_PROPIMAGE_APPS_B_BREAKAGE row=... verdict=... class=...` line per entry before the result line. There is no expected-fail list: every discovery failure is only listed (the ratchet is the generic runner's "Later" item in `V3_PROPIMAGE_RUNNER.md`).
- Disabled rows are `not_run`: `{row: reason}`, never rows of `apps`.

Side effect of merging the generic runner (#444) with this branch: both pins files pin the same signed boot GOP under one `ref`; `propimage_images.all_pins` now accepts an identical duplicate and still refuses two different objects under one ref (`PIN_DUPLICATE`).
