# V3 Windows support profile: one switch for the Windows-only capabilities

**STATUS: LIVE (IMPLEMENTED, NOT RUN ON HARDWARE), 2026-11-15.** Stage 1 of the flag cleanup implements this design (owner ruling `OWNER_RULINGS.md` §AT, 2026-11-15): the property is `windows-support=on|off` (the name is final), default on. GPU-free tests and mutants only; the first hardware proof is the Windows gate on a rented box with NO env file (*Implemented 2026-11-15*, below). Original status: DESIGN-ONLY, 2026-10-13 (owner decision on the default; scope fixed by ablation). Related: `V3_WINDOWS_USER_RING_RELAY.md`, `V3_FLAG_INVENTORY.md`, owner rulings D4 (Windows-only behaviour keyed on the guest's declared state, not a flag), §AE (no heuristics; a fallback is a clean mode), §AI (Linux Passthrough forbids host-owned mappings).

**⊘ Corrections folded 2026-11-15 (Stage 1):** (1) the property name `windows-support` is final, not provisional. (2) *What the switch is* asks for "a single capability witness ... no scattered `if windows` checks": `WindowsProfile` is that witness, but it is read at about ten sites (six `if windows.support()` in the served chain, the channel link's own copy of the identity, `bool`s copied into `ChannelAlloc`, `PtChan` and `Slot`), which is a deviation recorded as a follow-up (one capability object passed to every admission point). (3) The identity is guest-declared: see *Security posture*, below.

## Decision (owner, 2026-10-13)
A device property `windows-support=on|off` (name provisional) gates a chunk of kayfabe that Linux guests do not use. **Default `on`, so every image is supported out of the box.** `off` is a hardened Linux-only profile: the Windows capabilities cannot be reached even by a guest that declares a Windows identity.

## What the switch is (and is not)
- It gates AVAILABILITY of capabilities. The guest's declared state still selects routing inside an enabled profile (D4); the switch is not a heuristic and not a behaviour fork with one wrong value: both values are valid configurations.
- A configuration chosen by the VM's launcher (a device property), never an environment variable and never inferred from the guest.
- Mechanism: a single capability witness constructed only when the switch is on (the pattern already used by `WindowsUserRingPermit` and the Windows mapping permit), passed to the admission points, so with the switch off the Windows paths cannot be entered. No scattered `if windows` checks.

## Candidate scope (to confirm by ablation: a feature is Windows-only only if a Linux guest runs fully with it off)
USER ring relay and migratable passthrough; the deferred API (`5080` admission, registry, host-authored actions); Windows user-channel passthrough routing; the Windows-only display features (SDR colour, LUT mirror, ILUT offset 256, IMP enable) and display-control answers only Windows issues. Not gated: anything Linux needs (UVM, doorbell tiers, the common display path, channel budget, kf-mem).

## Tests (the point of the switch)
- Linux gates (9/9 + gate 10) and the fast suite (30/30) pass with `windows-support=off` AND with `on`; the off run is the proof that Windows additions do not change Linux.
- Windows runs use `on`. A Windows guest on an `off` VM must fail cleanly and by name (counted refusals), never hang or fault.
- Hostile test: a Linux-profile guest that declares a Windows identity and sends Windows-only allocations is refused with `windows-support=off`.
- The flag inventory records this property as a profile, and every behaviour flag it replaces is deleted (hardwired or removed), per the flag rules: only debug and measurement trace flags remain.

## Per-driver and per-die differences are derived, not flagged (owner, 2026-10-13)
Where a behaviour is right for one guest driver or die and wrong for another, it is DERIVED inside kayfabe from the guest's declared state (the driver branch and version from SET_GUEST_SYSTEM_INFO, the host-derived chip facts), so it never needs to appear on a command line. Conditions for a derived switch to be accepted:
- it changes COMPATIBILITY behaviour only, never a security boundary: a guest controls what it declares, so it must be safe for any declared value (a lie can only change that guest's own compatibility behaviour, never privilege, mapping exposure or another VM);
- it is a pure function of declared and host-derived facts, covered by GPU-free tests that include unknown and malformed values;
- a declared state outside the measured set takes the clean fallback (refuse by name, count, claim nothing; §AH), never a neighbour's behaviour;
- a flag that survives ablation only because two drivers disagree is replaced by such a derivation, and the flag is deleted.

## The host driver is measured; the guest version is untrusted (owner, 2026-10-13)
Two disjoint version axes (`kf_abi::host_driver`, `kf_abi::hostabi`, `V3_DRIVER_MATRIX.md`): the GUEST version (declared, untrusted) only selects how kayfabe decodes the guest's own requests, so a false declaration can at most make that guest's requests fail or mis-parse; the HOST driver version is measured on the host
by kayfabe, which no guest can influence, and it alone selects the layouts of every host ioctl kayfabe issues. Host calls are authored from kayfabe's own internal structs and carried to the host's measured layout by field name (exact-membership rule: an unmeasured host driver, or a field the host layout lacks that carries a value, is refused by name), never forwarded as guest bytes.
Properties to pin with tests (GPU-free): (1) the host version used for layout selection comes only from the host query, never from any guest-supplied value; (2) for every host control kayfabe issues, a property test with random guest-controlled input shows that only the allowlisted value fields can differ from the authored default (handles, pointers and every unnamed field are authored, translated or zero, never taken from guest bytes); (3) a host driver outside the measured set refuses the calls whose layout was not measured, with a counted named error;
(4) a guest that declares any version, including a different one from what it really is, cannot change a host struct field outside that allowlist. Open: the `0x2080a028`/legacy-GSS host asks have no measured layout at 595.91.07 and are refused (inventory row `hostask-2080a028`).

## Guest version: detected, not trusted; skew rejected when it cannot be satisfied (owner, 2026-10-13)
- **No vGPU presentation** (`V3_VGPU_COMPAT_RESEARCH_20261013.md`): every vGPU graphics workload also runs on bare metal, which kayfabe supports, so no workload needs it.
- **Detect the guest version instead of relying only on `guest-driver=` on the command line.** Sources, all guest-controlled and therefore never trusted: the fn-1 fields (`guestDriverVersion`, `guestVersion`, changelist, vgx pair) and the GSP firmware image the guest loads (its version section), checked against each other. `guest-driver=` stays only as an optional pin: if given it must equal the detection or the boot is refused by name. What the detection selects is a layout row; a false declaration can only select a row that the guest's own requests then fail to match (refused, counted), never another VM's or the host's behaviour.
- **Skew handling is ours, tested, and bounded.** For every pair (declared guest branch, presented row) kayfabe supports only what the matrix shows to be losslessly transcodable for the payloads it uses (fields added or removed that kayfabe does not need are fine; anything else is a refusal named at boot), the way vGPU also refuses what it cannot satisfy. Closed-driver branches that have no open tag (Windows r580_78) map to a measured twin row only with evidence (captured exchanges plus the oracle), recorded per row.
- **Tests:** the fn-1 negotiation oracle built from NVIDIA's own code (`claude/fn1-oracle-20261013`); matrix transcoding round trips across every supported pair; declared-version fuzz (random and malformed strings refuse or fall back cleanly); a mismatch beyond the supported distance refuses at boot with a named error.

## Implemented 2026-11-15 (Stage 1; GPU-free tests and mutants, NOT run on hardware)

**What is in.** `kf_rm::winprofile::WindowsProfile` is the capability witness this document asked for: `support` (the device property, `kf3_realize`'s `windows_support` argument, ABI 33) and the guest's declared identity (`declares_windows`: the measured Windows build, read from every fn 1; each declaration replaces the last). `WindowsProfile::active()` is true only when both hold. One value per VM is shared by the served chain (a `CommandObserver` seated first records the declaration; `WindowsOnly<P>` wraps each Windows link so it answers, holds and defers nothing when inactive), the channel link (`ChannelAlloc::windows`, `user_work`), the memory plane (the mirror-space start) and the display plane (the SDR colour path and caps page). The 18 profile flags are hardwired together and every env read is gone; the groups, their tests and what each mutant proves are in `V3_FLAG_INVENTORY.md` (amendment 2026-11-15) and `scripts/ci/windows_profile_mutants.py`.

**⚠ Fabricated answers are product behaviour for a declared Windows guest** (class (c): a value no host query produced; each measured as required, none claims GPU work): the `GFX_POOL_QUERY_SIZE` sizes, `NV_OK` for `GR_CTXSW_PREEMPTION_BIND` and the cross-client `GR_CTXSW_ZCULL_BIND` with nothing bound on the host, the six echoed NV0073 controls, the software-runlist submit `NV_OK` (contents ignored; host-owned scheduling, `OWNER_RULINGS.md` §W reversed) and `IMP_ENABLE` TRUE. They are served only while `active()`.

**What `off` does.** The host stub, the software-runlist link, the memory-list descriptor, the probes, the user-work classification, the kernel-GR tier and the colour path are unreachable by any declaration; a Windows guest is refused by name at its first Windows-only control (expected Code 43, NOT measured).

**Hypotheses, each with its falsifier (state before the run):**
1. *The identity gate keeps Linux unchanged.* Falsified by any Linux arm that passed at the base revision and fails now (`v3_gates.sh` 9/9 with gate 10, `fast_suite.sh` 30/30 twice, `gfx_suite.sh`, `cuda_ladder.sh`, the Linux app matrix, the video/OFA lane), or by a Linux guest's QEMU log showing a `WINDOWS PROFILE` / `FABRICATED answer (Windows profile)` line, `gr_tier=true` or `scheduled_at_birth=true` (both caps pages are derived and logged at realize for every guest, so `caps page derived (sdr=true)` is NOT a falsifier; the page a guest is shown is switched by `sync_caps_page`).
2. *The identity gate is not too tight for Windows.* Falsified by a Windows guest with NO env file that hits Code 43, a missing `WINDOWS_GATE_PASS`, or a host-authored act missing from its log (below).
3. *`windows-support=off` is a real opt-out.* Falsified by any `WINDOWS PROFILE` line or `scheduled_at_birth=true` in a log of a VM started with `windows-support=off` and a Windows guest.
4. *The mirror-space floor per space equals the old per-process floor for Windows.* Falsified by a Windows gate that passed with the env file and fails now at a `VA_BELOW_TWIN_FLOOR` refusal or an Xid 31/32 in the first seconds of the first user channel (the only change is that prewarmed spares are default-start, so the first Windows spaces are built inside the guest's held page-directory reply: look at `rpc_held` and `mirror space=` timings).

### Security posture, plainly (review of PR #438, 2026-11-15)

- The identity is the guest's own fn 1 (`SET_GUEST_SYSTEM_INFO`). It is a compatibility selector (rule D4), **not a security boundary**, and the default is **on**. "A Linux guest never reaches the profile" holds for an **honest** guest only. Any guest, including guest root, can declare Windows 580.88 on a 580.65.06 wire.
- A guest that does reaches, on a default VM, about **fifteen paths that used to need an operator env flag**: user-work Passthrough twins and the USER ring; the 64 KiB-floor mirror spaces; the host `NV50_DEFERRED_API` object; the kernel-GR tier (a host GR context and allowlisted objects with re-authored methods); the copy-engine relay; memory-list SYSRAM descriptors over guest RAM; asynchronous `DISABLE_CHANNELS` with cross-client re-enable; host-owned scheduling at birth; the SDR colour decoder (guest LUT/TMO reads); and the made-up answers listed above.
- **No path into another VM or the host was found.** That is INFERRED from reading the code (per-device planes; async-preempt targets resolve inside this VM's maps; the echoed controls answer with the request's own bytes, bounded by the request; the CE relay needs a reached host fence). It was **not tested**, and the design's own condition for a derived switch ("safe for any declared value") is therefore not proven. A dedicated hostile-guest review of the memory-list descriptor, the GR-tier method re-authoring and the colour decoder as default-reachable code is a follow-up.
- **`windows-support=off` is the hardening** for Linux-only and multi-tenant hosts: no declaration then reaches any of it.
- Narrowing noted: `declares_windows` needs a host-stub cell, which exists only for wire 580.65.06 (Windows 580.88). The 581.51 software-runlist allocation cell is unreachable in production; no measured loss (581.51 on kf3 was already Code 43, `traces/sweep_integrate_20261018/MATRIX.md`). Its unit test injects a synthetic active profile.
- Known follow-ups (not in this PR): one capability object instead of scattered checks; `ChannelPolicy` reading the shared `WindowsProfile` instead of its own copy of the identity (two records that can drift; they are cleared together at a chain rebuild since the review fix); the SDR caps page derived for every guest at realize (a failure now leaves only the base page, logged); reading the colour gate once per frame; prewarming after fn 1 so a Windows VM can use spares.

### Known coverage gap (delta review of PR #438, 2026-11-15)

`windows_profile_mutants.py` reports 70 mutants with no survivor, but that number is weaker than it reads. **9 of the 23 use-site mutants are killed only by the text-matching pins in `crates/kf-qemu/tests/windows_use_sites.rs`, which prove a line exists, not that it works, and 5 more have a single behavioural killer.** The reviewer's own 15 use-site hardwires, spelled to avoid the pins' forbidden strings, mostly survive (13 of 15). The sites with no behavioural coverage, and so the known gap:
- `ChanPlane::birth`: a later re-binding of the plan or of `kernel_gr`/`scheduled`/the slot identity (D1-D3), and the pump's copy-engine relay (D4);
- `MemPlane` construction (what `plane.windows` is: D5, D6) and `HostRm::alloc_vaspace_at` passing its start through (D12, D13);
- `DisplayPlane::build`'s `ColorPath::new` arguments and the `KF3_DISPLAY_SDR_COLOR` read (D8, D9), the display worker's four per-use `sdr()` reads (D7) and the drainer's `sync_caps_page` call (D10);
- **`Device::realize` building the shared profile from the property (D11): a change that makes the device ignore `windows-support=off` would pass every GPU-free test, and the release run does not exercise `off`.**
Follow-ups: (1) behavioural tests for those sites (each a call to a tested function over the real object: a `birth_plan` method used directly, `MemPlane::mirror_start`, one `sdr()` read per frame, `profile_for(cfg)` tested for `off`), with D1-D13 added to the mutants script and pins that assert structure (single binding) rather than presence; (2) a committed fn-1 re-selection test (the reviewer's probe: `ReselectAtFn1(Defaulted)` re-selected to 580.65.06 keeps the declaration); (3) a dedicated hostile-guest review of the default-reachable paths. Also wanted on hardware: a `windows-support=off` run with a Windows guest, so the hardening has evidence.

### Interaction with the untabled-video offer filter (merge of #427, 2026-11-16)

`KF3_WIN_HIDE_UNTABLED_VIDEO` (`kf-qemu/src/rmfacts.rs`, `kf_rm::hostquery::hide_untabled_video`) is **not** part of the Windows profile and is **not** gated on the declared identity: it is a host fact read once at realize, before any guest declaration, default off, and when an operator sets it exactly as `1` it applies to every guest of that VM (Linux, an undeclared guest and a `windows-support=off` VM included). With the variable unset (every launcher) it changes nothing for any guest, whatever `windows-support` says. Keying it on the declaration would need the same re-publish step as the colour caps page (the engine list is served from static info); that is not done and not claimed.
