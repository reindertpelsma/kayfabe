## 1. Owner rulings that apply

- **"Stub what workloads do not need"** (`OWNER_RULINGS.md` §H, 2026-10-02) refined by §S (2026-10-07): a refusal that only blocks a feature workloads do not need may
  be stubbed *as a GPU without the feature answers* (capability absent / not permitted), never `OK` to an action; privileged host-management actions with no
  compute or display effect may be accepted silently; **GPU work that reached hardware is never forged** (§A.3, §S.3). Applied below: a probe that answers
  `NV_OK` to a bind with nothing bound (`KF3_PREEMPT_BIND_PROBE`, `KF3_ZCULL_BIND_PROBE`) is a §S.6 "preempt stays host-owned" stub *only if the owner rules
  so*; otherwise it is a stub hiding a real feature, and the proposal is the host-authored bind on the VM's own twin.
- **Derive, never capture** (`AGENTS.md`, Rules; `OWNER_RULINGS.md` §A.7-8): per-die facts come from unprivileged host controls, per-family facts from
  ogkm-generated tables, only family rows are hand-kept. **All families are first-class.** A captured per-die table is "the defect v3 exists to end".
- **No thread that serves input may stall** (`AGENTS.md`; `THE_CONSTRAINTS.md` §35, 2026-09-17, restated 2026-10-09) and **only BAR0 writes trap**. §S's BAR0-read
  trap (`KF3_BAR0_TRACE`) and §Y's read-trace mode (`KF3_BAR0_READ_TRACE`) are the two *approved, default-off* exceptions.
- **Owner, 2026-10-09 (via the coordinator, binding for this inventory):** (1) a flag needed for correctness is removed and its behaviour hardwired, unless the
  user has a real reason to choose; (2) every flag needed to boot gets a performance analysis; (3) measurement flags are never required to boot — if the
  program only works with one, it is B; nothing that changes guest-visible behaviour lives under `KF3_DIAG_*`.
- **Other rulings the rows lean on:** §U (class 5080 Translated-only; `KF3_DEFERRED_API`, `KF3_WIN_TWIN_DEFAPI_OBJECT`), §V (Windows per-process work as Passthrough;
  `KF3_WIN_USER_CHANNELS_PASSTHROUGH`), §W (`KF3_SW_RUNLIST_HOST_OWNED` "stays off and undecided"), §X (non-stall relay; `KF3_PT_NSI_*`), §Y (BAR0 trace mode),
  §Z on master (host-wide read-only telemetry; `KF3_GSS_NATIVE`), §AA (`KF3_INVALIDATE_CLEAR_OVER_ABSENT`).

## 8. A naming and registry rule

The owner's rule, applied. Three kinds of name and nothing else:

1. **`KF3_<NAME>`: a stable user choice** (config). Same meaning across releases, documented, validated. Today's genuine members: `KF3_PT_NSI_MIN_INTERVAL_US` (§X's pacing knob). Everything else
   currently under a plain `KF3_` name is either B (to be hardwired and deleted), E (deleted) or a control.
2. **`KF3_DIAG_<NAME>`: pure measurement** (trace, snapshot, census, counter, log cap). **Hard rule: nothing under `KF3_DIAG_` changes a reply, a register value, a trap, a
   lock or a thread the guest can observe, other than by the time its own output takes**; any flag that does is B (or `NEGCTL`). Concretely this excludes today's
   `KF3_DIAG_UNMAP_DELAY_MS` (it sleeps the VA thread to change timing: that is a control), `KF3_BAR0_READ_TRACE` and `KF3_MAPLOG` *as implemented* (a vCPU read exit; an `eprintln!` per doorbell) until they
   are re-done off the hot threads, and any "diagnostic" that answers a control (`KF3_ASYNC_PREEMPT_REENABLE_NOACT`, E).
3. **`KF3_NEGCTL_*` / `KF3_INJECT_*`**: positive/negative controls and fault injection, destructive by design, test only, never in a launcher.

Rules that make it hold:

- **One registry** (`kf_util::flags`, a const table: name, kind `CONFIG|DIAG|NEGCTL|INJECT`, parser, default, doc line, owning crate). Every other `std::env::var("KF3_…")` is a CI gate
  failure (a grep gate like the existing claims/unsafe gates). The registry parses uniformly: `"1"` = on, `"0"`/unset = off, anything else is an error at realize with the name quoted
  — never "any value is on" (`KF3_MAPLOG`, `KF3_NO_*`) and never "a typo refuses the boot" for DIAG (it warns and stays off).
- **`KF3_DIAGNOSTICS=1` is a master switch for the *cheap* DIAG set only** — the flags whose output is produced off the vCPU, drainer and act thread or is bounded and lock-free
  (e.g. counters, `KF3_DIAG_TCENSUS`, `KF3_DIAG_PT_STALL_SNAPSHOT` after the `try_lock` fix, the display traces after the vCPU line moves to the worker). The **heavy** tracers that
  trap or log on a vCPU (`KF3_DIAG_BAR0_READ_TRACE`, `KF3_DIAG_BAR0_WINDOW_TRACE`, `KF3_DIAG_DISPLAY_WRITES`, `KF3_DIAG_MAPLOG` until reworked, `KF3_DIAG_DOORBELL_CPL`) are never enabled by the master
  switch; each needs its own explicit name, because they change timing and §Y calls them "an explicit, loudly reported diagnostic exception". A production run has no `KF3_*` set
  and the status line prints `diag=off`; with any DIAG set, realize prints one banner listing every active name (as `DIAGNOSTIC BAR0 TRACE MODE ON` already does).
- **The recorded environment is the whole `KF3_*` environment**, not the launcher's flag list: launchers write `command.json` from `env | grep ^KF3_` (fixes the gap in §3).
- **A measurement flag may not appear in `FLAGS`/`WIN_FLAGS`.** The Windows launchers take `WIN_DIAG=<list>` (default empty) for M names; `windows_broker.sh:282` today hard-codes
  five (`KF3_BAR0_TRACE`, `KF3_MAPLOG`, `KF3_DISPLAY_METHOD_TRACE`, plus `KF3_RPC_TRACE` and `KF3_TCENSUS`).
- A B flag that is *waiting for an owner ruling* (`KF3_SW_RUNLIST_HOST_OWNED`, `KF3_WIN_TWIN_DEFAPI_OBJECT`, `KF3_GFX_POOL_PROBE`, the bind probes) is renamed `KF3_PENDING_<NAME>` with a
  dated entry in the registry and a deletion date: it is neither a diagnostic nor a product setting, and the name says so.

## 10. Performance summary of the flags that boot Windows (rule 2)

- **No B flag adds a BAR0 read trap, a vCPU lock, a vCPU syscall, or a sleep.** Measured/code-read: the B flags act on (a) the drainer inside `Device::gsp` (decode, clone ≤ 1 MiB, ≤ 32 log lines),
  (b) the act thread (host ioctls at birth/bind/evict/preempt), (c) the worker (pump, eventfd writes), (d) the VA thread at prewarm or per mirror space, (e) the display thread.
- **Violations by B flags** (all on non-vCPU threads; none "almost instant" by measurement): `KF3_ASYNC_PREEMPT` (act thread, 183-383 µs synchronous host ioctl, worst case bounded only by the host RM preempt
  timeout); `KF3_TSPACE` (VA thread deaf for 128.6 ms at prewarm, harmless only while no statement can arrive: unmeasured); `KF3_KERNEL_*` and `KF3_WIN_USER_CHANNELS_PASSTHROUGH`
  births (act thread, worst act 5.96 ms measured over the code43 runs). Uncapped guest-reachable logging: `KF3_DEFERRED_API` (2 lines per trigger, `chan.rs:1069, 1085`),
  `KF3_GFX_POOL_PROBE` (1 per query, `gfxpool_probe.rs:45`), `KF3_ASYNC_PREEMPT_REENABLE_NOACT` (E).
- Cleanups the audit found while reading: `KF3_WIN_USER_CHANNELS_PASSTHROUGH` does a `std::env::var` (global env lock) per mirror-space alloc on the VA thread (`mem.rs:2617, 2788`);
  `KF3_SCHEDULE_LATE_JOINERS` records `guest_sched` on the drainer even with the switch off (`chan.rs:2870-2879`); `KF3_RELAY_GET_REFRESH` made `relay_serve` take the relay lock blocking
  (`chan.rs:4995-5004`).
- **The measurement flags in the default Windows launchers are the real performance hazard**, not the B flags: §6.
