STATUS: RESEARCH, 2026-10-19. Lane R1, branch `codex/trap-research-20261019`, based on the measured TSG-mirror revision `0d7ba7438`. GPU- and VM-free work only. No production default, timeout, timer, interrupt policy or KVM registration changed. The optional diagnostic was tested locally but never enabled in a VM.

## Public Linux/RM source, explicitly Linux-only

**CODE READ:** NVIDIA's public [580.159.04 intr_tu102.c](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/580.159.04/src/nvidia/src/kernel/gpu/intr/arch/turing/intr_tu102.c) defines leaf enable/disable, stall masking, W1C vector clearing and pending reads. `_intrDisableStall_TU102` masks RM-owned UVM/client leaves then selected top subtrees; `_intrEnableStall_TU102` restores masks, excluding nonstall top categories where appropriate. Cached masks avoid some reads in hot paths; state-load/debug paths explicitly read enable registers. `intrClearLeafVector_TU102` writes one selected bit; `intrIsVectorPending_TU102` reads LEAF. Public `dev_vm.h` family layouts agree with the tested offsets and 8/16 leaf distinction. The oracle was initially derived independently from public 580.65.06 definitions; the corresponding 580.159.04 definitions/flow were then checked, without closed-driver disassembly.

**CODE READ:** [intr.c](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/580.159.04/src/nvidia/src/kernel/gpu/intr/intr.c) services pending engines and DPC work, with repeat/pending checks; [os_sanity.c](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/580.159.04/src/nvidia/src/kernel/os/os_sanity.c) clears/enables/triggers the loopback and waits for its ISR. **INFERRED:** a latched event during a mask must remain pending and become deliverable on unmask; otherwise no further edge is guaranteed to restart service. This is the CpuIntr contract under test, not a measured physical GPU reassertion experiment. Linux/RM source is not evidence of the closed Windows driver's implementation; Windows claims above come only from register traffic.

## KVM/QEMU mechanics: what (c) actually buys

**CODE READ:** upstream [Linux v7.0 coalesced_mmio.c](https://github.com/torvalds/linux/blob/v7.0/virt/kvm/coalesced_mmio.c) registers address/length zones on the MMIO bus; write handling appends address, size, value and PIO tag under the VM's `ring_lock`. A full ring falls back to ordinary userspace MMIO. One VM owns the shared ring. With a 4-KiB page, 8-byte header and 24-byte entries there are 170 slots, of which 169 are usable. Entries carry at most eight data bytes; reads are not coalesced. Producer serialization gives append order, not a total wall-clock order for simultaneous vCPUs. Setup allocates and takes `slots_lock`; it must remain off the vCPU. `KVM_CAP_COALESCED_MMIO` supplies the mapping-page offset; zone registration is an ioctl/structure, not a separate `KVM_CAP_*_ZONE` interface. See [KVM API](https://docs.kernel.org/virt/kvm/api.html) and [UAPI layout](https://github.com/torvalds/linux/blob/v7.0/include/uapi/linux/kvm.h).

**CODE READ:** the repository contains the kf3 overlay, not the entire QEMU core. R1 checked full local QEMU and then the actual retained host **QEMU 10.2.4** source; hashes are in [HOST_FACTS.json](../../traces/trap_reduction_20261018/HOST_FACTS.json). Host `accel/kvm/kvm-all.c:2882-2912` replays via `cpu_physical_memory_write`/`address_space_write` and advances `first`, guarded by a plain shared `coalesced_flush_in_progress` bool. `system/physmem.c:3196-3208` acquires BQL only if the target region is not lockless, then flushes if its `flush_coalesced_mmio` flag is set. `memory_region_add_coalescing` sets that flag. Core references: [kvm-all.c](https://github.com/qemu/qemu/blob/v10.2.4/accel/kvm/kvm-all.c), [physmem.c](https://github.com/qemu/qemu/blob/v10.2.4/system/physmem.c), [memory.c](https://github.com/qemu/qemu/blob/v10.2.4/system/memory.c).

**CODE READ:** this is **not an unconditional flush on every KVM exit or every unrelated MMIO**. Flagged-region accesses, explicit flushes and memory transactions can drain it. The vCPU can be the drainer on MMIO dispatch. The current kf3 write regions are lockless: do not claim they already take BQL, or that every flush inherently starts under it. But a VM-wide flush can dispatch another device's BQL-taking callbacks; a worker calling it does not move other callers off-vCPU. Its plain guard is not a concurrent worker/vCPU synchronization protocol. Giving it a mutex would violate the rule. An uncontrolled `while first!=last` drain may also chase newly appended entries. No bounded, exclusively worker-owned consumer with coherent synchronous readback has been established.

**CODE READ:** [Linux v7.0 eventfd.c](https://github.com/torvalds/linux/blob/v7.0/virt/kvm/eventfd.c) accepts exact address/width plus optional 1/2/4/8-byte DATAMATCH. Length zero permits an address-only shortcut on `KVM_FAST_MMIO_BUS`; **length zero cannot combine with DATAMATCH**. The existing 4-byte per-token doorbells therefore use normal KVM MMIO emulation/bus dispatch, not that zero-length fast bus. Both normally avoid userspace returns, not hardware exits. Their eventfd counter does not transport arbitrary mask/W1C values or synchronously update the read shadow. No x86 hardware facility identified here implements an arbitrary RAM-backed SET/CLEAR/W1C device without executing an emulation handler. Direct hardware/PV doorbells are a separate guest/helper tier, not a stock Windows solution.

**CODE READ discrepancy / STOP on design changes:** the old Notifier documentation says a signal acquires nothing a peer can hold; upstream [fs/eventfd.c](https://github.com/torvalds/linux/blob/v7.0/fs/eventfd.c) explicitly takes its waitqueue spinlock. R1 changes neither interpretation nor design. Generic coalescing, worker-wait fixes, mitigation relaxation and production fast-path enablement stop at this boundary for owner review.

## Doorbell path and ledger

**CODE READ:** existing QOM property `doorbell-ioeventfd=on` (default false), max 256 placements. C `kf3_ioeventfd` makes direct KVM_IOEVENTFD calls with exact token match so refusal preserves the trap fallback. Register drainer consumes counters then calls the SAME trap doorbell arm: native passthrough writes the host doorbell; mediated/translated work uses existing rung bitmap/worker flow. A counter drained before act catches later writes on the next readiness wake. Birth/free act thread registers/removes; removal drains before acknowledging/freeing the twin. See `qemu/hw/misc/kf3/kf3.c:790`, `crates/kf-qemu/src/device.rs` Sink/drainer, `crates/kf-chan/src/dbfast.rs:785-850`, and [existing design](V3_DOORBELL_IOEVENTFD.md).

**CODE READ:** passthrough ledger `rung` and `forwarded` include trap and fast transports; `trap` counts trapped rings, `fast` counts eventfd stores, `fast_wakes` counts consumer deliveries, so their ratio measures incidental coalescing. `fast_absorbed`, `fast_failed`, `fast_sites`, `fast_refused` account for outcomes/placement. Mediated ledger fields do not all have the same meaning as raw host MMIO ring counts. No GP_PUT polling is introduced. P1's traced doorbells are observed KVM MMIO writes, so those observed stores were on the trapped path. Earlier 29.4 us is first-to-last timing for three writes, not three independent measured per-exit latencies. An ioeventfd A/B must measure wake-to-consumption too, not only vCPU return.

## Per-exit cost model and host mitigations

**CODE READ / INFERRED:** for one userspace MMIO store:

```
T_user = guest instruction + hardware exit/entry
       + KVM fault/decode/emulation/bus miss + kernel/userspace transitions
       + mitigation barriers + QEMU return from KVM_RUN
       + flatview/RCU lookup + MMIO dispatch + atomic apply/shadow
       + optional irqfd signal + next KVM_RUN preparation/ioctl
       + scheduling and measurement perturbation
T_coalesced = hardware exit/entry + KVM emulation + ring append/spin synchronization
              + amortized eventual consumer cost/fallback
T_ioeventfd = hardware exit/entry + emulation/bus match + eventfd signal/wake
```

**CODE READ:** length-zero fast-MMIO can skip data-dependent decoding work; it cannot identify individual token values. In-kernel handling that reenters without userspace also avoids mitigations triggered specifically by returning to userspace. None of these formulas establishes a host-specific 1–2 us kernel path or 9–10 us userspace path.

**CODE READ / INFERRED (DERIVED):** the submit-latency README's 9–10 us/write is a spacing/chain attribution, not a measured isolated MMIO round trip. Its `hops.py` records kvm_mmio timestamps, counts writes and takes first-to-last ISR time; it has no matched hardware-exit→QEMU→reentry sample for each write. The stated 233.7 us/22 writes is 10.62 us/write (or 11.13 us per one of the 21 inter-write intervals), and includes guest ISR/DPC gaps. R1's newer whole-capture consecutive same-thread interrupt-write spacing has median **11.15 us**, n=68,369, min 7.03/max 5,095.256; still not isolated exit time. The handler's atomic/shadow work is plausibly sub-microsecond but is not measured here. `deliver(Message)` can add a syscall. ## AVIC and patched-host tier

**CODE READ / MEASURED:** owner launch profile includes hv_relaxed, hv_vapic, hv_spinlocks=0x1fff, hv_vpindex, hv_runtime, hv_time, hv_synic, hv_stimer, hv_tlbflush, hv_ipi and hv_frequencies; no explicit hv-avic. `hv-vapic` already supports an exitless EOI path. [QEMU Hyper-V docs](https://www.qemu.org/docs/master/system/i386/hyperv.html) describe hv-avic as allowing SynIC with hardware acceleration. [Linux hyperv.c](https://github.com/torvalds/linux/blob/v7.0/arch/x86/kvm/hyperv.c) inhibits APICv when SynIC AutoEOI is used; [avic.c](https://github.com/torvalds/linux/blob/v7.0/arch/x86/kvm/svm/avic.c) has further runtime inhibits. Module Y and a CPU flag do not prove active VM delivery. AMD AVIC/x2AVIC is the relevant architecture, not Intel posted-interrupt terminology; a host GPU's real IRQ is still handled by the host RM before the guest irqfd path. No direct assignment of the GPU IRQ to this VM is implied.

**MEASURED / CODE READ:** the exact host `Module.symvers` contains no `kvm_io_bus_register_dev` export. Upstream [kvm_main.c](https://github.com/torvalds/linux/blob/v7.0/virt/kvm/kvm_main.c) defines it without exporting it; setup requires slots_lock and allocation, teardown an SRCU grace period. Some other helpers are exported or restricted to KVM modules; they do not provide a supported external attach API. A normal out-of-tree module cannot simply register this interrupt page with stock host KVM. No kallsyms/kprobe or private-pointer workaround is proposed.

**INFERRED design sketch:** optional patched-host KVM device type, attached to the VM fd by an authenticated owner at setup, per-VM state/read-only guest page, validated BAR relocation, pre-pinned kernel access without page faults, bounded exact SET/CLEAR/W1C/TRIGGER operations, atomic pending/enables and a reviewed loss-free IRQ handoff. Reset, multi-vCPU races, overlapping write widths, hostile offsets, route lifetime and teardown all require model/negative tests. No host GPU capability belongs in that callback. A complete lock-free injection/wakeup protocol is not supplied here. This is a host-kernel tier, separate from stock QEMU and from any optional guest helper. No private memory file was read; the publicly described tier is sufficient to state feasibility.
