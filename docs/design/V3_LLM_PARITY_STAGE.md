# The `llm_parity` payload stage: one LLM on the host and in the Linux guest

**STATUS: LIVE as code, 2026-11-15; NEVER RUN ON A BOX, and every input pin is UNSET, so the stage refuses today (`unpinned`).** Built and GPU-free tested: the stage, its two arms, the share arguments, the verdict and the record. Everything about a real ollama, a real virtiofsd, the kf3 QEMU build, the guest kernel and the GPU is **UNVERIFIED** until the first-run checklist (section 8) has been walked on a box. The stage is manual-only: it runs only when named by `--only llm_parity`, in the large tier, and it is not in any default plan. The Worker's `llm_parity` stage slot stays DESIGN-ONLY (`ci/vast-broker/defaults.json` is untouched). Depends on the box downloader (draft PR #425, `scripts/ci/box_downloader.py`).

Labels: **OWNER RULING** binds. **MEASURED** names what was run and where. **INFERRED** is reasoning from measured or read facts. **UNVERIFIED** is a fact about a system nobody has checked. **CODE READ** is read, not run.

## 1. What the owner asked for

- **OWNER RULING 2026-11-15 (OWNER_RULINGS section AS item 8):** the LLM may run on the host and in the guest. Fetch the **model and ollama once**, through the downloader, and share them with the Linux guest as one read-only directory instead of downloading again in the guest. Parity is at least 90 percent of native, preferably 95. **Parity is reported and is never a release-gate pass/fail threshold.**
- **OWNER CORRECTION, same day (relayed by the coordinator):** the primary share is **virtio-fs** (`virtiofsd` plus `vhost-user-fs-pci`), faster than 9p; **9p (virtfs) is only a documented fallback** when virtio-fs is unavailable. Do not enable DAX unless it is shown compatible.

## 2. What PASS means

The stage's PASS is exactly: both arms ran; every timed run of both arms produced the **same text** (and the same token-id hash when ollama returned token ids in all of them, and the same token count); both arms held the **whole model in GPU memory** (`/api/ps`: `size_vram == size > 0`); both inputs match their pins on both arms; both arms ran the same ollama version, the pinned one; the timings are usable; the ratio is recorded. The payload adds "no Xid beyond the allow-list": every stage, this one too, runs under the payload's Xid watcher (`make_stage` -> `stage_grade`).

The ratio is **data**. It is guest median decode tok/s over host median decode tok/s (medians of the timed runs, computed by the stage from raw token counts and nanoseconds, never taken from an arm). The record carries `meets_min` (>= 0.90), `meets_preferred` (>= 0.95) and `gate: false`; nothing reads them: a guest at 10 percent of native is a PASS with `meets_min: false`, and tests pin that (`test_the_ratio_value_never_changes_the_verdict`, `test_rows_never_read_the_ratio_value`, mutant `verdict-reads-the-ratio`). A zero, negative, NaN or infinite timing is not a usable timing: the ratio is `INVALID` (null) and the stage FAILs with `timing_invalid`, because "the ratio is recorded" would be false.

**Tolerance: none.** Agreement is exact: one distinct text hash across all timed runs of both arms. There is no looser mode in the code. Both arms run the same ollama binary on the same GPU with greedy decoding, so exact equality is the expectation. If the first box run shows drift, the tolerance is defined from the observed drift by a reviewed change, not guessed here.

**Trust.** The guest arm's output is untrusted data from the machine under test. It is size-bounded, strictly parsed (exact keys, no NaN, no duplicate keys, bounded integers, the label must match), and only counted. A guest that lies can forge a ratio or an agreement; nothing here defends against that and no other guest lane does either. The host arm is trusted.

## 3. The pins (what is unpinned, and why)

`scripts/ci/llm_parity_pins.json` (schema `kayfabe.llm-parity-pins/1`) holds three items. **All three hashes, all three sizes, all three source lists and the ollama version are UNSET.** An item is pinned only when `sha256` and `size` are both real values; the stage refuses with the named reason `unpinned` (listing the item names) before it fetches or runs anything, in every path (`check` exits 3). The downloader manifest (`kayfabe.download-manifest/1`) is generated from the pins and validated by the downloader's own parser; nothing is ever accepted unpinned, and a pin is set in a reviewed commit with its sources, never by a run.

| item | what | the earlier traces used | pin state |
|---|---|---|---|
| `model` | one GGUF of Qwen2-0.5B-Instruct, fp16 | **the same model**, as `Qwen/Qwen2-0.5B-Instruct`, HF snapshot `c540970f9e29518b1d8f06ab8b24cba66ad77b6d` (`traces/llm_parity/vc_bare_53c2bc20.out`), run through torch 2.6.0 and transformers, not ollama | UNSET |
| `ollama` | the ollama Linux amd64 release tarball (`.tgz`), `bin/ollama` plus `lib/ollama` | **nothing: no earlier trace ran ollama**, so the repository has no ollama version or hash anywhere (`grep -ri ollama` finds only the software wishlist and a report-test fixture) | UNSET (`ollama_version` too) |
| `virtiofsd` | the Rust virtiofsd as one executable, for the virtio-fs transport only | nothing | UNSET |

Why the model is "the same model, not the same file": the traces' snapshot is a safetensors repository, which ollama cannot load. The pin is one GGUF of that model (candidate, UNVERIFIED: `Qwen/Qwen2-0.5B-Instruct-GGUF`, `qwen2-0_5b-instruct-fp16.gguf`). Its tokens will not necessarily equal the torch runs' tokens, and this stage compares host with guest, never with the torch traces. The earlier ratio (guest 0.45 of bare metal decode, `traces/llm_parity/vh_amd/summary.md`) came from torch eager decode and is a different workload.

virtiofsd availability, MEASURED 2026-11-15 on the development machine (Ubuntu 26.04): `apt-cache policy virtiofsd` offers 1.13.2-6ubuntu0.1 (a Rust build, `.deb` sha256 `724d4e3d605d0319f33f164d9469f2c4a3bf46bad29d98b0f71ae7aa9a9f6025`, 1146208 bytes; the binary needs glibc 2.39 and libseccomp2, libcap-ng0). **That build cannot run on the Vast box**: the box image is "Ubuntu 22.04 VM" (`scripts/bench/box/README.md`, glibc 2.35), and INFERRED (no 22.04 archive was checked) that 22.04 has no Rust `virtiofsd` package, only the C virtiofsd inside QEMU 6.2's package, which is root-only. So the stage fetches a pinned virtiofsd through the downloader, as a build that runs on glibc 2.35 (a static build). The deb above is recorded as a measurement, not a pin.

## 4. The two arms: one file

`scripts/ci/llm_parity_arm.py` runs on the host (`python3 -I llm_parity_arm.py`) and is sent over ssh to the guest (`python3 -I -` on stdin). One file, because two copies drift in prompt, token count and what the timer encloses (`scripts/bench/provision_host_llm.sh` records a 2x error from exactly that). It:

1. reads the model and the tarball once, timed, hashing both and printing `KF_LLM_SHARE_READ label= file= bytes= secs= MBps=` (**the throughput check**: in the guest this is the virtio-fs read of the model);
2. unpacks the tarball with a member filter (regular files, directories and in-tree relative symlinks only; no absolute name, no `..`, no hard link, device or fifo; size and count caps; the work directory must be new);
3. refuses with `port_busy` if something already answers on 127.0.0.1:PORT (it would measure somebody else's server);
4. starts `bin/ollama serve` with an allow-listed environment (own HOME and model directory, `OLLAMA_HOST=127.0.0.1:PORT`; the caller's credentials never reach it), imports the model with `ollama create` from a Modelfile, runs one warm-up and 3 timed `/api/generate` calls (greedy: temperature 0, top_k 1, seed 1, 128 tokens, num_ctx 2048, one fixed prompt), reads `/api/ps`, stops the server (process group) in a `finally`;
5. prints one `KF_LLM_ARM_RESULT {json}` line with raw counts and nanoseconds. `create_secs` (model import) and `load_ms` (the warm-up's `load_duration`) are in the record, so the model load time is visible per arm.

Order: the host arm runs first and must leave no `ollama` process (`host_server_left_running` otherwise), then the guest boots; they never share the GPU concurrently.

## 5. Sharing the model and ollama with the guest

### 5.1 The share

The stage builds `<work>/share/` holding **only** `model.gguf` and `ollama.tgz`, as regular files mode 0444 in a directory mode 0555 (hard links to the downloaded files, copies when the filesystem refuses). The downloader's state directory and the virtiofsd binary are never in it. The host arm reads its inputs from the same directory, so its hashes also verify the share.

### 5.2 virtio-fs (primary): `scripts/ci/llm_parity.py`, `virtiofsd_argv` and `qemu_share_args`

```
setpriv --reuid 65534 --regid 65534 --clear-groups --inh-caps=-all --ambient-caps=-all --bounding-set=-all --no-new-privs \
  virtiofsd --socket-path=<work>/vfs/kfllm.sock --shared-dir=<work>/share --readonly --sandbox none --cache always --rlimit-nofile 0 --log-level warn
-chardev socket,id=kfllmc,path=<work>/vfs/kfllm.sock -device vhost-user-fs-pci,chardev=kfllmc,tag=kfllm
```

The QEMU arguments go after `--` to `boot_capture.sh`, which hands them to `boot_nvkvm.sh` (it appends `"$@"` after its own device arguments). The daemon is started by the stage before the boot (QEMU connects at realize) and stopped in a `finally`. The socket directory is mode 0700 and owned by the daemon's uid; QEMU runs as root on the box and connects.

Findings the correction asked for:

1. **virtiofsd rootless: MEASURED 2026-11-15** (virtiofsd 1.13.2, Ubuntu 26.04 dev machine, run as uid 65534 through `setpriv` with every capability set emptied and `no_new_privs`): `--sandbox none` starts and listens, and a stock QEMU 10.2.1 connected to it ("Client connected, servicing requests"). `--sandbox namespace` was **refused** on the same machine (`Error entering sandbox: CleanMount ... Permission denied`, with and without the capability drops; the cause was not established; `kernel.apparmor_restrict_unprivileged_userns = 1` here). `--sandbox chroot` is root-only by the daemon's own message. So the stage uses `none`. What `none` costs: no chroot or mount namespace around the daemon. INFERRED from how virtiofsd looks names up (one component at a time, relative to a directory it already holds) that a symlink in the share cannot make the daemon open a host path outside it, and the share holds only two regular files; the daemon's uid can read only what that uid can read. **UNVERIFIED on a Vast box** (nested KVM guest container: whether `setpriv`, the uid switch and the unix socket behave the same). `--cache always` and `--rlimit-nofile 0` are in the argument list but were not part of the timed run (the measured one used `--cache auto` and the default rlimit): they are on the first-run checklist.
2. **Guest kernel: UNVERIFIED.** No guest image exists on the machine this was written on. The fat guest is the Ubuntu 24.04 cloud image with the stock `linux-generic` kernel (`provision_guest_llm.sh` pins it); my recollection, not a check, is that `CONFIG_VIRTIO_FS` and `CONFIG_FUSE_FS` are modules there (`virtiofs`, `fuse`). MEASURED only on the dev host's kernel (6.x, Ubuntu 26.04): `VIRTIO_FS=m`, `FUSE_FS=y`, `9P_FS=m`, `NET_9P_VIRTIO=m`. The guest hook mounts with `mount -t virtiofs -o ro kfllm /mnt/kf-llm`, then proves `findmnt` says `virtiofs` with the `ro` option and that a write probe fails; any other result is `guest_mount`. **The thin guest (`scripts/fastguest/`) cannot run this stage at all**: it borrows the host kernel's NVIDIA modules only, has no `virtiofs`/`fuse` modules in its load order, no network, no Python and no ollama. This stage is fat-guest only.
3. **kf3 and RAM that vhost-user-fs might pin: CODE READ plus one MEASUREMENT.** `kf3_dev_realize` (`qemu/hw/misc/kf3/kf3.c`, around lines 1605-1631) calls `ram_block_discard_require(true)` and refuses when it fails; the comment lists what disables RAM discard: VFIO (legacy and iommufd), vfio-user, `nvme://`, libblkio drivers that may pin memory, vhost-vdpa (noted as never the hazard), SEV and COLO. vhost-user is not on that list. In QEMU 10.2 `ram_block_discard_require` fails if `ram_block_discard_disabled_cnt` or the uncoordinated-disable count is non-zero (`system/physmem.c`, read). MEASURED: on stock QEMU 10.2.1 a VM with `memory-backend-memfd,share=on`, `vhost-user-fs-pci` (connected to a running virtiofsd), `virtio-mem-pci` and `virtio-balloon-pci` realized without error; `virtio-mem` calls `ram_block_coordinated_discard_require`, which fails when any device has called the full `ram_block_discard_disable(true)`, so `vhost-user-fs-pci` does not call that. **Not excluded by that test:** the *uncoordinated* disable variant. The source of `hw/virtio/vhost-user*.c` is not in the partial QEMU tree available here, so that is INFERRED from the kf3 comment's list and not read. First-run check: boot kf3 with the share arguments; a refusal would print `kf3: RAM discard is already disabled by something that pins guest RAM ...` or `Cannot set discarding of RAM broken`, in either device order. Guest RAM must be shared memory (`memory-backend-memfd,share=on`); `boot_nvkvm.sh` already sets that for kf3 (`NVKVM_RAM_BACKEND=memfd`), which is also what vhost-user-fs needs (MEASURED: connected with exactly that backend).
4. **DAX is not enabled.** No `cache-size` property is ever emitted (a test forbids `cache-size`, `dax` and every writable-mode word in all argument lists), so no host file is mapped into a guest-visible window; DAX would add a host-memory mapping region next to kf3's own BAR windows and nobody has shown it compatible.
5. **The kf3 QEMU build has neither device today.** `scripts/bench/build_kf3.sh` configures with `--without-default-features`; in QEMU 10.2.4 `meson.build` `have_vhost_user` comes from the `vhost_user` feature option (default `auto`), which that flag disables, and `CONFIG_VHOST_USER_FS` needs it. INFERRED from `meson.build` and `meson_options.txt` (the rest of the tree is not here): the build needs `--enable-vhost-user` (no extra library) for `vhost-user-fs-pci`, and `--enable-virtfs` (needs `libattr1-dev` and `libcap-ng-dev`) for `virtio-9p-pci`. Changing the configure line changes the build's identity and forces one rebuild of every build directory (the script says so itself). **This PR does not touch `build_kf3.sh`.** The stage detects the situation: it asks the kf3 binary for `-device help` and refuses with `no_share_transport` when neither device exists, and `transport_unavailable` when a named transport's device is missing. Until a separate change adds the flag, **the stage cannot boot a guest with a share**, and the first run must start with that change.

Hostile-argument handling: every path that reaches a QEMU option or the daemon's argument list passes `safe_path`: absolute, alphabet `A-Za-z0-9._@+/-` only (no comma, which is QEMU's option separator, no space, `=`, quote, glob, control character or non-ASCII), no `.`, `..` or empty segment, no trailing slash, at most 4000 characters; a share must also be canonical (no symlink in the path), a directory, and not group- or world-writable; the socket path is at most 100 bytes (`sun_path`). The tag is `[A-Za-z0-9_]{1,31}`. The daemon's uid must be an integer in 1..2^31-2 (never root, never a bool). Arguments are built as lists and never go through a shell; the only shell line is the guest mount command, built from a fixed mount point and the validated tag with `shlex.quote`. The work directory's ancestors must be searchable by the daemon's uid (`share_not_traversable`).

### 5.3 9p (fallback only)

`-fsdev local,id=kfllm9p,path=<share>,security_model=none,readonly=on -device virtio-9p-pci,fsdev=kfllm9p,mount_tag=kfllm`; the guest mounts `-t 9p -o trans=virtio,version=9p2000.L,ro,msize=1048576`. `--transport auto` (the default) picks virtio-fs when the QEMU binary has `vhost-user-fs-pci`, else 9p when it has `virtio-9p-pci`, else refuses. A named transport is never silently replaced by the other. The result record says which one ran, and the 9p path needs no virtiofsd pin.

## 8. First-run checklist (nothing below has been done)

0. **Pins first.** Choose and review: the ollama version and its `.tgz` (confirm the release asset is a `.tgz`; if the project only ships another archive format, the arm needs a decompressor), the GGUF (size, sha256, a source that survives), the virtiofsd static build. Fill `llm_parity_pins.json` (hashes, sizes, `sources`, `ollama_version`) in a reviewed commit. Confirm the pinned ollama build supports the box GPU's compute capability (`lib/ollama` ships its own CUDA runtime; the node needs the NVIDIA driver's `libcuda`, in the guest too).
1. **QEMU build.** Land `--enable-vhost-user` (and, for the fallback, `--enable-virtfs` with `libattr1-dev`, `libcap-ng-dev`) in `build_kf3.sh` and rebuild; confirm `qemu-system-x86_64 -device help | grep -E 'vhost-user-fs-pci|virtio-9p-pci'`.
2. **virtiofsd startup.** On the box: the pinned binary runs on glibc 2.35 (`ldd`), starts as uid 65534 under the `setpriv` line above, creates its socket, and QEMU connects (`Client connected, servicing requests` in `<work>/virtiofsd.log`); `--cache always` and `--rlimit-nofile 0` are accepted. If the box refuses `setpriv --bounding-set` or the uid switch, say which.
3. **kf3 and the share.** The boot realizes `kf3-gpu` together with `vhost-user-fs-pci` (section 5.2, item 3): no `RAM discard is already disabled` refusal.
4. **Guest kernel and mount.** In the guest: `modprobe virtiofs` works (`CONFIG_VIRTIO_FS`, `CONFIG_FUSE_FS`), `findmnt /mnt/kf-llm` shows `virtiofs ro`, the write probe fails. The first `KF_LLM_SHARE_MOUNT` and `KF_LLM_SHARE_READ label=guest file=model` lines are the first reading of virtio-fs throughput here; compare with the host arm's line for the same file (the host's read is from a warm page cache, so it is an upper bound, not a like-for-like).
5. **Guest resources.** Guest disk: the stage needs 12 GiB free under `/var/tmp` (the tarball unpacks there, and `ollama create` copies the model); the guest RAM is 8192 MiB, 4 vCPUs (as the earlier LLM lane). GPU memory: the fp16 0.5B model is about 1 GB plus context, far below any box card, and `fb-mb` follows the card as `boot_nvkvm.sh` computes it; the stage requires full GPU residency, so confirm `/api/ps` reports `size_vram == size` in the guest.
6. **Ollama in the guest.** Which libraries it needs beyond `lib/ollama` (the arm sets `LD_LIBRARY_PATH` only if the caller had one); whether the first CUDA call under kf3 works with ollama's bundled runtime (the earlier torch lane needed the guest driver's `libcuda` and a persistence-mode note: `LP_GUEST_PM`); whether `ollama serve` holding the adapter open for the whole run avoids the per-process adapter teardown the torch lane recorded.
7. **Time.** Record `create_secs`, `load_ms`, the share reads, the three timed runs per arm and the whole stage's wall time; `LLM_PARITY_MIN_REMAINING_MS` (60 minutes) is a guess until then. Downloads: the downloader's default cap is 125 MB/s, also a design value.
8. **Result.** One `KF_LLM_PARITY_RESULT` line with both raw timings and the ratio. Only a green run with the rows above justifies flipping `LLM_PARITY_IN_LARGE` (section 6).
