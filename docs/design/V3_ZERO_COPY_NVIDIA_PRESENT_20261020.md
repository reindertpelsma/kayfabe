# V3 zero-copy presentation when the host desktop renders on the NVIDIA GPU — what exists, what is missing, what to measure

**STATUS: RESEARCH, 2026-10-20 (file dated by the coordinator; written 2026-10-19, GPU-free, dev box, branch `claude/zero-copy-tier-20261020` from `integration/prod-candidate-5-20261018` `f8f9d1a5f`).** Nothing was run on a GPU or on the trusted host; no host file was written.
Labels: **MEASURED** = read from a committed log or trace (path given), **CODE READ** = read in the tree at this revision, **DOC READ** = a repo design doc or a public document (URL given), **INFERRED** = reasoning, never evidence.
Every proposal states its falsifier. Nothing here is derived from reverse engineering of closed binaries; sources are kayfabe's code, ogkm/open-gpu-kernel-modules (public GitHub), mutter, and public NVIDIA/CUDA documentation.

## 0. The finding that reframes the request

**The zero-CPU-copy tier for "compositor on the same NVIDIA GPU" is already built, and was MEASURED working on a GNOME Wayland session on this host's RTX 4070 on 2026-10-08.** It is `V3_DISPLAY.md` §8.11 "the GPU-copy rung" (rung 0, `OWNER_RULINGS.md` §L): kayfabe allocates its own VRAM frame objects, exports each as a dma-buf through the GPU's nvidia-drm render node, and per frame a CUDA kernel packs the composed frame into one of them in NVIDIA block-linear layout. No byte crosses PCIe and nothing of the guest's is exported. What the owner is asking for as "zero copy" is therefore, in kayfabe's vocabulary, rung 0 plus (optionally) removing its one on-GPU pass. The current AMD-compositor setup uses rung 1 (a LINEAR system-memory udmabuf filled by a copy-engine DMA), which is the *other* GPU's rung by design (`EV_DEVICE`).

Owner ruling, binding (`docs/OWNER_RULINGS.md:399-410`, §L): *"exact zero copy isn't needed though, what we do need is that we can avoid a GPU-CPU copy ... a shared RM object lets the guest change the bytes underneath."* So the guest's own scanout surface is never exported; a GPU-to-GPU copy into a kayfabe-owned object is the sanctioned design. Everything below stays inside that ruling unless stated.

## 1. How the display worker gets a frame to the broker today

CODE READ (`crates/kf-qemu/src/display.rs`, `crates/kf-cuda/src/display.rs`), per tick, on the display worker thread (never a vCPU):

1. **Compose** (CUDA kernels on the display stream): the guest's scanout surfaces (store VRAM, read through the store-bounded VAs), windows, blending, scaling, the grab-mode cursor, into a **VRAM staging frame** (`cuMemAlloc`, `compose_begin` `kf-cuda/src/display.rs:829-850`). Size `w*h*4`: 1920x1080 = 8,294,400 B; 3840x2160 = 33,177,600 B.
2. Then one or both of (`display.rs:5560-5640`, `kf_broker::gpucopy::plan` `crates/kf-broker/src/gpucopy.rs`):
   * **pack (rung 0)** `compose_to_slot` (`kf-cuda/src/display.rs:1356-1397`): a *kernel* (one warp per GOB, `cuda/display/kf_bl_pack.cu`) writes staging -> a kayfabe-owned VRAM slot, block-linear. VRAM -> VRAM, SM work, not the copy engine, not PCIe. Slots: 5 x 10 MiB (`SLOT_CLASS0`, covers 1080p), one growth to 36 MiB (`SLOT_MAX`, covers 4K: `crates/kf-disp/src/vramslot.rs:92-98`).
   * **D2H (rungs 1/1b/F_SHM, console)** `compose_to_host` (`kf-cuda/src/display.rs:1330-1349`): `cuMemcpyDtoHAsync` staging -> a sealed memfd that was `cuMemHostRegister`-ed (`display.rs:757-790`) and also wrapped as a udmabuf. This is a copy-engine DMA across PCIe into system memory; **the CPU never touches the bytes** (`OWNER_RULINGS.md` §M, "the CPU never copies a frame"). 5 backings x 7.9 MiB at 1080p (`V3_DISPLAY.md` §8.2).
   * D2H is *not* done when rung 0 carries the frame, unless the console asked (`plan`, `gpucopy.rs`: "never only because the broker is active while it takes the GPU copy").
3. A completion event signals; only then the relay ATTACHes/COMMITs the slot's fd to the broker (`Phase::Send`, `display.rs:~5640-5660`). So kayfabe does not use GPU fences toward the compositor: the frame is complete before the compositor sees it (CODE READ); RELEASE means "no longer reading", not GPU-idle, so an `EXPORT_SYNC_FILE` check guards slot reuse (`V3_DISPLAY.md` §8.11 "Slots and reuse").

**Measured copy times (MEASURED; the only ones in the repo; no 1080p/4K broker-specific number exists):** counter `scanout_avg_us`/`scanout_max_us` = queue-to-observed-completion of one scanout (compose + pack or D2H, one number, `display.rs:933-936`, printed `device.rs:2960-2990`):
* pack, 1024x695, RTX 3060, X11 broker: avg 341 us, max 4124 us over 3465 scanouts (`traces/v3_display/broker_20261003/brkA/run_brkA_qemu_excerpt.log`, `scanout_pack=3464`); slot variant E1s0: 321 us (`brkE1s0`).
* D2H (shm / LINEAR rung), same guest size: avg 503 us (`brkB`, 2979 scanouts), 551 us (`brkC`).
* Linux guest, RTX 3060, display-SW run: avg ~1.1 ms, max 2-18 ms (`traces/v3_display/dispsw_20261003/...`; guest resolution NOT verified from the log; do not read it as 1080p).
Therefore: the numbers are queue-to-completion latencies at a small mode, they do not separate compose from copy, and they say nothing about 4K. INFERRED upper bound for the pack pass alone at 4K: read 33 MB + write 33 MB at the card's 504 GB/s (public spec) is ~0.13 ms, i.e. under 1% of a 16.7 ms tick; falsified by a per-stage CUDA-event timing (Sec. 5).

## 2. What a compositor on NVIDIA imports via `zwp_linux_dmabuf_v1`

* **mutter builds its advertised table from EGL** (DOC READ, mutter `src/wayland/meta-wayland-dma-buf.c`, https://gitlab.gnome.org/GNOME/mutter/-/raw/main/src/wayland/meta-wayland-dma-buf.c): `init_formats()` -> `cogl_renderer_egl_query_dma_buf_formats/modifiers` (i.e. `eglQueryDmaBufFormats/ModifiersEXT` of the renderer GPU), main device = the EGL device's render node, a render tranche plus (per surface with a scanout candidate) a scanout tranche filtered by the KMS plane's modifiers. Import = `eglCreateImage(EGL_LINUX_DMA_BUF_EXT)` per plane (`cogl_renderer_egl_create_dmabuf_image`), **no CPU-mapped fallback**; a failure in `create_immed` is a *fatal protocol error* (`ZWP_LINUX_BUFFER_PARAMS_V1_ERROR_INVALID_WL_BUFFER`, "failed to import supplied dmabufs: ...").
* **What NVIDIA's EGL accepts: MEASURED on this host, 2026-10-08, GNOME Wayland on the RTX 4070, host 595.91.07** (`traces/v3_display/broker_interactive_20261008/`): `QUERY_FORMAT XR24 LINEAR` answered yes, then at import **"the display CANNOT show XR24 modifier 0x0 ... ADVERTISED ... and then refused to import it"** (`wl2_broker_lines.txt`, `wl1_relay_lines.txt`): **LINEAR system-memory udmabuf is advertised and refused**. The block-linear NVIDIA modifier `0x0300000000606014` was answered yes, and **"the display imported a GPU-copy frame (its RELEASE came back)"**: `broker[... sent=176 gpucopy=175 gpucopy_backoffs=1 ... dmabuf_trips=0 carrier_refused=0 ...]` (`wl2_broker_lines.txt`). With rung 0 disabled (`display-broker-vram=off`) the run fell to wl_shm, `sent=398 releases=396` (`wl3_shm_regression.txt`). The older doc line "Expected: rung 2 (shm) on an all-NVIDIA Wayland desktop (NVIDIA's GL refuses LINEAR dma-bufs)" (`V3_DISPLAY.md` §8.2) is thereby MEASURED, not a guess.
* Public sources on the NVIDIA side are thin and do not settle linear-sysmem: the NVIDIA tree's own export code returns an error for objects without struct pages ("Cannot create sg_table for NvKmsKapiMemory"; "GetMemoryPages will fail for vidmem allocations"), https://raw.githubusercontent.com/NVIDIA/open-gpu-kernel-modules/main/kernel-open/nvidia-drm/nvidia-drm-gem-nvkms-memory.c (DOC READ via a fetch summary; re-read the file at the 595 tag before relying on a line number). INFERRED consequence: a vidmem nvidia-drm dma-buf is opaque to non-NVIDIA importers and to `mmap`; only NVIDIA's own stack resolves it (through `GEM_EXPORT_NVKMS_MEMORY`, `V3_DISPLAY.md` §8.11 Security). This matches the code's `EV_DEVICE` rule: another GPU's compositor never gets rung 0.
* A forum report of 595.71.05/610.43.03 (https://forums.developer.nvidia.com/t/bug-report-vram-not-reclaimed-for-sampled-cross-process-dma-buf-imports-in-595-71-05-driver/374816) says a compositor sampling a *cross-process* dma-buf import leaks a bounded (~2.2 GB) private VRAM pool, which the reporter reads as the driver making a private VRAM copy for sampling foreign buffers. User report, not an NVIDIA statement; **open: whether mutter->NVIDIA EGL samples kayfabe's slot in place or copies it** (hardware-only, Sec. 7).

**What this means for the current broker once GNOME runs on NVIDIA (the owner's stated move):**
* CODE READ order (`kf-broker/src/conn.rs` `choose`): rung 0 needs an explicit yes for the block-linear pair, `CAP_MODIFIERS`+`CAP_RELEASE`, `EV_DEVICE` = this GPU (`conn.rs:2595-2618`, line "the compositor renders on this GPU: the GPU-copy rung may be used"), the ABI gate (host driver 595.91.07 is in `traces/driver_matrix/drmnv.tsv` since 2026-10-08; nvidia-drm version must equal the RM's, `kf-qemu/src/gpucopy.rs` `probe`), `modeset=1`. All five hold in the owner's setup by the log above, so the expected tier is **rung 0, not wl_shm**.
* The message "the display refused every dma-buf layout offered" is a *broker* log line that was wrong for any F_SHM frame; fixed on `claude/cursor-xor-wire-20261017` (`V3_BROKER_PRESENT_TIER_20261017.md` §1, §4); the carrier line now says "the VMM chose this carrier" and counts refusals. Read `carrier_refused`/`gpucopy_backoffs` in the `broker[...]` status instead.
* **wl_shm fallback is what costs a CPU copy**: kayfabe fills a memfd by DMA, then the compositor uploads it to a texture each frame ("costs the compositor one upload per frame", broker message). Reached when: rung 0 is withdrawn (ABI gate, `display-broker-vram=off`, slot provisioning refused), or the detector backs off.
* **Known risk on exactly this setup (CODE READ + DOC READ, not yet MEASURED on candidate 5):** the acknowledgement detector (`Ack`, `DETECT_COMMITS = 3`, `DETECT_MS = 1000`, `conn.rs:111-113, 519-577`) trips on a quiet guest because mutter releases a dma-buf only when it is replaced (MEASURED for LINEAR on mutter 50.1, `V3_BROKER_PRESENT_TIER_20261017.md` §2). The 2026-10-08 rung-0 run shows `gpucopy_backoffs=1` (one trip at start). The kayfabe-side fix described in that doc §4 (count a commit toward a trip only when a newer commit exists and the pair is proven) is still open (no change found in `conn.rs`). Each trip = ~5 s (doubling) of host rungs, which on NVIDIA means LINEAR (refused) -> wl_shm.

## 3. Candidate designs

| | feasibility | who allocates | what is copied | verdict |
|---|---|---|---|---|
| **R0** existing rung 0 | built; MEASURED imported by mutter on NVIDIA 595.91.07 | kayfabe (RM client for the display + nvidia-drm render node) | compose -> staging (VRAM) -> pack -> slot (VRAM); zero PCIe bytes | the answer for "no CPU/system memory round trip" |
| **(a)** broker allocates on the compositor GPU (GBM/EGL), VMM imports and copies | feasible but heavy; not needed | the broker (new libgbm/EGL dependency) | same as R0, plus an fd flows broker -> VMM | not recommended |
| **(b)** export RM vidmem as dma-buf | already done by R0 with public ogkm ioctls | kayfabe | n/a | exists; no patch needed |
| **(c)** keep sysmem LINEAR, no CPU copy | refused by NVIDIA EGL on this host (MEASURED) | n/a | n/a | dead on NVIDIA; fine on the iGPU (it is rung 1 today) |
| **(d)** pure KMS plane | out of scope | n/a | n/a | rejected |
| **(e)** single-pass compose-into-slot | new work, small | kayfabe | removes the staging pass for simple scenes | optional stage 2, only if measured worth it |

### (a) Broker allocates a GBM/EGL buffer on the compositor GPU; the VMM imports and copies VRAM->VRAM
* **Dependencies / rule:** the broker is built to link no libdrm/EGL/GL/GBM (`broker/README.md:111`, `broker/Makefile:13`; only the test source `dmabuf_source.c` links libgbm, Makefile:117). A GBM allocator would have to be an *optional helper process* (a separate binary the broker spawns, the way `dmabuf_source` is separate), so the broker proper keeps its no-dependency rule.
* **Importing that dma-buf into kayfabe's GPU work:** CUDA external memory in the public docs lists OPAQUE_FD, OPAQUE_WIN32(_KMT), D3D11/D3D12 and NvSciBuf handle types and **no dma-buf type** (DOC READ: https://docs.nvidia.com/cuda/cuda-runtime-api/structcudaExternalMemoryHandleDesc.html and the driver-API struct page https://docs.nvidia.com/cuda/cuda-driver-api/structCUDA__EXTERNAL__MEMORY__HANDLE__DESC__v1.html; the fetched summaries did not show a dma-buf entry; a CUDA-version-specific recheck is owed). So the CUDA route is not documented as available; a Vulkan route is: `VK_EXT_external_memory_dma_buf` + `VK_EXT_image_drm_format_modifier` were added to the NVIDIA Vulkan driver in 515.48.07 and need nvidia-drm modeset=1 (secondary source: GamingOnLinux 515.48.07 article; NOT confirmed on 595 here), then Vulkan->CUDA interop to write it. That adds a Vulkan stack to a CUDA-only VMM. The unsafe rule (only `*_unsafe.rs` in kf-linux-raw/kf-qemu/kf-cuda) would put it in kf-cuda or a new `kf-vk` crate.
* **Ownership/sync/security:** reverses the fd direction: a *less-trusted host process* (the broker, which talks to the compositor) would hand fds to the VMM, which would import them into its RM/Vulkan context; today the VMM only ever exports (`§8.11 Security`). Both are host-side and the guest controls only pixels, but the VMM would now parse a foreign fd's layout. The explicit-sync question (`linux-drm-syncobj-v1`, in wayland-protocols since 1.34, mutter 46+ per upstream notes; not verified for 50.1 here) is orthogonal: R0 does without it because the frame is complete before COMMIT and slot reuse is gated by RELEASE + `EXPORT_SYNC_FILE`.
* **vCPU rule:** unaffected if the import is on the provisioning thread (as R0's `kf3-vram-provision`).
* **Size (INFERRED):** helper ~600 lines C + protocol (alloc request/reply, fd passing) + kayfabe Vulkan import ~1500 lines Rust + tests. **Benefit over R0: none for copies** (still one VRAM->VRAM copy); only lets the compositor's own allocator pick the layout, which might help direct scanout (unknown). **Falsifier for "R0 is enough":** with GNOME on NVIDIA, `Present: FLIP` is never reported for a fullscreen guest while compositor frame times show the sampling pass as a cost.

### (b) NVIDIA-specific export of RM vidmem as dma-buf
* **Exists in the tree:** `kf-qemu/src/gpucopy.rs` steps 2-4: `alloc_display_slot` (RM) -> `export_display_slot` -> `DRM_IOCTL_NVIDIA_GEM_IMPORT_NVKMS_MEMORY` -> `PRIME_HANDLE_TO_FD` (a dma-buf, `DMA_BUF_MAGIC`-checked, identity-collision retry); the same RM export fd is imported into CUDA (`cuMemImportFromShareableHandle`, `kf-cuda/src/display.rs:1405-1430`). The two private ioctls are in the open nvidia-drm sources; layouts are gated per tag by `tools/drivermatrix/drmnv.py` (575.51.02 ... 615.71.09 measured equal). **No patch to the host driver is needed** (consistent with `project_host_patch_tier`: stock install needs none). Attribute sets S0/S1/S2 were all imported by CUDA and by the NVIDIA X server (`V3_DISPLAY.md` §8.11 "Partly superseded", box 54032077, 580.159.04); the default S1 (NVKMS offscreen block-linear) is what GNOME imported at 595.91.07.
* **Limits:** private ABI per driver tag (gate refuses outside the measured interval and when nvidia-drm and the RM differ); the dma-buf is not CPU-mappable and not importable by non-NVIDIA devices (INFERRED from the export code above); a compositor holds an import of any slot, so slots are never freed while the device lives (`kept`), 5 x (10+36) MiB worst case per head.
* **Not available/needed:** `nvidia_p2p`/`NV_DMABUF` export via RM is the datacenter peer-to-peer API, not a display path; no use found for it here.

### (c) Leave the frame in sysmem, make the compositor take it without a CPU copy
* On the **iGPU** this is today's rung 1: a LINEAR udmabuf over pinned pages, written by the copy engine; AMD imports it, zero CPU involvement (MEASURED `CAN import` on the AMD compositor, `V3_BROKER_PRESENT_TIER_20261017.md` §1, with the pitch-multiple-of-256 rule, `V3_DISPLAY.md` §8.21).
* On **NVIDIA** it is refused at import (MEASURED above), mutter has no fallback (no CPU map, fatal protocol error), and the broker's probe turns that into `EV_FORMAT x=0` -> shm. Direct scanout of an imported sysmem buffer: mutter's `try_acquire_scanout` imports with `gbm_bo_import(..., GBM_BO_USE_SCANOUT)` on the *same* GPU and requires the modifier in the CRTC plane's list (DOC READ, same mutter file); whether NVIDIA's GBM accepts a foreign udmabuf there is not established by any source I could reach, and the EGL import already fails. Even if it worked, the display engine would read the frame over PCIe every refresh. **Rejected for NVIDIA.**

### (d) Bypass the compositor with a KMS plane
Out of scope: the host session owns the monitor (DRM master is the compositor's); taking it would end the desktop for a VM window, defeats the cursor/input/clipboard/ACPI work the broker exists for (`V3_BROKER_ROADMAP_20261015.md`), and hardware planes belong to the host display engine kayfabe does not drive. The honest equivalent is in the compositor: if mutter promotes the broker window to a plane ("Present: FLIP", wp_presentation `ZERO_COPY` flag; the broker already logs it, `nb_session_wl.c:4708-4770`), the host scans out the slot directly. Conditions (mutter source): fullscreen, unscaled, format+modifier in the plane's list, same GPU.

### (e) Shorten R0 itself (the only real "more zero" available inside the ruling)
Compose writes staging; pack copies staging -> slot. A compose kernel variant that writes block-linear straight into the slot for the common case (one full-screen XRGB window, no scaling, no colour program, grab-mode cursor already composed by the same kernel) removes a 33 MB read+write pass at 4K. Still a copy (the guest's surface is read, the slot is written), so within §L; it keeps "the guest cannot change the bytes after the copy". Gain INFERRED <= ~0.13 ms of GPU time per 4K frame at 504 GB/s; worth building only if Sec. 5 measures the pack stage above ~1 ms. Size (INFERRED): one kernel variant + selector + the existing byte-for-byte reference test (`kf-disp/tests/bl_pack_kernel.rs` pattern) ~400 lines.

## 4. Recommendation

1. **Do not build a new zero-copy path now.** The no-CPU-copy tier exists, is gated, and imported in a real GNOME-on-NVIDIA run. Move the monitor, run the existing broker, and read the counters (stage 0).
2. **The likelier problems on the NVIDIA setup are not copies**: (i) detector trips on a quiet guest -> 5 s of wl_shm (kayfabe-side fix owed, Sec. 6 stage 1); (ii) whether the compositor samples the slot in place or copies it (forum report) and whether it promotes to a plane; (iii) pacing (`V3_DISPLAY_PACING_20261017.md`), which the owner's "laggy feel" more probably tracks than an 8-33 MB DMA (INFERRED; decided by Sec. 5).
3. Only if stage 0 shows rung 0 refused or a measured copy cost, go to stage 2.

## 5. The measurement that decides it (stage 0, no code)

Run order after the cable move, existing broker (candidate 5 build), one 60 s Windows desktop + one 60 s game-like load, at 1080p and at 4K guest modes; capture the QEMU `kf3:` status lines and the broker log. **Existing fields to read:**
* Tier chosen, in order: broker `the compositor renders on this GPU: the GPU-copy rung may be used` (or `... on DRM device a:b, not this GPU's`), `the display CAN show XR24 modifier 0x0300000000606014`, `frames go as a GPU copy in host VRAM`; carrier changes ("frames now arrive as plain shared memory ...", once per change).
* `broker[... sent= gpucopy= gpucopy_backoffs= dmabuf_trips= carrier_refused= carrier_unchecked= formats_unasked= dropped= releases= reclaims= ...]` (`conn.rs:~870`). **Pass:** `gpucopy/sent` ~ 1, `gpucopy_backoffs` = 0 or only the start-up one, `carrier_refused` = 0.
* `disp[... scanouts= scanout_avg_us= scanout_max_us= ... scanout_d2h= scanout_pack= pack_skipped= display_vram_mib=]` (`device.rs:2960-3000`): `scanout_pack` rising, `scanout_d2h` ~ flat (only the console's requests), `display_vram_mib` 50 at 1080p then ~230 after the 4K growth.
* `fps[... kms= tear= copies= skipped= ...]` (`kf-disp/src/pace.rs:576-620`): `copies` ~ `tick`.
* Broker `Present: FLIP|COPY` (`nb_session_wl.c:4708`): FLIP = scanned out directly.
* Host side, read-only: `nvidia-smi dmon -s ut` (SM utilisation, PCIe rx/tx): the D2H tiers show PCIe traffic ~ frame size x rate (1080p30 ~250 MB/s, 4K60 ~2 GB/s), rung 0 shows none from the display path. mutter frame times via `journalctl --user -u gnome-shell` + `sysprof`/`gnome-shell` perf overlay, or the broker's presented-time stream.

**Fields to ADD (proposed, not built):**
* kayfabe, per scanout, CUDA-event timed on the display stream: `compose_us`, `pack_us`, `d2h_us` (avg/max, plus a per-mode bucket 1080p/4K) next to `scanout_avg_us`. Falsifier for "the copy is not the cost": `pack_us` avg > 1 ms at 4K, or `compose_us + pack_us` > 25% of the tick.
* broker, from `wp_presentation`: `commit_to_present_us` (avg/max/p99) and counts of `ZERO_COPY` vs not, plus the per-carrier count, logged with `broker[...]`; and the mutter-reported `main_device` (already `EV_DEVICE`).
* a one-line `tier=` summary in the broker status: `native|linear|shm`.

**Decision table.** (A) rung 0 held, `gpucopy_backoffs` <= 1, `scanout_avg_us` < 2 ms at 4K: no zero-copy work; take pacing. (B) rung 0 held but trips repeat on a quiet guest: stage 1. (C) tier is shm/linear for any reason other than a trip: fix that reason (ABI gate, `modeset`, slot provisioning, `display-broker-vram`), per the log line. (D) rung 0 held, `pack_us` large at 4K: stage 2 (e). (E) rung 0 refused by mutter at import (`EV_FORMAT x=0` for the block-linear pair): the S1 attribute set may not be what mutter 50 wants; re-run with `KF3_VRAM_ATTRS=s0|s2` (the existing E1 switch, `gpucopy.rs` `attrs_from_env`) before any redesign.

## 6. Staged plan

* **Stage 0 (no code):** the Sec. 5 run, once per tier of interest (also keep a `display-broker-vram=off` run to price wl_shm on NVIDIA, as `wl3` did on 2026-10-08).
* **Stage 1 (smallest change that removes the dominant copy, in the order the data may call for):** (i) the owed `Ack` fix (`V3_BROKER_PRESENT_TIER_20261017.md` §4: trip only on a commit older than the newest, and after the pair is proven), so a quiet guest never falls to shm; falsifier: a burst of 3 frames then idle on mutter-on-NVIDIA still produces `gpucopy_backoffs` 0 after the fix and >= 1 before; (ii) add the Sec. 5 timing fields; (iii) if D2H still runs while rung 0 carries (`scanout_d2h` rising with the console idle), find the requester (the 4 Hz refresh when "nobody asked" applies only without a broker, `plan`).
* **Stage 2 (true zero copy, only if (D) fires):** (e) compose-into-slot for the simple scene. Not (a): it adds a dependency and an fd direction without removing a copy. The guest-surface export is excluded by §L and would need an owner decision, a stable single-buffer fence/pace scheme and the copy-on-write the owner asked to avoid.

## 7. Honest limits (hardware only)

* Whether mutter 50.1 + NVIDIA 595.91.07 (not the 2026-10-08 mutter) still imports S1 slots and releases them; the 2026-10-08 run predates candidate 5 (kf3 `2a20e699`) and the broker's cursor/pacing work. Candidate 5 broker grades (`traces/candidate5_20261018/`) are GPU-free (broker checks), not a GNOME-on-NVIDIA run.
* Whether the compositor samples the slot in place or makes a private VRAM copy (forum report); whether it promotes it to a plane (needs `Present: FLIP`).
* 4K pack/compose times; 4K slot growth behaviour under NVIDIA (`SLOT_MAX` 36 MiB covers 3840x2160 by arithmetic, not yet by a run in the committed traces I found).
* The CUDA documentation fetches did not show a dma-buf handle type; a dma-buf import into CUDA is not established either way for 13.x.
* Public documentation says almost nothing about NVIDIA EGL's linear/sysmem import; the LINEAR refusal is a measurement on one host, one driver tag, one compositor.
* Nothing in this document was run; every number marked MEASURED was read from a committed trace, none was produced here.
