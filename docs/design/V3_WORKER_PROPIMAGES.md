## What exists

- **`propimages.json`** (schema `kayfabe.worker-propimages/1`): `strict: true`; `swap` (release-level exchange of the two slots, default false); `unmeasured_note`; `objects` (id, role `image` or `gop`, the pin ref the box looks up in `scripts/ci/propimage_apps*_pins.json`, the private object name, size, sha256); `images` (label `imga`, `imgb`; the object; `slot` 1 or 2; `measured_families`, the families the image has run on; `apps`: id, `lane`, and the reason for the lane; `excluded`: applications that are deliberately not listed, with the reason). There is no per-family list of dies: the images apply to every family in `releaseDies`.
- **`src/propimages.js`**, pure:
  - `propimagesConfigProblems(config, {registry})`: every problem of a configuration as a named token (`NOT_STRICT`, `UNPINNED:<id>`, `SIZE:<id>`, `SLOT:<l>`, `SWAP`, `DUPLICATE_LABEL:<l>`, `UNKNOWN_OBJECT:<l>`, `LANE:<l>:<app>`, `UNKNOWN_APP:<l>:<app>` when the runner's registry is given, `EXCLUDED:<l>`, `MEASURED_FAMILIES:<l>`, `GOP`, ...).
  - `propimagePlan(leg, options)`: the part, the assignment and the log lines for one leg; `propimagesForLeg` is its `part`. Image objects are `{label, kind: "prebuilt", disk: {from: "pin", ref, sha256}, apps: {id: {mode: "present", lane}}}`, the object the runner's `propimage_runspec.validate_list` reads. `propimages_strict` is always `true`; there is no option to say otherwise.
  - `buildLeg` / `buildInstruction(profile, options, ...)`: the whole instruction. The base fields are derived from `tierEnvironment(profile, options)` (what the Worker sends today); the part is added ONLY for `propimages: true` (default off) on a release-profile leg, with the leg's `die` and the release's `releaseSeq`. A driver-matrix leg is refused (`instruction release matrix`): the instruction has no driver fields and the payload refuses such a leg while `PAYLOAD_RELEASE_MATRIX_EXECUTOR` is 0.
  - `canonicalInstruction(doc)`: the bytes `payload_instruction.py` writes (`json.dumps(indent=2, sort_keys=True)` plus a newline).
- `tierEnvironment` is not changed (a test pins today's rehearsal variables), `src/index.js` imports neither module (a test pins that), and no environment variable carries the part: it has no `KF_*` spelling, so the Worker sends it as the instruction file (`--instruction`). The route that hands the file to a box is not built (below).

## Who runs which image

- Only the **release** profile takes images. A request with the flag on the check profile (small or middle tier) or the sweep is refused by name (`propimages release only`). Inside a release the family's two boxes are the flagship (leg tier `large`, slot 1) and the second die (leg tier `middle`, slot 2); both carry an image list. `payload_instruction.py` therefore accepts `propimages` on tier `middle` as well as `large` (it refused `middle`; one line, its tests and mutants updated in this change; `small`, `adhoc` and `unknown` are still refused).
- A die's slot is its place among the release matrix rows of its family, the order `planRelease` uses (`slotOfDie`). Image slot 1 runs on the family's first box and image slot 2 on its second, exchanged when `config.swap` XOR (`releaseSeq` is odd): consecutive releases rotate which die gets which image, while one release number always gives one assignment, so a retry on the same sha never moves an image. A family with a single die available (`familyDies: 1`, and the one-die rehearsal) runs both images on that box and is not rotated; the plan text says so.
- `releaseSeq` is a request field (a non-negative integer, required for the two-die split), not state kept here. The Worker should take it from the admin start of the release, as the ordinal of the release (the number in the release tag, or a counter the admin route keeps next to the batch); the only property the rule needs is that a retry of the same release carries the same number. The Worker today has no such value (batch ids are random), so that is part of the route that is not built.
- The base Windows stages (`windows_gate`, `windows_gate_2`, `windows_apps`) are in the plan of both boxes and run on both; only the image stage differs. Every plan prints, per leg: the die, its slot, the release number and its parity, the config swap, the effective swap, and which image runs here or on the other box (`propimagePlan(...).lines`).

## What the parity tests cover (run 2026-11-16 in this tree)

For the one-die rehearsal (both images), the slot-1 leg on an Ada die (image A, even release), the same leg on an odd release (image B) and the slot-2 leg on the second Ada die (tier middle, image B), `node --test ci/vast-broker/test/propimages.test.js` checks:

1. The instruction the Worker builds equals a committed golden file byte for byte (`test/fixtures/propimages/`).
2. The box's own parser (`payload_instruction.parse`) reads each golden and writes the same bytes back; `vast_payload.py --instruction G --emit-instruction H` writes `H` equal to `G` (slot 1, image A); `--dry-run` prints `KF_PAYLOAD_PROPIMAGES strict=1 images=imga` and plans `propimage_apps`; the box refuses the list on tiers `small` and `adhoc`.
3. The standalone command line built from the same images (`--image prebuilt:pin:REF#sha256=SHA --label L --app ID=present,lane=LANE ... --strict`) is parsed by `propimage_runspec.split_flags` into the same normalized spec as `validate_list` of the instruction's images, and `propimage_apps.py plan` prints the same plan for the flags and for `--images-file`. Without `--strict` the same flags are the permissive run of the same images.
4. For eight base legs (rehearsal with and without a SPEC lane, large, release middle, check middle and small, sweep) the instruction `vast_payload.py --emit-instruction` builds from the environment `tierEnvironment` sends equals the Worker's instruction byte for byte.
5. Any golden with image B is refused today by the box's dry run with `STRICT_UNKNOWN_APP:imgb:<first app>`, because image B's application definitions are another change (#446); the tests assert exactly that refusal, and assert the accepting form once every image B application has a definition.

Not covered: that a box can fetch the objects, and that any listed application passes.

## Bandwidth: what a leg downloads, from its instruction

`estimateBandwidth(instruction, tier, options)` in `src/bandwidth.js` returns the expected download and upload of one leg and the text the Worker puts in the leg's log. It is pure; nothing calls it yet, so no price changes.

- **Every number is in `ci/vast-broker/bandwidth.json`**: the margin (default 15 percent, applied last to the sums), the repo clone, per payload stage a list of entries, and per stage an upload. The `.js` holds no data number (a test scans it). An entry has: `id`, `what`, `class` (`r2-pinned`, `r2-listed`, `official-url`, `package`, `repo`), `down_bytes` or `size_from`, `url` (a URL or an object name), `basis` (`measured` or `ESTIMATE`), `date`, `source` (the run or report it came from), `note` (required for an ESTIMATE), and optionally `when`, `per_image`, `calibrate`. A box pays per GB whatever the source, so an official URL counts exactly like an R2 object.
- **Pinned sizes are read, not copied.** `size_from` is `propimage:image` (the object of each image in the instruction, from `propimages.json`), `propimage:<id>` (another object, such as the signed GOP), `driver:<os>/<version>` (an NVIDIA installer pinned in `release-matrix.json`) or `r2:<name>` (a size the Worker passes from an R2 list; the entry's `down_bytes` is the fallback). The guard refuses a pinned size copied beside its pin.
- **Which entries count** follows the instruction: the stages of the payload's own plan (`plannedStages` is compared with `vast_payload.py --dry-run` in the tests), minus `--skip`, restricted by `--only`; an entry with `when` counts only if the instruction matches (`images`, `tier`, `winapps`, `spec`, `linux_apps`). An image list adds exactly the pinned size of the images in it; with the split that is one image (about 50 to 63 GB) per box, both only on a one-die box.
- **Pricing.** The numbers go to `bandwidthOverrides(estimate)` for `cfg.bandwidthDownOverride` / `bandwidthUpOverride`. `resourceCaps` in `policy.js` takes `max(profile row, override)`, so today an estimate can only raise a leg above its profile row; lowering it needs `resourceCaps` to take the estimate as the number. That is a `policy.js` edit, and `policy.js` is one of the files the workflow bootstrap fetches from BASE, so it needs a bundle pin; it is not made here. A test pins the current `max` behaviour.
- **Upload** is an evidence pull-back estimate per stage (the whole-run collect archives of 2026-11-16 were 4.8 to 9.9 MB).
- **Breakdown.** `estimate.lines` is one line per item, `GB down|up [basis class] id (label): what <where the size came from>`, then the sums and the margin. The `id` is the id in `bandwidth.json`, so a surprise in a bill maps to one entry to edit.
- **Actual bytes.** `vast_payload.py` records, per stage, the rx and tx bytes of the box's default-route interface (`/proc/net/dev`, `/proc/net/route`) in its result file under `net_bytes`; `vast_report.py` validates it and does not forward it. `scripts/ci/bandwidth_calibrate.py` reads those files and proposes a table update.

### Changing the bandwidth numbers

1. Run `python3 scripts/ci/bandwidth_calibrate.py --instruction instruction.json RUN1/kf-result.json [RUN2/kf-result.json ...]`. It prints a diff of `bandwidth.json` and never writes it. It sets the one `calibrate: true` entry of each stage to the stage's actual download minus the stage's other entries, and the stage upload to the actual upload, with the basis no longer ESTIMATE, today's date and the run files as the source. A stage with no such entry is only reported.
2. Read the diff and apply it (or edit `bandwidth.json` by hand: one entry, its `down_bytes`, `basis`, `date`, `source`, `note`). To change an image size, edit it in `propimages.json`, not here.
3. Run `python3 scripts/ci/bandwidth_check.py` and commit. The check fails on an entry without a class, source or date, an ESTIMATE older than 60 days or without a note, an unknown field, a payload stage missing from the table, and a table stage the payload no longer has. Example: the apps stage turned out to move 5.2 GB; the calibrate diff changes `apps.media` to `"down_bytes": 5200000000` with a new date and source, and `bandwidth_check.py` prints `bandwidth table: PASS`.

## The die constraint and delivery

Images are listed for every family in `releaseDies`; where a family has not been run, the lanes are the discovery lane (above), so no family is excluded and no strict release fails on an unproven one. The box learns the images as pin refs (`propimage-...zip`) and looks the object up in the pins files, which hold the size and sha256; the instruction repeats the sha256 so the object is checked twice (a mismatch is `PIN_SHA256_MISMATCH`). The instruction carries no object name, size or reason text (a test pins that). How the bytes reach the box is not decided by this change: the standalone run uses a presigned URL file the operator mints (`kayfabe.download-urls/1`) or pushed files.

## The `/bench-data` allow-list (decision: left unchanged)

The Worker route `GET /bench-data/<run>/<name>` answers with a presigned URL for an allow-listed name. It is gated by a live run token and the run's deadlines, but NOT by profile or stage (`DEPLOY.md`, `/bench-data` scope note: any live box can ask for the SPECviewperf copy). A check-profile box runs the tree of a pull request. Adding the images to the allow-list would therefore let that tree request them, which is a larger exposure than the one the owner approved for the benchmark copy. The allow-list in `src/benchdata.js` is NOT changed, and two tests fail if an image name or object key is added to it. The condition to add them is a route that also requires the release profile and a leg whose instruction lists the image (one run record field); that is the route work below.
