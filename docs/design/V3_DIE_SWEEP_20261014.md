## 2. Procedure (per die)

1. Rent (`vms_enabled=true`, KVM image, `--disk 150`), `/root/night/arm_autodestroy.sh <id> 240`, check `df -h /`, `/dev/kvm`, the GPU.
2. `box_facts.sh` (before the driver swap and after): PCI ids, BAR region sizes, Resizable-BAR capability, link, host BAR1 total.
3. `provision_full.sh` with D2/D3; READY line; `v3_gates.sh` (bare-metal gates on the same box: if these fail, the box is at fault).
4. Image (D4/D10, `push_image.sh <alias>`) to `/root/win`; `die_run.sh phase1` (census, flag, bind, shutdown), then `die_run.sh phase2` (new QEMU process, screenshots, evidence every 90 s); a diagnostic
   boot is `die_run.sh probe` (`WIN_TRACE=1` + `WIN_FLAGS="KF3_BAR0_TRACE KF3_BAR0_READ_TRACE=1 KF3_READ_TRACE_RANGES=…"`, optional `PROBE_PS=<ps1>`); `collect.sh <alias> <dir>` brings the TEXT evidence back
   (counts of resets/refusals, filtered kf3 log, `nvidia-smi` text, box facts, gate summary). Screenshots are fetched with the QMP `screendump` the harness already takes and stored as small palette PNGs.

### 3.5 Blackwell: GB206 (RTX 5060 Ti) — three walls cleared, the fourth is the Windows RM's own decision

All of this is on vast 55943552 (UK, 23 vCPU, `10de:2d04`; 55835565 last night), `v3_gates.sh` 9/9 + gate10, births 12/12 USER.

**(a) The kf-disp gap [done, measured at realize on the hardware].** Cause as the night found it, with the full list: the derived Blackwell classes `NVCA7D`/`NVCA7E`
have **no context DMAs** (`SET_CONTEXT_DMA_{NOTIFIER,SEMAPHORE,ACQ_SEMAPHORE}`, `SET_NOTIFIER_CONTROL_OFFSET`, `SET_{,ACQ_}SEMAPHORE_CONTROL_OFFSET` do not exist): the
address is in the method (`SET_SURFACE_ADDRESS_HI/LO_{NOTIFIER,SEMAPHORE,ACQ_SEMAPHORE}`: `ADDRESS_LO` 31:4, `TARGET` 3:2 = IOVA/PHYSICAL_NVM/PHYSICAL_PCI/
PHYSICAL_PCI_COHERENT, `ENABLE` 0:0), exactly as NVKMS programs it (`ogkm-595.84 nvkms-evo4.c`, `EvoSetWinNotifierSurfaceAddressAndControlC9` and the semaphore
twins). **Seven names were not the whole gap:** the window class also has no inline `SET_CSC{0,1}LUT_ENTRY/_SEGMENT_SIZE`, which the vocabulary required. Change (`kf-disp`,
`kf-qemu`): `Naming` (context DMA *or* surface address, chosen by what the derived table has, a class with neither is refused by the first missing surface name),
`Place`/`Aperture` on `Effect::Notify`, `Effect::Release`, `Acquire`; the plane's `Io::at` turns a surface address into a context DMA bounded to the 16/8/4 bytes the
completion needs (system memory through guest RAM, video memory through the store, both refuse an access outside by name; `TARGET_IOVA` is refused: a
discrete GPU's display has no IOMMU space). Context-DMA families are unchanged (148 kf-disp tests, the whole workspace subset green). Unit tests:
`every_family_row_resolves_its_vocabulary`, `the_naming_form_follows_the_derived_table`, `gb20x_core_notifier_is_a_surface_address`,
`gb20x_window_flip_uses_surface_addresses_for_notifier_release_and_acquire` (acquire, release, notifier, flip-away order), `gb20x_target_and_address_decoding`, and the GPU-free
realize-path test in `kf-qemu` for every row. **On the box: `kf3: display plane built — … engine vocabulary` and the GB206 Windows guest runs with `display=on`.** Not done (and not needed
for the guest to start): a Blackwell scanout backend (`ScanVocab::resolve` is `None` for `CA7E`; the boot layer shows) — V3_FEATURE_GAPS H22.

**(b) The Code 43 [three walls, each from a BAR0 trace of the Windows guest, `KF3_BAR0_TRACE`/`KF3_BAR0_READ_TRACE` + `WIN_TRACE`, `traces/…/gb206_5060ti/`].**
Hypotheses stated before each run:
- *Trace before any change [measured]*: FSP EMEM write `c0000000 1610de7e 00000020` (CAPS_QUERY, sub-message CLOCK_BOOST), `QUEUE_TAIL=8`, `QUEUE_HEAD=0`; the **FSP answered** (`MSGQ_TAIL=0x10`; read back
  `c0000000 1510de7e 0 16 0` = `NVDM_TYPE_FSP_RESPONSE`, command 0x16, status 0). The Linux RM then sends `CLOCK_BOOST` and the COT (`fast_gb206lx` trace: 0x20 → 0x14, 868 bytes). **The Windows RM sends neither**:
  it clears the GSP queue head and spins ≥10 000 reads of `0x1103c4` per attempt, toggling `0x1103c0`, four attempts. HB1 is false.
- **HB2 [measured trace, inferred mechanism]:** `0x1103c4` is `NV_PGSP_FALCON_RESET_PRIV_LEVEL_MASK` and `0x1103c0` `NV_PGSP_FALCON_ENGINE` (`ogkm-595.84 blackwell/gb100/dev_gsp.h`). `kgspResetHw_GB100`
  waits for `READ/WRITE_PROTECTION_LEVEL0` = ENABLE on the first, then `kgspResetHw_GH100` writes `RESET_ASSERT`, waits `RESET_STATUS == ASSERTED (0)`, writes `DEASSERT`, waits `DEASSERTED (2)`
  (`kernel_gsp_gb100.c:68-91`, `kernel_gsp_gh100.c:113-150`). kf3 read the PLM as 0 and the engine word as the guest's own write, so the wait for DEASSERTED could never pass. **Falsifier:** with both served
  the guest still sends no `CLOCK_BOOST`/COT *after a completed reset* — **and it does not, but that is not a falsification: the stop moved** (next item). **Fix:** `GspReg::GspFalconEngine`
  (`answer_on_store` + an FSM-recorded observation field, the `BCR_CTRL` pattern; reads `0x200` idle, `0x1` after ASSERT, `0x200` after DEASSERT) and a static boot register for the PLM (both fields ENABLE = `0x11`),
  Blackwell only (GH100 has no PLM wait); header-checked tests (`gsp_reset_fsm.rs`, `hwref_check`).
- **HB3 [measured register order, inferred mapping]:** after the reset the guest writes `MAILBOX0/1` = `0x3dbff000/0x2` (the `GSP_FMC_BOOT_PARAMS` address), `NV_PGSP_MAILBOX(0)` = 0, the six `BCR_*` words and the
  RISC-V `CPUCTL` = 1, then reads `HWCFG2` (`0x2400`) and `MAILBOX0` in a loop. That is **`_kgspBootstrapGspFmc_GH100`** (`kernel_gsp_gh100.c:716-776`), the route of `kgspBootstrap_GH100` taken when the FSP is
  *not* told to boot the GSP-FMC (`PDB_PROP_KFSP_DISABLE_GSPFMC`; in the open driver a regkey, the Windows RM took it by itself) — **no COT at all**. **Falsifier:** with `STARTCPU` published as the boot trigger the guest

## 4. Traps found on the way

- **`provision_box.sh`'s mirror floor rejects a fast box.** It times a download of `dists/jammy/Release` (~130 KB) and refuses
  below 200 kB/s; on vast 55835556 (Nevada) all three mirrors measured 120–165 kB/s that way while a 20 MB ranged download of
  the same mirrors ran at ~5 MB/s [measured]. The small file measures latency, not bandwidth. Worked around on the box copy
  (floor 50 kB/s); the script itself is not changed.
- **The first ssh of a vast VM reaches a different host key** (the pre-boot endpoint), so a strict known_hosts refuses the VM
  once it is up; drop the entry.
- **`provision_bench_tree.sh` needs `/root/NVIDIA-Linux-x86_64-580.159.04.run` before `provision_full.sh` starts** (`TREE_RC=2`, then `FG_RC=1`/`KF3_RC=1`: "missing … the guest needs the SAME .run").
  The box can `curl` it from `us.download.nvidia.com` in seconds (sha256 checked against the dev machine's copy); do that first.
- **The vast offer list changes by the minute and the `vms_enabled` filter hides most of it:** 2 offers at 13:45, 7 at 13:50, 13 at 14:05; the cheap Ampere/Turing/Blackwell offers of the night
  were gone in the morning and reappeared (RTX 2060S $0.094, RTX 5060 Ti $0.162) in the afternoon. Re-search before every rental; do not give up on a family after one empty listing.
- **A rental that never answers ssh is dead:** vast 55830508 (RTX PRO 5000, Australia, machine 149455) read `running` for 35 minutes with `Connection refused` on both the direct and the proxy port;
  vast 55927182 (4070S Ti) refused to start (`GPU error, unable to start instance`). Both destroyed; cost < $0.50 together.
- **`10de:2bb9` is not a usable Blackwell rental for this lane:** "RTX 6000D" (vast 55941464, $1.47/h) enumerates as a **3D controller** (no VGA/display function), BAR1 = **128 GiB**
  (Resizable BAR on), and the image's `nv_dispi.inf` does not list it (`inf_ids_nv_dispi_580.88.txt`). Destroyed after 12 minutes. Check the PCI id against the INF list (D13) before renting.
- **Script traps fixed in `win_die.sh`/`die_run.sh`:** a stale `qpid` file once matched a *reused* pid and refused the next start (`QEMU 95211 already runs`) — `stop` now removes it; `ssh -f … &` and
  `nohup … &` over ssh keep the session open until every child closes its pipes (use `… > /dev/null 2>&1 < /dev/null &` and poll); `pkill -f "<pattern>"` inside an `ssh` command line matches the
  command line itself and kills the session, and the `[x]pattern` trick does not help when the same line later names the script — use `pgrep` + `kill <pid>`.
- **A checkout the harness edited is "dirty" and `run_fast_guest.sh` then wants `kf3-bins/<rev>-dirty`:** `scp` of a script into the box's checkout turned 30 arms into `NOTRUN`. `git checkout -- .` first;
  a docs/scripts-only commit on top of the binary's revision needs `QEMU_BIN=` (and is fine by the merge bar: say so).
- **Unclean `stop` after a reset-looping guest (GA104) leaves NTFS dirty:** the next boot sat at the "Windows Boot Manager" spinner for >10 minutes on a 4-vCPU box. Not a kayfabe result; do not read it as one.
