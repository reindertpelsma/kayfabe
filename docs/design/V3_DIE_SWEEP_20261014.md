# V3 die sweep — the Windows LTSC baseline under kayfabe on rented dies

**STATUS: LIVE, 2026-10-14 (night run, lane B; results fill in per die as they are measured).**
Goal (owner, night plan item B): boot the automated-test Windows 11 LTSC baseline (guest driver 580.88) under kf3 on vast
KVM rentals with dies other than the owner's AD104, with a screenshot per die (desktop + `nvidia-smi` in the guest), and
answer per die whether the host's BAR1 size (no Resizable BAR on vast) matters. MEASURED and INFERRED are kept apart.

## 2. Procedure (per die)

1. Rent (`vms_enabled=true`, KVM image, `--disk 150`), `/root/night/arm_autodestroy.sh <id> 240`, check `df -h /`, `/dev/kvm`, the GPU.
2. `box_facts.sh` (before the driver swap and after): PCI ids, BAR region sizes, Resizable-BAR capability, link, host BAR1 total.
3. `provision_full.sh` with D2/D3; READY line; `v3_gates.sh` (bare-metal gates on the same box: if these fail, the box is at fault).
4. Image (D4) to `/root/win`; `die_run.sh phase1`, then `die_run.sh phase2`; logs, kf3 `qemu.log` (filtered), screenshots back to git.

## 3. Results

### 3.1 GB206 (RTX 5060 Ti, Blackwell) — vast 55835565, UK, EPYC 7K62, 23 vCPU, 98 GiB, $0.162/h

- **Box facts [measured, `box_facts.sh`]:** `10de:2d04`; Region 0 64 MiB, **Region 1 (BAR1) 256 MiB**, Region 3 32 MiB;
  no Resizable-BAR capability in the VM's config space; link 16 GT/s x8 (cap 32 GT/s x16). Template driver 575.51.03 saw
  no device ("No devices were found"); after the swap the open 595.91.07 reports BAR1 Total 256 MiB, FB 16311 MiB.
- **Bare metal on the box [measured]:** `v3_gates.sh` at `bf510bdf4`: `V3_GATES_SUMMARY pass=9 fail=0 gate10=PASS`, births ok.
- **`display=on` is refused at realize on GB20x [measured]:** `kf3: realize refused: display=on: method vocabulary:
  NVCA7D_SET_CONTEXT_DMA_NOTIFIER is not derived` — QEMU exits before the guest runs. Cause [measured against
  `crates/kf-disp/data/classes-580.65.06.tsv`]: `kf_disp::engine::Vocab::resolve` requires 54 methods; 7 do not exist in
  the Blackwell classes `NVCA7D`/`NVCA7E` (all exist on Ada `C77D`/`C67E`):
  core `SET_CONTEXT_DMA_NOTIFIER`, `SET_NOTIFIER_CONTROL_OFFSET`; window `SET_CONTEXT_DMA_NOTIFIER`,
  `SET_CONTEXT_DMA_SEMAPHORE`, `SET_CONTEXT_DMA_ACQ_SEMAPHORE`, `SET_SEMAPHORE_CONTROL_OFFSET`,
  `SET_ACQ_SEMAPHORE_CONTROL_OFFSET`. Blackwell display has no context DMAs: the address goes in the method
  (`SET_SURFACE_ADDRESS_HI/LO_*`, as V3_DISPLAY.md §(C) already notes for surfaces). This is a **code gap in kf-disp, not
  a missing constant** (no lane-C item): the engine needs a second notifier/semaphore addressing mode for CAx.
  V3_FEATURE_GAPS H22 lists "Blackwell scanout backend unavailable"; what is new is that the refusal now stops the
  whole device at realize, so a GB20x Windows guest cannot use `display=on` at all at this revision.
- **Windows, `display=off` + QEMU std VGA (D8) [measured]:** phase 1 reached QGA in ~90 s; the new instance
  `DEV_2D04` was present **without a driver** (`CM_PROB_REINSTALL`, no driver key; the old AD104 instance is a phantom on
  class key `\0001`, `oem3.inf` = 580.88). The image's own package `nv_dispi.inf` lists `DEV_2D04` (and every die tried
  tonight, `inf_cover.ps1`); `pnputil /add-driver … /install` bound it (class key `\0002`) and it failed at once
  (`CM_PROB_FAILED_POST_START`, Code 43) — expected before the flag. With `EnableGpuFirmware=1` on `\0002` and the service
  key, in a NEW QEMU process: **still Code 43**; autologon reached the desktop on the std VGA (Basic Display), and
  `nvidia-smi` cannot reach the driver. Host BAR1 stayed at 4 MiB used of 256 MiB. kf3's last counter line:
  `family=Blackwell phase=Cold trapped=23 applied=21 refused=2 serviced=2 read_exits=27` — the guest never left Cold.
- **What the guest did [measured, kf3's first-20-writes log]:** an FSP EMEM packet `0xc0000000 0x1610de7e 0x20`
  (MCTP SOM|EOM; NVDM type `0x16` = `NVDM_TYPE_CAPS_QUERY`, vendor `0x10de`; payload `0x20` = sub-message
  `NVDM_TYPE_CLOCK_BOOST`: this is `kfspCheckForClockBoostCapability_GB100`, `ogkm-595.84 kern_fsp_gb100.c:139-162`),
  `QUEUE_TAIL=8`, `QUEUE_HEAD=0`, then the message-queue read side, then `0x110c00` (GSP `QUEUE_HEAD(0)`) and
  `0x1103c0` (GSP falcon `ENGINE` reset) toggled 1/0 repeatedly. kf3's FSP model answers only a COT packet
  (`kf-chip/src/fsp_gsp.rs:416-441`, by design since 2026-09-26) and leaves every other NVDM packet unanswered.
- **Hypothesis HB1 (INFERRED, not yet tested):** the Windows driver's FSP caps query times out without an
  `NVDM_TYPE_FSP_RESPONSE`, and the Windows RM's error path then never sends the COT packet that boots the GSP
  (Linux RM logs "FSP doesn't have clock boost capability" and continues). **Falsifier:** a full BAR0 trace showing a
  COT packet (`NVDM_TYPE_COT` 0x14) written after the caps query — then the stop is later and elsewhere.

## 4. Traps found on the way

- **`provision_box.sh`'s mirror floor rejects a fast box.** It times a download of `dists/jammy/Release` (~130 KB) and refuses
  below 200 kB/s; on vast 55835556 (Nevada) all three mirrors measured 120–165 kB/s that way while a 20 MB ranged download of
  the same mirrors ran at ~5 MB/s [measured]. The small file measures latency, not bandwidth. Worked around on the box copy
  (floor 50 kB/s); the script itself is not changed tonight.
- **The first ssh of a vast VM reaches a different host key** (the pre-boot endpoint), so a strict known_hosts refuses the VM
  once it is up; drop the entry.
