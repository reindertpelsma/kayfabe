# Mapping-walk gate: scope, completion ordering and bounded work

## Question, evidence and falsifiers

The coordinator reported ETW correlation on 2026-10-27 from boot 7321, branch `claude/etl-analysis-20261027`: consecutive completion intervals followed walk wall time, and one interval exceeded TdrDelay. This is supplied evidence, not an ENS10 host measurement. It motivates testing whether the CPU relay's global hold unnecessarily couples independent spaces. It does not identify the host publication/finish/vector-delivery ordering of each submitted guest packet.

CODE READ in `crates/kf-chan/src/user_turn.rs`: Obs harvests host GET/reference and Wb writes guest GET **before** Put asks walk_busy. The gate delays future source reads/publication. It does not by itself delay harvesting a published packet. MEASURED in ENS10 baseline tests at commit 309124774: `ens10_published_fetch_writeback_does_not_wait_for_any_walk_to_finish` and `ens10_processed_marker_is_observed_before_the_put_gate_with_lazy_on_and_off` pass on the original gate. They falsify the narrow hypothesis that the PUT gate alone prevents those observations. They do not establish end-to-end Windows interrupt delivery or GPU fairness. Guest DMA submission is not used as proof of native host-ring publication in this design.

The preregistered publication hypothesis is falsified by any A-only mapping operation mutating B's host mappings/rows, or by a publication through an affected/unknown source. The progress hypothesis is falsified by a lost completion/register wake, premature release of an overlapping request, stale life/target identity, changed descriptor publication, or failure of an existing lifecycle/model/property test. An exploration frontier cap is inconclusive and fails the test. No timer step may rescue a lost obligation.

## What the current gate protects

CODE READ in `crates/kf-qemu/src/mem.rs`, `device.rs`, `chan.rs`, `userpump.rs` and `crates/kf-chan/src/user_turn.rs`: the original Inbox predicate ORs the manager busy bit, every unsettled statement, queued splits and running split tokens. The VA loop includes pending/in-flight walks and an armed invalidate. It wakes the original waiter list only at VM-wide idle. That received/settled barrier also orders held RPC replies and must remain global for replies.

The USER adapter checks mapping readiness at three distinct sites: before fresh/cached PUT and observation/anchor creation, before guarded publication, and before source migration. Pointer mode still reads descriptors and admits a source even though it reads no PB. Scan/Window modes additionally read PB bytes. Translated `Rows::walk_pending` waits on missing rows while an applicable walk is pending. A MEM_OP split holds its requesting stream until its real prefix receipt, walk/apply and host invalidate complete. Source snapshots, ownership, permissions, exact bytes, software/allocation liveness, RAM generation and registration anchors remain separate admission checks.

The lifecycle obligations are unchanged (CODE READ in `docs/design/V3_USER_RING_LIFECYCLE_20261016.md` and the real Relay): I1 no PB read in Pointer; I2 exactly-once ordered entries; I3 SYNC_WAIT requires the processed-marker witness, not a walk wake; I4 registration reply/epoch and clean PUT anchor; I5 only lifecycle events change mode; I6 event-driven progress without a lost trailing wake; I7 validated bytes equal published bytes; I8 source/anchor reads stay below the PUT in use, with one fresh PUT per turn and generation-correct caching. A walk release is a scheduling hint, never a fabricated GPU receipt or mode transition.

## Phase 1: key by the host mutation target

CODE READ in `crates/kf-mem/src/vasmgr.rs`: every apply selects a table entry by VasKey and calls that entry's target. `VasTable::keys_for_pdb` selects **all** entries with the named PDB. CODE READ in `crates/kf-qemu/src/mem.rs`: each live guest-space target has its own Mirror rows/log/ledger and host VA space; recycling excludes live channels. The dependency here is the host mapping mutation domain. This does not assume that guest page-table pages never alias.

Two targets may share a guest root or subtree. A named-PDB walk selects all known matching roots; each selected target is held. An explicit own-space split mutates only its selected host target, even if a different target's guest tables share bytes. The other target's existing committed host rows do not change merely because guest table bytes changed. Waiting globally did not refresh that other target either. Thus a B source snapshot admitted through B's unchanged host rows remains eligible while only A is applied. This preserves existing guest-selected invalidation scope; it does not infer or add map requests from table writes. Shared GPU execution resources or an RM-global API lock may still serialize hardware activity, outside what a CPU source gate can prevent.

The production protocol is:

1. Statements publish their target and received sequence before enqueue. The bounded target map retains the latest outstanding sequence per key. PageDir, Unset and Retire name their exact target; BAR PDE changes and Sysmembar retain a global hold. Received, applied-through and RPC-settled are distinct milestones. After the VA worker processes a batch, a per-key hold can end only when its latest sequence is applied and its target is absent from the resolved active scope; this does not advance the global RPC reply barrier. A newer untaken statement retains its hold. Global/overflow statement holds stay conservative until RPC settlement.
2. Space splits retain `(ticket, token, target)` while queued **and** running, through host-invalidate acknowledgement. Queue-to-running transfer holds the queue and running metadata together. Multiple requests for the same key cannot release one another. PDB-form splits retain the conservative global hold through completion.
3. The VA worker publishes the union of pending, in-flight and target-settlement domains **before synchronous apply**, then updates it after completion. Publishing the scope also retires applied per-key holds that have no target work remaining, before the next unrelated synchronous apply starts. The snapshot is bounded. All-PDB, unresolved/missing PDB, unknown aperture and CPU-window targets stay global. This prevents a snapshot's omission of a target from being treated as proof of independence.
4. The real invalidate port is shared through an Arc; the vCPU still performs only its existing atomic writes and wake. Workers compare the armed request generation with the resolved snapshot. A new generation closes globally until resolved. The scope metadata is never locked by a vCPU. Worker metadata acquisition is try_lock; contention/poison closes conservatively.
5. USER turn entry, guarded publication and migration call the same scoped admission helper with the Record's retained VasKey. The real Translated serve supplies its Slot's trusted key to Rows and registers a scoped waiter. Diagnostic readers lacking target identity retain the aggregate predicate. The exact source snapshots and final publication guards remain intact.
6. Scoped waiters register before waking the VA worker. Ready scoped waiters are drained before entering synchronous apply and again after end-of-loop settlement. Registration rechecks readiness immediately: the USER decision can continue and a Translated pump re-owes its consumed guest-token edge, so a registration just after a drain does not wait for a foreign apply to return. RPC settlement still precedes legacy-overflow draining. A registration arriving after the release/take wakes the next loop. A late hint for a retired/reused token cannot authorize publication: allocation identity, live record and RAM/source generation are still revalidated. Reset drops the old scope and waiter identities under the existing reset exclusion.
7. Scope and waiter metadata are capped at 512 entries. Oversized target/split sets close globally without an unbounded worker scan. Statement overflow becomes a global hold until its sequence settles. Scoped waiter overflow uses the existing idle wake path. This is conservative under pressure; it does not allocate one object per ring attempt.

No GPU pause, guest-selected host address, vCPU lock, unmap-then-remap, forged completion, coalescing delay or timeout/poll adjustment is introduced. The default is hardwired; no boot flag is required.

## Phase 2: range certificates, not guessed disjointness

INFERRED from the walker diff interface: the changed VA set is unknown before the report. Phase 1 therefore holds the **entire affected target**, even if a source later proves disjoint. It does not satisfy a strict per-range relay admission goal within one space. A multi-target batch retains all of its requested target domains until the manager removes the batch; per-entry early release within that batch is not implemented. An all-space/global operation also intentionally retains a global hold. This is a documented limit, not a claim that all unaffected work is now independent.

A range implementation needs a complete stable diff certificate and a request/row epoch spanning descriptor, PB, source swap and publication. An optimistic source snapshot may publish only after its target's relevant pending operations are resolved and the bounded change log proves the **whole source footprint** unchanged. A changed/expired epoch, log overflow, unknown alias/target, unresolved operation or RAM generation requires retry/hold. Pointer descriptors need the same rule; it cannot inspect arbitrary GR shader operands on the CPU. Already executing GPU work continues under the owner's changed-VA contract: changed addresses can resolve old/new/fault, and never freed/reused unrelated memory. Existing post-invalidate retirement is retained.

A submitted GPU packet can intentionally address changed VAs: the owner permits old/new/fault there while refresh proceeds. Consequently “no packet ever references a changing VA” is not literally compatible with “refresh never pauses the GPU.” The enforceable relay condition is that source admission/publication cannot use a partially changed or unvalidated source snapshot. This design does not add a global drain to enforce the stronger interpretation.

## Independent cost lever: slicing work safely

DESIGN-ONLY: an apply continuation can cap each CPU visit by both verb count and a soft elapsed-work slice in the requested 100–200-ms range. It must stop only between authored host verbs, carry diff/ownership/undo state, complete the host invalidate for a committed prefix, and ACK only that prefix. Deferred frees remain after the relevant invalidate. Pending runs remain unacknowledged so the walker retries them. Rollback/refusal cannot expose an unowned page. No unmap/remap cycle is added.

This is not a hard gate-hold bound. A single RM call or GPU walk is not preemptible here and can exceed a slice. Furthermore, yielding and immediately re-holding a per-space gate does **not** shorten its continuous hold while unresolved same-space work remains. Releasing safely between prefixes requires the phase-2 range certificates, per-prefix wakes and unchanged-range admission. To promise an end-to-end hard bound would additionally require a bounded walker continuation and a bounded host RM interface; CPU tests cannot supply those host timing bounds. The next useful implementation is a continuation with overrun counters and commit-on-ACK tests, followed by range admission; simply opening a gate every 100 ms would violate safety.

## ENS10 addendum: why the ENS6 peak is not a 110-ms bound

Supplied evidence in the coordinator's ENS10 update on 2026-10-27: boot 7391 at ENS9 `64c50ad4`, with raised TDR thresholds, completed the Enscape arm without event 153 before the arm time limit. Its 2.43-s apply coincided with a 2.529-s completion gap; the reported reservation peak was 2,410,051 us. This supports late rather than lost completion for that arm; it is not an ENS10 hardware measurement or a timeout-based fix.

CODE READ in `crates/kf-host/src/channel/sparse.rs` and `sparse/slice.rs`: `layout_refresh_peak_us` is the sum of timed reservation/free verbs since `begin_layout_slice`, including the current interval. It excludes the rest of mapping, unmapping, diff processing and GPU time. `GpuMirror::begin_refresh` renews the shared allowance before retry; end-refresh retry spends the same allowance. Initial roots bypass this wrapper. `reset_sparse` also charges this counter outside the begin/end-refresh pair, so the label does not uniquely identify one apply. The map/unmap maxima in the supplied heartbeat are not individual reservation/free maxima and cannot bound this sum.

CODE READ in `crates/kf-host/src/sparse.rs`: admission error cleanup previously called `replace` for **every** newly sparse tile without checking either slice threshold. This is a genuine unbounded post-admission RM tail, separate from the CPU restore scan fixed in ENS5. Replacement also began all remaining children after an expensive release/child without rechecking time. The fixed 17-us verb cost in ENS6 tests left both holes undetected. The original claim of at most one replacement overshoot was false for admission error cleanup. Aggregate heartbeat maxima alone cannot prove which path caused boot 7391's particular peak.

ENS10 now defers complete-tile cleanup when its optional allowance is spent, retaining the reservation and putting its key on the existing validated cleanup queue. Original wanted bits are restored as before; retry rechecks occupancy and intent. Cleanup is not suppressed merely by RM backoff if budget remains. Inside a replacement, exhaustion stops starting children and invokes mandatory rollback; this is a slice deferral, not a fabricated RM refusal/backoff. A deferred sparsify returns partial progress instead of withdrawing earlier accepted coverage. No live block is released, and placement exclusion spans the entire replacement/repair.

MEASURED in ENS10 CPU run 2026-10-27, `slice-red.log` at commit `ca9fcbd57`: four new regressions fail on the old host implementation. In `slice-green2.log`, all 317 host library tests pass (3 existing ignored), including refusal cleanup and sparse-coverage invariants. The slow-release simulations reduce three/four 120-ms calls to a release and mandatory restore, **240 ms**, explicitly disproving a universal 110-ms expectation even after the fixes. Full-suite and mutation results are recorded with the final source seal in the ENS10 evidence directory.

Residual CODE READ limits: a replacement can require releases of already-created children plus original restoration; recycle can require a multi-call repair; none can safely abandon a half-released owner. `clear` before host-space reuse still converts its complete sparse geometry, and retirement/free and ordinary mapping verbs are not bounded by this admission slice. A single RM call itself is unpreemptible. Therefore the patch removes two admission budget bypasses, but does **not** establish a 100–200-ms maximum for the entire apply or continuous own-space hold. That remaining goal requires the continuation/range-certificate design above and host reservation-call timing; it must not be advertised as solved by this soft budget or by raising TDR thresholds.

## Latency decomposition addendum (DESIGN-ONLY, 2026-10-27)

The owner requests bounded per-USER-packet/turn timestamps to distinguish publication delay, host-marker observation and notification delivery. This instrumentation is **not implemented** in the sealed ENS10 source. Existing hold/reference/GET counters are not substitutes. The implementation must preserve missing or ambiguous evidence rather than manufacture a complete packet timeline.

CODE READ in `userpump.rs`, `user_turn.rs`, `user_storage.rs`, `device.rs` and `kf-trap/src/cpuintr.rs`: successful native publication returns from `publish_guarded` only after the private PUT and authored doorbell. Both `PumpIo::publish_*` and `Pump::publish` use it. `hw_words` and `user_ring_peek_one` read tagged references; `Marks::peek` extends only issued tags. A normal marker is `SET_REFERENCE` plus `NON_STALL_INTERRUPT`; its processing witness is not an arbitrary graphics shader's finish timestamp. Markers cannot be added inside an open method packet, and Pointer markers may be latched off. A missing marker must remain missing, not be inferred from GET or a guest SET_REFERENCE.

CODE READ in `kf-chan/src/worker.rs` and `device.rs`: ready-event dispatch calls `nsi_engine_edge` and can raise a vector **before** `relay.peek(Event)` samples a marker. Engine events are GPU-wide, not packet-specific receipts. `latch_and_deliver(v)` latches logical vector v; `deliver` signals physical MSI-X line 0 only for `Raise::Message`, while masking can retain pending logical bits. A logical latch, an eventfd write attempt, a successful eventfd notification and guest DPC entry are four different observations. A timestamp of an unrelated or earlier vector is not proof that a packet's completion was delivered.

The reviewable implementation contract is:

1. Use an explicit relay life/channel/generation/absolute entry or turn id, retained across retries and migration. Record first worker observation of queued demand or PUT (label which), first and subsequent native publications, and the existing covering marker id. Do not equate a FIFO descriptor with a Windows DMA packet. A turn whose source entry is not yet read can record demand but no invented descriptor identity.
2. Use the device heartbeat's `born` Instant as the diagnostic clock, bound before workers start. Tests inject nanoseconds. Export the clock origin/pair with heartbeat output. Record observations at the event, never reconstruct timestamps from an unrelated session's last wake. Do not add a GP_PUT poll or change markers, scheduling, admission or interrupt policy to improve the sample.
3. Keep a fixed-capacity pending table and last-N slow ring, with overflow/eviction/reset/canceled/no-marker counters. Markers cover batches of preceding entries; cap association work and report uncovered entries explicitly. Observe marker progress through `Marks::peek`, preserving its actual observation time. A marker observed after an earlier vector is an ordering/correlation case, not a zero or negative stage silently clamped into a complete record.
4. Record gate start/end intervals and cause (own-target walk, other-target/global fallback, split, scan budget, plus other/unknown). A cause change closes the preceding interval. These waits contribute only before a successful publication. An affected target's wait must not be relabeled as unrelated merely because another walk also exists.
5. Capture logical latch and actual notification separately. Worker-side packet history may lock only metadata never used by a vCPU. The generic `deliver` path can also run on a vCPU: publish bounded atomic notification sequence/time/line/eligible-logical-vector observations there; never acquire packet-history, channel or publisher locks, read USER storage or format a dump there. Held/masked vectors and failed signals remain incomplete notification records. Retain vector/sequence evidence and flag ambiguity from GPU-wide events or coalescing.
6. Publish `observe_to_publish`, `publish_to_marker_observed`, `marker_observed_to_notification` and end-to-end only when the **same** life/turn has an ordered, unambiguous correlation. Checked arithmetic must satisfy the telescoping sum. Report marker-observation delay as observed, not GPU-finish delay; host completion can predate its CPU sample. Notification-before-marker-observation records retain both observations and an explicit status. Do not silently choose a later interrupt to make a timeline fit.
7. Keep per-stage count/max and coverage/incomplete counts in heartbeat output. Trigger one bounded slow-history dump at the first >50-ms stage/end-to-end sample and another at shutdown; no fast-packet logging. Dump outside publication/IRQ metadata locks. Include still-pending slow records so a never-completing packet is not absent from diagnostics. Thresholds decide recording only.

Required failing-first tests before production hooks: exact stage-sum identity; gate delay changes observe-to-publish only; a slow GPU-marker stage leaves the first/third stages unchanged; a delayed notification changes only the third; vector before marker observation stays explicit/incomplete; GPU-wide unrelated vector cannot complete a record; masked-then-unmasked delivery uses the later successful signal; failed signal is not a notification; open packet/markers-off never gain a synthetic marker; retry preserves the oldest observation; migration/reset/token reuse cannot cross-associate; bounded overflow retains counters; first-slow and shutdown dumps are bounded and no fast packet logs; clock pairing uses the heartbeat origin. Each changed recording behavior needs at least two mutation killers, including native hook-composition checks. Full lifecycle/property regression remains required after instrumentation; this design alone does not fulfill the addendum.

## Diagnostics and proof boundary

CODE READ in `crates/kf-qemu/src/mem/walk_scope.rs`: fixed-size per-USER-record clocks and VM counters record own-space, split and global hold counts, cumulative time and maximum observed hold, plus other-space passes. Heartbeat `WALK_GATE` prints them. Hold time ends at a later probe/release/retirement; it is not a timestamp of GPU completion. Changed reference-word samples during an aggregate busy walk (`ref_changes_walk`, including guest SET_REFERENCE values) and guest-GET writeback admission contention during a busy walk are separately counted. Reference changes are not a count of completed packets. `get_wb_busy_max_us` measures observation-to-successful-writeback after such a contention. It does not prove that the walk caused the contention or bound the host-finish-to-Windows-vector interval. An “other-space hold” should be absent in narrowed mode; `other_allowed` counts the checks that passed.

The two new scope graphs (splits and applied statements) import the existing lifecycle support harness, which drives the production Relay/Fetch/Marks/Lifecycle parser. Its scope oracle reconstructs the real Inbox queue/running/ACK adapter. The publication hook supplies the same native predicate at the modeled publication/migration boundary. Existing source-guard tests bind all three native call sites; native waiter tests cover the release/register race. Scope arrival can interleave with every relay microstep. Exhaustive and deterministic seeded schedules check own-space safety, exact descriptor publication, I1/I8, migration, Window entry and actual exhausted-credit coverage. A fair suffix after finite own holds must terminate; a second test keeps a foreign hold unfinished throughout progress. The model's release hint/worker fairness and GPU service are explicit environment assumptions, checked separately where the production wake mechanisms are testable. No OS, RM, GSP or Windows wall-time guarantee follows from a scheduler-step bound.

The full existing model/property suites remain required. Mutation testing must separately distinguish behavioral native-predicate kills from source-composition guards; compilation errors are never counted as kills. Results, precise scope of exploration, limitations and source seal belong in the ENS10 evidence directory and lane report.

MEASURED in ENS10 standalone CPU simulation 2026-10-27: [the unwired recorder prototype](../../traces/ens10_20261027/latency-prototype.rs) passes 13 tests, including stage-sum identity and own-gate/scan-budget delay confined to observe-to-publish. This is not production hook coverage or a host timing result. The prototype assumes an explicit packet-to-notification association; native GPU-wide correlation, heartbeat-clock binding, partial-stage aggregation, complete gate-interval retention and first-slow pending-packet dumps remain to implement. It is an evidence artifact, not a drop-in native recorder.
