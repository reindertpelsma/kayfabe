# Required GPU check with an untrusted Vast host

[CODE READ] Owner rulings §F and §T.12 require untrusted replaceable compute, no account credentials on boxes, verified offers, and teardown only by owned IDs. This design adds a merge-queue availability/correctness signal. It never supplies release provenance. README.md is outside this change.

## Trust boundaries

| Actor / asset | Trust and authority | What compromise or lies can do |
| --- | --- | --- |
| GitHub OIDC issuer, HTTPS and RS256 | Trusted for repository, event, run and attempt identity; not workflow integrity | Issuer compromise defeats authentication |
| Reviewed Worker code, deploy account, singleton Durable Object ledger | Trusted capability and accounting boundary | Compromise exposes the account key and its full upstream authority |
| Vast control plane | Trusted for offer metadata, credit, instance identity and SSH coordinates | Wrong metadata, availability or billing; not proof of GPU execution |
| Rented host, its root and all returned bytes | Untrusted | Lie about success/failure, omit work, hang, exploit SSH client bugs; never feed an attestation |
| Merge-group workflow / proposed source | Changeable by the proposed merge | Spend only the Worker's fixed bounded capability, choose an SSH public key, forge the check; review/rulesets protect workflow changes |
| Trusted build job on a GitHub-hosted runner | Trusted origin of the transferred archive and expected SHA-256 within the reviewed workflow | Build inputs remain proposed code; hash is transfer integrity, not release provenance |
| Run job | Disposable GitHub-hosted runner, contents:read only, no OIDC or configured secrets | A client compromise has no cloud account secret or release authority; implicit read token and artifact access remain residual exposure |
| Dedicated Vast key in VAST_API_KEY | Worker secret only | Its upstream permissions can affect other account assets if stolen; prefix/ledger restrictions are code policy, not upstream isolation |
| Owner / repository rules / environment reviewers | Trusted deployment and merge authority | Can bypass failures; record the reason for any bypass |

[CODE READ: external documentation, checked 2026-10-21] [GitHub workflow selection](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows) selects the workflow at the event SHA/ref. [merge_group](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group) uses the merge-group SHA/ref. Thus the merge-group run uses the workflow from the merge commit; workflow identity cannot be pinned here. [OIDC claims](https://docs.github.com/en/actions/reference/security/oidc) document event_name, repository, ref, run_id, run_attempt, exp and nbf, plus custom audiences and id-token:write. Safety comes from the fixed Worker capability, not the token or a workflow-name comparison.

## Worker capability and state

[INFERRED: design] One SQLite-backed Durable Object, selected by a constant name, serializes rental reservations across all runs and cron. KV alone is insufficient for atomic admission. Persist a reservation and full TTL cost before creating an instance. Never retry an ambiguous create: retain a blocking reservation and report operator reconciliation. A crash between upstream creation and recording its returned ID cannot be made atomic across Vast and Cloudflare. Do not discover that instance by scanning the shared account or delete by label. The owner must reconcile it manually; TTL cannot guarantee cleanup of an unknown ID.

[INFERRED: design] Authenticate every public endpoint with RS256 against the fixed GitHub JWKS URL, caching imported keys, refreshing on key rotation and rejecting non-RS256 algorithms, wrong issuer/audience/repository, invalid/missing exp or nbf, and missing numeric run identity. Permit merge_group and workflow_dispatch only on refs/heads/master. Status and destroy also require the recorded run_id + run_attempt. The public request body accepts exactly ssh_public_key. No image, script, offer, budget, TTL, label, instance or account identifier is client selectable.

[INFERRED: design] Fixed policy: one live or unresolved reservation, verified VM offers, one GPU from an explicit model allowlist, reliability >=0.99, 120 GB disk, KVM image docker.io/vastai/kvm:ubuntu_cli_22.04-2025-05-16, <=0.50 USD/hour, 150 minute lifetime, kf-ci- labels. Owner-configured reserve defaults to 8 USD; default daily limits are 4 reservations and 5 USD estimated spend. Estimate charges the full TTL up front and is not refunded by early destroy. This bounds the admission estimate, not storage/network fees, rate changes or outage overrun. Reject nonfinite or missing prices/credit, and recheck returned offers instead of trusting search filtering alone.

[INFERRED: design] POST /rent returns the recorded id after creation, without waiting for boot. An identical run/attempt returns the same ID, including after destroy; a different key for that run is refused. The required SSH-key expression is single-line and length-bounded, and the onstart uses a quoted heredoc. The per-instance SSH attachment API bootstraps KVM guests, without adding an account-wide key. GET /status/{id} uses only a ledger ID, verifies its exact recorded kf-ci- label, and returns sanitized host/port only with Vast running status and published SSH coordinates. This is Vast's readiness indication, not an active TCP/SSH proof; the runner's bounded connection verifies actual reachability.

[INFERRED: design] Never enumerate account instances. Check ledger membership before any instance API call; validate the live label before mutations. A labelled but unrecorded ID supplied to an endpoint is reported and rejected without inspection or deletion. Automatic discovery of unknown IDs would require forbidden shared-account enumeration, so manual reconciliation belongs to the owner. Foreign instances, including other Codex leases, remain untouched.

[INFERRED: design] POST /destroy/{id} is idempotent. Cron every five minutes considers only ledger records, deleting expired instances or public GitHub runs that are completed/deleted. GitHub API errors do not imply deletion; TTL remains effective. Failed deletes retain the record for retry. Cron and explicit destroy log fixed event names and numeric IDs, never tokens, keys, raw upstream errors or bodies. Redirects are rejected; upstream calls and response sizes are bounded.

## Workflow and hostile output

[INFERRED: design] merge_group:checks_requested and workflow_dispatch trigger an always-run path decision. Manual dispatch requires the protected gpu-vast environment and master; rental requires environment approval for either event. No pull_request trigger, credential injection into the rented box, or Cloudflare deployment from GitHub.

[INFERRED: design] A build job packages the public source/scripts plus trusted-runner-built gate/raw-client binaries and emits the archive SHA-256 as an output. Rent creates a unique ed25519 key; transfer to run uses GitHub's artifact service with one-day retention. The artifact is ephemeral rental authentication only, never reused elsewhere; a public-repository reader may download artifacts, so this choice exposes rental access during its short lifetime. Before deployment the owner must confirm the artifact service's encryption-at-rest guarantees; public-key-only generation in run would require a separate pre-rent handoff/coordination design because job outputs are published only after completion. This must not be represented as private artifact storage. Local key files are mode 0600 and are removed; the public key alone reaches Vast.

[INFERRED: design] Run has exactly contents:read and runs on a GitHub-hosted runner. It verifies the archive against the build job's output, streams tar over SSH stdin with no agent/forwarding/X11, and uses a private known_hosts file, accept-new, explicit identity, BatchMode, connection/keepalive bounds and an overall timeout. Only capped SSH stdout comes back. Stderr is discarded to prevent uncapped hostile diagnostics. No SCP/rsync return channel, downloaded executables, summaries, environment files or job-output parsing of remote data. Print captured data under a fresh stop-commands token generated after capture so the host cannot know it.

[INFERRED: design] Verdict requires SSH rc=0 and exactly one exact nonce-bound final success marker (grep -x); duplicates, trailing bytes, missing newline and output truncation fail. The remote harness invokes the real bare-metal and guest suites and a deliberately failing control, refusing a control that passes. This detects broken harnesses, not a deliberate liar: the host knows the nonce and can fabricate success. An always-run final job explicitly succeeds for irrelevant paths and otherwise requires successful path/build/rent/run jobs; skipped, failed or cancelled prerequisites fail. Unavailable offers report a distinct failure, never a successful skip. Destroy is best effort; Worker TTL is the independent cleanup path for known IDs.

[INFERRED: design] A GPU-free CI test validates run permissions and the transitive dependency graph for attestation/release jobs across workflows. It also rejects artifact-transfer/reusable-workflow escape routes from the GPU workflow. Repository review/rulesets must protect the guard itself: a proposed workflow can remove its own checks. No release or attestation depends on GPU results or consumes its artifacts. Existing ci.yml's unittest discovery runs the guard; changed lines in ci.yml: zero.

## Deployment, rotation and owner decisions

[INFERRED: procedure] Deploy manually from a reviewed revision with the owner's local Cloudflare authentication. Set the Worker audience to its exact HTTPS URL, deploy the SQLite Durable Object migration and five-minute cron, then set VAST_API_KEY with the Worker secret command. Never add a Cloudflare token or Vast key to GitHub. Set the public Worker URL as a repository variable and configure gpu-vast environment required reviewers and deployment branch rules for master plus merge-queue refs. Enable merge queue and require the final GPU check by its exact name. Review workflow and broker changes before approval.

[INFERRED: procedure] Ask Vast whether restricted-permission keys can restrict endpoints/resources and use a dedicated least-privilege key where supported. Rotate by creating a replacement key, updating the Worker secret through the owner's credentials, checking mocked configuration and a separately authorized smoke run, then revoking the old key. Never clear the ledger to unblock a rental without reconciling existing instances. Worker compromise requires key revocation and account-wide owner inspection; the broker still never cleans foreign boxes.

[CODE READ: external documentation] [Cloudflare Free limits](https://developers.cloudflare.com/workers/platform/limits/) include CPU time, daily requests, subrequests, memory and response-size concerns. [Durable Object pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) permits SQLite-backed objects on Free with separate request/duration/storage limits. No request waits for GPU completion; WebCrypto verifies JWTs, JWKS are cached and upstream queries are small. The owner must confirm current plan limits and measure actual CPU use before enabling the check. Free-plan exhaustion, cron delays or upstream outages can delay teardown and overrun the estimate; configure alerts and an independent owner billing watch.

## Falsifiable verification plan (declared before implementation)

[INFERRED: H1] Mock tests can prove the fixed broker capability rejects unauthorized claims/keys and prevents shared-account operations. FALSIFIER: any gate mutant survives, kills fewer than two independently named tests, a foreign-instance API call occurs, or tests cannot first fail on the pre-implementation tree. Stop on that outcome.

[INFERRED: H2] The local workflow guard and hostile-output harness can enforce the reviewed workflow's separation and verdict handling. FALSIFIER: an added privilege/attestation dependency passes the guard, or malformed/duplicate/truncated hostile output passes. Test failures must precede implementation, and each behavior mutant must kill at least two tests. This does not claim resistance to a malicious replacement of the guard itself.
