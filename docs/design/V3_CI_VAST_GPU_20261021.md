# Vast GPU tripwire with a fixed paid-account capability

[CODE READ: owner rulings §F/§T.12 and amendments] Vast is untrusted, replaceable compute. The account is the owner's own PAID shared account. ## Stage 1 identity, explicit approval and commit binding

[INFERRED: design selected under Amendment 2] Only workflow_dispatch is enabled. The owner dispatches the workflow **from the PR's own branch**, supplying the PR number as the only dispatch input. The Worker accepts no rent parameters. It verifies the signed OIDC actor_id, repository, workflow_dispatch event, SHA, branch ref, run_id and attempt; the Actions-run API must agree on actor, triggering actor, event, attempt, head SHA and head branch. It queries PRs associated with that SHA and requires exactly one open same-repository PR whose head SHA equals the run/token SHA and whose branch equals the run/token branch. Current head binding means a push after dispatch refuses admission; no current head is silently substituted for the dispatched commit. The workflow checks its numeric PR input against the server-derived PR number before posting any status. Dispatching master, a merge ref, a fork, an ambiguous SHA or a run with a changed head fails closed. Labels/comments and automatic push/review triggers are deliberately absent: only this explicit owner action spends money.

[CODE READ: API basis] GitHub documents [Actions workflow-run metadata](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run), [PRs associated with a commit](https://docs.github.com/en/rest/commits/commits#list-pull-requests-associated-with-a-commit) and [PR reviews](https://docs.github.com/en/rest/pulls/reviews#list-reviews-for-a-pull-request). Dispatch inputs are not assumed to appear in the run API. SHA-to-PR association is filtered by exact head equality, not mere commit inclusion. An unknown commit or API 403/5xx is UNAVAILABLE; no API error authorizes spending. Three calls suffice for an ordinary single-page decision; pagination is bounded and fails closed when incomplete. A fresh approval/run check precedes admission; mutable approvals are not cached as immutable facts. OPTIONAL read-only public-repo GitHub API access uses a Worker secret, never a runner/box secret.

[INFERRED: approval] Numeric configured owner ID must match OIDC actor_id and any triggering_actor claim, plus run actor/triggering_actor IDs. Matching a login is insufficient. `review_or_author` allows either PR author ID equal to owner ID or an APPROVED owner review whose commit_id equals the dispatched PR head. A latest owner DISMISSED/CHANGES_REQUESTED review rejects both paths. `review_only` rejects author-only permission; `actor_only` deliberately omits content approval and is weaker. Missing content permission is NEEDS_APPROVAL, distinct from test FAIL. Keep the confirmed default; never fall back on API errors. Review/author and run data remain trusted GitHub API facts, while workflow contents are proposed code.

[CODE READ: OIDC] Verify RS256 with WebCrypto against `https://token.actions.githubusercontent.com/.well-known/jwks`; cache keys with expiry and refresh on rotation. Check issuer, exact Worker-URL audience, exp/nbf, repository and numeric run identity. [GitHub OIDC reference](https://docs.github.com/en/actions/reference/security/oidc) documents these claims. [Workflow selection](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows) selects the workflow at the event ref/SHA: a changed workflow is not a pinned identity. Safety is the fixed capability plus owner/content gate.

[CODE READ / MEASURED: deferred queue] GitHub's [queue guide](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) describes pr-2 builds including PRs #1 and #2, and limits availability to eligible organization repositories. The repo metadata reports public/User ownership. Amendment 2 explicitly defers merge_group. The owner must choose personal hosting versus organization transfer; a future queue path needs authenticated complete group membership and queue-time head snapshots, not ref-only parsing. No merge_group token is accepted in stage 1.

## Fixed capability and own-instance ledger

[INFERRED: policy] POST /rent accepts no body/query capability. Image, offer filter, script, lifetime and label are Worker-authored. Offers require verified=true, vms_enabled=true, rentable=true, rented=false, one GPU in an explicit model allowlist, reliability>=0.99, at least 120 GB disk, <=0.50 USD/hour including selected disk. Use the KVM image `docker.io/vastai/kvm:ubuntu_cli_22.04-2025-05-16`, TTL 150 min and label `kf-ci-<run_id>-<attempt>`. Recheck every returned field and reject nonfinite/absent values. No SSH key or runner-to-box channel exists. The fixed onstart embeds only the repo URL, validated lowercase 40-hex SHA and random 32-hex nonce, checks detached HEAD, invokes `scripts/ci/vast_box_main.sh`, then emits one final `KF_RESULT <nonce> PASS|FAIL <sha256-of-summary>` marker.

[INFERRED: state] Use one SQLite-backed Durable Object with a constant name, serializing whole operations; a process-local flag refuses concurrent requests while an operation is active. Persist a reservation before external create. KV eventual consistency is insufficient for single-live/counters/idempotence. Keep run+attempt tombstones, immutable SHA, nonce, exact script/label, known instance ID, price, timestamps, accrued estimated cost, remaining reservation, sanitized final verdict and SHA cache. A repeat token returns its same rental, even after deletion. No blind second create after an uncertain response.

[INFERRED: Amendment 2 reconciliation exception] Normally never list the account: inspect/log/destroy only ledger IDs and validate their exact live kf-ci label. An unresolved persisted create intent may use Vast's account list **only to reconcile that exact intent's label**; this is Amendment 2's express exception to the previous no-list rule. Discard all foreign entries. Adopt a unique candidate only if label, fixed image and full onstart match the intent; write its ID to the ledger before any inspect/delete. Missing fields, duplicates or a labelled-but-unrecorded instance without a matching prior intent are reported, never destroyed. An absent candidate leaves the reservation blocked: eventual absence does not prove a create failed. No foreign instance is inspected/destroyed or returned to a caller. Large/incomplete reconciliation responses refuse admission; owner reconciles manually.

[INFERRED: cleanup] GET /status/{id} is OIDC-authenticated to the recorded run; it returns sanitized state/verdict/log. On a final marker store the result then destroy the owned instance; cron every five minutes also reads final logs and destroys at TTL or a completed/deleted Actions run. API errors do not imply the run/instance disappeared. Failed destroy retains its reservation and retries later. POST /destroy/{id} remains an authenticated owner-run cleanup endpoint for testing/manual cleanup, not a runner job. Log fixed events and owned IDs only. No upstream errors/bodies, tokens, result URLs or account contents are echoed.

## Money, cache, kill switch and true worst case

[INFERRED: accounting] Check RENTING_ENABLED first on every request (default false). Disabled renting preserves status and cleanup. Invalid `OWNER_GITHUB_ID="REPLACE_ME"` and invalid public configuration fail closed. Before creation reserve price×TTL; require credit>=8 USD plus this reservation, at most one live/unresolved rental, default max 4 rentals/day, daily spend<=3 USD and rolling 30-day spend<=30 USD. Sum lifetime costs overlapping each window plus remaining full reservations, including pending creation and unacknowledged destruction. Settle actual estimated elapsed cost only at acknowledged delete; refund only unused allowance. Midnight/rolling boundaries and process restarts cannot reset an active liability.

[INFERRED: repeat billing] Authorize the run/content before returning a SHA cache hit. A completed same-SHA run returns its cached verdict without a rental. An active same-SHA run can be observed through a recorded same-run grant without another rental. Minimum same-SHA rental gap defaults to 24h. A dispatch with run_attempt=1 uses cache; a rerun of the explicit owner's dispatch (run_attempt>1, verified against Actions API) is the documented force mechanism. It still needs current content approval and the minimum gap, caps and owner checks. A replay of one signed run/attempt can never create a second instance, including after a forced run. No client `force` input exists. Unknown/unavailable cache does not authorize spending. Budget refusal is UNAVAILABLE_BUDGET, other infrastructure failure UNAVAILABLE; neither is test FAIL or a successful skip.

[CODE READ: billing semantics] [Vast instance management](https://docs.vast.ai/guides/instances/manage-instances) distinguishes stopped and destroyed instances; stopped instances retain storage and storage billing. Destroy releases resources. No provider guarantee that an onstart process exit, VM poweroff or container shutdown changes the control-plane billing state has been established. [INFERRED: belt and braces] Run the workload under an on-box timeout equal to the fixed TTL to end its own process group without any account key. This bounds honest local work, not GPU billing on a malicious box. Do not claim that exiting self-destroys the instance. Worker final-marker/TTL destruction is the billing cleanup mechanism. If documented provider stop-on-exit semantics become available, the owner may approve that additional stop; do not invent a keyless destroy API.

[INFERRED: actual worst case] One nominal allowance is 1.25 USD. At max compute price, an undestroyed instance can add 12 USD/day or 360 USD/30 days, plus storage/network fees; there is NO finite proven dollar maximum while automatic funding remains enabled. Shared account credit is a last-resort account-wide ceiling only if the owner disables automatic top-up/invoiced credit, confirms Vast overdraft/debt rules and keeps modest prepaid funds; 8 USD reserve is admission headroom, not isolation of dev leases. Revoke the dedicated Vast key if compromised; revocation also disables automated delete, so reconcile broker IDs manually. RENTING_ENABLED=false stops new admission without deleting the ledger. Ask Vast whether dedicated keys support resource/endpoint restrictions. Never add Vast or Cloudflare credentials to GitHub.

## Logs and hostile output

[CODE READ] [Vast show logs](https://docs.vast.ai/api-reference/instances/show-logs) is `PUT /api/v0/instances/request_logs/{id}`, requesting a bounded tail, returning a result_url for asynchronously uploaded logs. The documented example uses `https://s3.amazonaws.com/vast.ai/instance_logs/`. The endpoint describes a default tail of 1000 lines; no byte maximum, upload-ready delay or completeness guarantee is documented. Never equate the API response with ready/fresh log bytes.

[INFERRED: retrieval] Keep one outstanding result URL per ledger record. Validate HTTPS host/path against the documented S3 location, no userinfo/query/redirects; fetch without any Vast/GitHub Authorization header. A not-ready URL is revisited in later bounded status/cron requests; a successfully read snapshot can request a fresh upload on the next poll. Limit all requests by time/bytes and reject truncation, redirects, oversized payloads and malformed JSON. Missing markers while active produce a pending state with UNAVAILABLE verdict, then FAIL/UNAVAILABLE at terminal state/TTL. Raw bytes must decode as valid UTF-8 for a result; invalid bytes still display safely but cannot pass. PASS requires exactly one nonce-bound final marker as the last nonempty raw line, valid lowercase summary hash and no transfer truncation. Parse before sanitization/display capping. Any valid PASS or FAIL marker triggers cleanup. A host can intentionally fabricate a valid marker; accepted tripwire limitation.

[INFERRED: sanitizer] Replace invalid UTF-8 for display, remove ANSI/control characters except newline/tab, prefix lines starting `::` or `##[` with a visible marker, cap UTF-8 output using head+tail on character boundaries with an explicit dropped-byte count. Redact configured Worker secret values defensively. Return no result URLs, upstream API bodies, foreign instance IDs or executable artifacts. The runner prints log text under a fresh random stop-commands token generated after retrieval, and never writes it to summaries, GITHUB_ENV or GITHUB_OUTPUT. It parses only the Worker's sanitized verdict and server-derived admission metadata. The optional one-time box→Worker result POST fallback is documented ONLY as an owner option if Vast logs are unreliable; no fallback endpoint is built.
