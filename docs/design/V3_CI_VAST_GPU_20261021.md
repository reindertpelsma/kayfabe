# Vast GPU tripwire with a fixed paid-account capability

[CODE READ: owner rulings §F/§T.12 and amendments] Vast is untrusted, replaceable compute. The account is the owner's own PAID shared account. A lying box may falsify this check, burn its allowance, or emit hostile text; its output must never reach a release/attestation. Amendment 2b supersedes the prior confirmed mode: default `approval_mode=owner_push_or_review`. Root README.md stays unchanged.

## Stage 1 identity, explicit approval and commit binding

[INFERRED from source: design selected under Amendment 2b] Enable pull_request opened/synchronize/reopened/ready_for_review and workflow_dispatch. For PR events, the signed OIDC ref names exactly one PR (`refs/pull/N/merge`); Actions-run metadata must name that PR and its head SHA. Fetch the current PR and require its head SHA equal the Actions run's head_sha and its same-repository head branch equal the run branch. GitHub's PR OIDC SHA identifies the synthetic merge commit; it is validated as a SHA but is not substituted for the PR head. The box checks out the exact PR head verified by the API. Owner dispatch can run any same-repository branch, including a branch without a PR. The Worker derives and validates branch/SHA from the signed ref plus Actions run and commit API; an optional numeric PR input is only a runner cross-check of a unique exact-head associated PR. Dispatch bypasses the automatic base/path restrictions while preserving approval, draft and spending controls. No client parameter supplies the tested SHA. A push after the run snapshot causes refusal/supersession, never silent substitution.

[INFERRED: content approval] Default owner_push_or_review means (signed event actor_id is owner AND the run's numeric triggering_actor is owner) OR an owner APPROVED review bound to exactly that head SHA. A rerun by another user cannot inherit the owner-push path; it needs a fresh exact-head approval to use the review path. owner_push permits only the first path; review_or_author and review_only remain selectable with their documented author/review meanings; actor_only permits only numeric owner identity without content review. A latest owner DISMISSED/CHANGES_REQUESTED review rejects content approval rather than falling back. Git author names/emails are ignored, including spoofed owner text. Owner push also vouches for earlier contributors' commits already on the branch: explicit residual accepted by this design. Dispatch requires the owner identity; PR events from another actor may use exact-head owner review. No event-name, repository or run/head mismatch can use any mode to bypass identity binding.

[INFERRED from source: drafts and storms] RENT_DRAFTS=false is the default. Drafts return NEEDS_APPROVAL without spending even for an owner push; ready_for_review can admit the now-ready head. At most one live instance; a new run never becomes an automatic rental queue. When a verified current head supersedes the active head of the same PR, destroy the older owned rental and return BUSY without creating a replacement in that request. Cron also compares the active PR's current head so a lost webhook/runner does not retain superseded work. Cached same-SHA verdicts and spending caps remain first-class gates.

[CODE READ: API basis] GitHub documents [Actions workflow-run metadata](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run), [PRs](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request), [PRs associated with a commit](https://docs.github.com/en/rest/commits/commits#list-pull-requests-associated-with-a-commit) and [PR reviews](https://docs.github.com/en/rest/pulls/reviews#list-reviews-for-a-pull-request). Validate run actor/triggering actor IDs and pull_requests membership; do not assume dispatch inputs appear in the run API. PR admission reads run, PR, reviews and paginated files; dispatch also uses commit association and verifies the selected commit. Pagination is bounded and incomplete responses fail closed. Mutable approvals are refreshed before new admission. Amendment 2e replaces the stored GitHub secret: the runner sends its short-lived read-only job token in X-GH-Token on rent/status requests. The Worker uses it only as a bearer on fixed-host api.github.com GETs, never as identity, never in storage/logs/errors or to Vast/S3/JWKS. Missing tokens use public reads; invalid/expired tokens yield UNAVAILABLE, never authorization. Successful GET responses have a short bounded in-memory cache, without token-bearing keys, and mutable admission/head facts are refreshed. Cron has no retained runner token and uses public reads; TTL cleanup runs before GitHub reads, so rate limits cannot prevent that deadline delete. Errors yield UNAVAILABLE, missing content approval NEEDS_APPROVAL. The trusted issuer/API binds the event; the workflow selects PR activity types because event action is not a separate OIDC claim.

[INFERRED from source: Amendments 2c/2d] Automatic admission requires PR base.ref in ALLOWED_BASE_BRANCHES (default ["master"]) from the GitHub API. A signed/client-supplied base is not evidence. Other bases return NOT_ELIGIBLE with no spending; only numeric-owner dispatch may run those branches. Draft refusal remains the default. The Worker is the trusted path filter: read PR files for the admitted head, check the PR head again after pagination, and skip only a complete nonempty list whose every filename AND previous_filename matches a small exclusion list. Default PATH_SKIP_PATTERNS is ["**/*.md","docs/**","traces/**","archive/**","LICENSE*",".github/ISSUE_TEMPLATE/**"]. ci/vast-broker/** always runs, including its Markdown. Matching is case-sensitive, root-relative and refuses traversal, backslashes, empty/dot segments and suspicious names. Unknown paths and non-string/missing metadata run; malformed pagination, count mismatch and >=3000 files run; an HTTP/API failure is UNAVAILABLE. Renaming code to a document or a document to code runs. No client path list is accepted. A complete all-skipped list returns HTTP 200 NOT_NEEDED/PASS bound to the exact head and creates no ledger/budget entry. All other cases proceed through normal approval/caps; docs do not permit an identity bypass.

[CODE READ: OIDC] Verify RS256 with WebCrypto against `https://token.actions.githubusercontent.com/.well-known/jwks`; cache keys with expiry and refresh on rotation. Check issuer, exact Worker-URL audience, exp/nbf, repository and numeric run identity. [GitHub OIDC reference](https://docs.github.com/en/actions/reference/security/oidc) documents these claims. [Workflow selection](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows) selects the workflow at the event ref/SHA: a changed workflow is not a pinned identity. Safety is the fixed capability plus owner/content gate.

## Trust boundaries

| Actor / asset | Trusted authority | Hostile/compromised effect |
| --- | --- | --- |
| GitHub issuer and API | Numeric identity, run/commit/PR/review facts | Compromise defeats the approval gate |
| Owner, environment reviewers, branch protection | Deployment and approval | Can bypass the check; record a reason |
| Worker code/deploy account and singleton ledger | Admission, ownership, budgets, sanitization | Compromise exposes the upstream key's full permissions |
| Vast control plane | Offers, balance, instance identity and log API | Incorrect billing/status or missing/stale logs |
| Rented root/host and its output | UNTRUSTED | Fake PASS/FAIL, omit work, burn allowance, print hostile bytes |
| GitHub-hosted rent/poll job | OIDC transport and commit status | No connection to box; executes no returned code; no release authority |
| Proposed workflow and PR source | Changeable code | Can lie about tripwire results; cannot choose Worker image/script/caps |
| Dedicated Vast secret | Upstream account authority | Theft may affect shared assets; application policy is not upstream key isolation |

## Fixed capability and own-instance ledger

[INFERRED: policy] POST /rent accepts no body/query capability. Image, offer filter, script, lifetime and label are Worker-authored. Offers require verified=true, vms_enabled=true, rentable=true, rented=false, one GPU in an explicit model allowlist, reliability>=0.99, at least 120 GB disk, <=0.50 USD/hour including selected disk. Use the KVM image `docker.io/vastai/kvm:ubuntu_cli_22.04-2025-05-16`, TTL 150 min and label `kf-ci-<run_id>-<attempt>`. Recheck every returned field and reject nonfinite/absent values. No SSH key or runner-to-box channel exists. The fixed onstart embeds only the repo URL, validated lowercase 40-hex SHA and random 32-hex nonce, checks detached HEAD, invokes `scripts/ci/vast_box_main.sh`, then emits one final `KF_RESULT <nonce> PASS|FAIL <sha256-of-summary>` marker.

[INFERRED: state] Use one SQLite-backed Durable Object with a constant name, serializing whole operations; a process-local flag refuses concurrent requests while an operation is active. Persist a reservation before external create. KV eventual consistency is insufficient for single-live/counters/idempotence. Never persist any GitHub bearer. Keep run+attempt tombstones, immutable SHA, nonce, exact script/label, known instance ID, price, timestamps, accrued estimated cost, remaining reservation, sanitized final verdict and SHA cache. A repeat token returns its same rental, even after deletion. No blind second create after an uncertain response.

[INFERRED: Amendment 2 reconciliation exception] Normally never list the account: inspect/log/destroy only ledger IDs and validate their exact live kf-ci label. An unresolved persisted create intent may use Vast's account list **only to reconcile that exact intent's label**; this is Amendment 2's express exception to the previous no-list rule. Discard all foreign entries. Adopt a unique candidate only if label, fixed image and full onstart match the intent; write its ID to the ledger before any inspect/delete. Missing fields, duplicates or a labelled-but-unrecorded instance without a matching prior intent are reported, never destroyed. An absent candidate leaves the reservation blocked: eventual absence does not prove a create failed. No foreign instance is inspected/destroyed or returned to a caller. Large/incomplete reconciliation responses refuse admission; owner reconciles manually.

[INFERRED: cleanup] GET /status/{id} is OIDC-authenticated to the recorded run; it returns sanitized state/verdict/log. On a final marker store the result then destroy the owned instance; cron every five minutes also reads final logs and destroys at TTL or a completed/deleted Actions run. API errors do not imply the run/instance disappeared. Failed destroy retains its reservation and retries later. POST /destroy/{id} remains an authenticated owner-run cleanup endpoint for testing/manual cleanup, not a runner job. Log fixed events and owned IDs only. No upstream errors/bodies, tokens, result URLs or account contents are echoed.

## Money, cache, kill switch and true worst case

[INFERRED: accounting] Check RENTING_ENABLED first on every request (default false). Disabled renting preserves status and cleanup. Invalid `OWNER_GITHUB_ID="REPLACE_ME"` and invalid public configuration fail closed. Before creation reserve price×TTL; require credit>=8 USD plus this reservation, at most one live/unresolved rental, default max 4 rentals/day, daily spend<=3 USD and rolling 30-day spend<=30 USD. Sum lifetime costs overlapping each window plus remaining full reservations, including pending creation and unacknowledged destruction. Settle actual estimated elapsed cost only at acknowledged delete; refund only unused allowance. Midnight/rolling boundaries and process restarts cannot reset an active liability.

[INFERRED from source: repeat billing] Authorize the run/content before returning a SHA cache hit. A completed same-SHA run returns its cached verdict without a rental. An active same-SHA run can be observed through a recorded same-run grant without another rental. Minimum same-SHA rental gap defaults to 24h. A dispatch with run_attempt=1 uses cache; a rerun of the explicit owner's dispatch (run_attempt>1, verified against Actions API) is the documented force mechanism. It still needs current content approval and the minimum gap, caps and owner checks. A replay of one signed run/attempt can never create a second instance, including after a forced run. No client `force` input exists. Unknown/unavailable cache does not authorize spending. Budget refusal is UNAVAILABLE_BUDGET, other infrastructure failure UNAVAILABLE; neither is test FAIL or a successful skip.

[CODE READ: billing semantics] [Vast instance management](https://docs.vast.ai/guides/instances/manage-instances) distinguishes stopped and destroyed instances; stopped instances retain storage and storage billing. Destroy releases resources. No provider guarantee that an onstart process exit, VM poweroff or container shutdown changes the control-plane billing state has been established. [INFERRED: belt and braces] Run the workload under an on-box timeout equal to the fixed TTL to end its own process group without any account key. This bounds honest local work, not GPU billing on a malicious box. Do not claim that exiting self-destroys the instance. Worker final-marker/TTL destruction is the billing cleanup mechanism. If documented provider stop-on-exit semantics become available, the owner may approve that additional stop; do not invent a keyless destroy API.

[INFERRED from source: actual worst case] One nominal allowance is 1.25 USD. At max compute price, an undestroyed instance can add 12 USD/day or 360 USD/30 days, plus storage/network fees; there is NO finite proven dollar maximum while automatic funding remains enabled. Shared account credit is a last-resort account-wide ceiling only if the owner disables automatic top-up/invoiced credit, confirms Vast overdraft/debt rules and keeps modest prepaid funds; 8 USD reserve is admission headroom, not isolation of dev leases. Revoke the dedicated Vast key if compromised; revocation also disables automated delete, so reconcile broker IDs manually. RENTING_ENABLED=false stops new admission without deleting the ledger. Ask Vast whether dedicated keys support resource/endpoint restrictions. Never add Vast or Cloudflare credentials to GitHub.

## Logs and hostile output

[CODE READ] [Vast show logs](https://docs.vast.ai/api-reference/instances/show-logs) is `PUT /api/v0/instances/request_logs/{id}`, requesting a bounded tail, returning a result_url for asynchronously uploaded logs. The documented example uses `https://s3.amazonaws.com/vast.ai/instance_logs/`. The endpoint describes a default tail of 1000 lines; no byte maximum, upload-ready delay or completeness guarantee is documented. Never equate the API response with ready/fresh log bytes.

[INFERRED: retrieval] Keep one outstanding result URL per ledger record. Validate HTTPS host/path against the documented S3 location, no userinfo/query/redirects; fetch without any Vast/GitHub Authorization header. A not-ready URL is revisited in later bounded status/cron requests; a successfully read snapshot can request a fresh upload on the next poll. Limit all requests by time/bytes and reject truncation, redirects, oversized payloads and malformed JSON. Missing markers while active produce a pending state with UNAVAILABLE verdict, then FAIL/UNAVAILABLE at terminal state/TTL. Raw bytes must decode as valid UTF-8 for a result; invalid bytes still display safely but cannot pass. PASS requires exactly one nonce-bound final marker as the last nonempty raw line, valid lowercase summary hash and no transfer truncation. Parse before sanitization/display capping. Any valid PASS or FAIL marker triggers cleanup. A host can intentionally fabricate a valid marker; accepted tripwire limitation.

[INFERRED: sanitizer] Replace invalid UTF-8 for display, remove ANSI/control characters except newline/tab, prefix lines starting `::` or `##[` with a visible marker, cap UTF-8 output using head+tail on character boundaries with an explicit dropped-byte count. Redact the Vast binding and the current request's GitHub bearer before displaying or persisting logs; redact known GitHub-token-shaped strings defensively. No GitHub bearer is retained for later requests or cron. Return no result URLs, upstream API bodies, foreign instance IDs or executable artifacts. The runner prints log text under a fresh random stop-commands token generated after retrieval, and never writes it to summaries, GITHUB_ENV or GITHUB_OUTPUT. It parses only the Worker's sanitized verdict and server-derived admission metadata. The optional one-time box→Worker result POST fallback is documented ONLY as an owner option if Vast logs are unreliable; no fallback endpoint is built.
