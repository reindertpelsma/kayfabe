# Guest GPU utilisation: the `report-utilization` device property (design note)

**STATUS: LIVE, 2026-11-17 (implemented GPU-free, owner decision 2026-11-17, `docs/OWNER_RULINGS.md` §AV; NOT run on hardware: every sentence marked [inferred] or [not measured] below is a hypothesis with a falsifier in section 9).** Owner decision: build it; a device property, default ON, users may turn it OFF to avoid host leakage; read-only and one way: no guest-supplied byte is ever sent to the NVIDIA host/driver for this feature, the host read is a fixed host-authored request.

Evidence labels used throughout (a design note written before the code is `/root/night/UTIL_FLAG_20261117.md`; this document is the folded, as-built version): **[ogkm]** read in the pinned oracle trees (`third_party/ogkm-580` = 580.159.04, `b81d58ee`; `third_party/ogkm-595` = 595.84, `722ae845`, fetched with `scripts/ci/fetch_oracles.sh` exactly as CI does), **[measured]** a logged run (path named), **[inferred]** my reading, not tested.

## 1. Which RM controls carry utilisation

The stack, bottom to top: the guest's NVML (`libnvidia-ml`, closed source) and `nvidia-smi` ask the guest's kernel RM; the guest's kernel RM talks to the emulated GSP with `GSP_RM_CONTROL` RPCs. **Function 76 IS `GSP_RM_CONTROL`** [ogkm: `src/nvidia/inc/kernel/vgpu/rpc_global_enums.h:86`, `X(GSP, GSP_RM_CONTROL, 76)`]. The census line `GSP rpc UNSERVICED Unserviced { code: 76 }` is therefore "a `GSP_RM_CONTROL` no link answered" and carries no control id: `kf_gsp::Unserviced` holds `code` and `sequence` only (`crates/kf-gsp/src/boot.rs:341`; the id is attached by the `kf_rm::unserviced` ledger and by the `GSP REFUSED fn76/<cmd>=0x56` lines). So the logs name the refused controls, and the list of refused ids in `evidence/refused_rm_controls_h2.txt` (58 ids, Windows image-B session) is the thing to read, not the "76".

Two producers of the same numbers exist in the open headers, and both are derivable. Nothing in the open sources says which one the closed NVML reads on a given OS; the table separates what a committed log shows (paths named) from what is only the header's say.

| carrier | control / object | ogkm | what it is | guest evidence |

What this means in plain words: **Linux** (the guest this project measures most): the kernel half of NVML's utilisation path is carrier A and B, both in the open headers; which of them `utilization.gpu` reads on Linux has **not been measured** (no Linux guest run asked for utilisation while a census was recorded). **Windows**: carrier A's POLL is measured to be asked for `utilization.gpu`; carrier C also arrives with it and cannot be answered. So the design serves A and B from one host reading, and the hardware plan (section 9) begins by measuring which of A/B/C each OS actually consumes, with a falsifier for each.

Chain effect worth knowing (read in ogkm): `gpushareddataConstruct_IMPL` runs `_gpushareddataRequestDataPoll` under `NV_ASSERT_OK_OR_RETURN` (`gpu_user_shared_data.c:~100`, `_gpushareddataSendDataPollRpc` :~345), so while `0x20800aff` is refused the guest's user `RM_USER_SHARED_DATA` alloc with a non-zero mask fails, which is a candidate reason NVML turns to its other (refused) paths. Serving INIT and POLL without a publisher was rejected by `sweep.rs` ("an NV_OK would promise a page that is never written"); this design adds the publisher, so the argument no longer stands (it is folded there).

## 2. The request and response layouts: generated, never typed

`tools/util-probe/probe.c` is compiled (gcc, the compiler is the parser) against each ogkm tag's public SDK headers and prints `sizeof`/`offsetof`/macro values; `tools/util-probe/generate.py all` fetches the 21 tags from 570.86.15 up (sparse, shallow, 5 s each), writes one receipt per tag (`traces/util_layout_20261117/<tag>.tsv`, with commit and output hash in `sources.json`) and emits `crates/kf-abi/src/utilization_generated.rs`. `check` recompiles the two PINNED oracle trees and fails unless they equal their receipts and the committed Rust equals a fresh `emit` (`crates/kf-abi/tests/utilization_layout_is_current.rs`; skipped without the oracle unless `KF_REQUIRE_ORACLES=1`, the `stripped` job sets it).

What the compiler printed (all 19 probed tags; **[ogkm]**): the GPUMON geometry is identical at every tag (params 55888 B, sample 776 B, 72 samples, engine record 128 B, `util` at 0, `procId` at 8; the matrix's own `CTRL_LIMITS_..._PERFMON_UTIL_BUFFER_SIZE` agrees: 55872 = 776 x 72 from 570.86.15 up, and the code cross-checks the two at runtime). **The RUSD layout is NOT stable**: `perfDevUtil` is at 1976 for 575.x/580.x and at **1992** from 590.48.01 (595.84, 610, 615 as well), and `sizeof(NV00DE_SHARED_DATA)` is 2464 / 2600 / 2608 / 3144 / 3152 / 3184 by tag. 570.x has an older INIT struct (no `bInit`, a compile error in the probe, recorded as `unprobeable`) and gets no row. The SET_DATA_POLL interval field is `pollFrequencyMs` before 595 and `pollIntervalMs` from 595: kayfabe never reads it (the guest's interval is ignored), so the probe does not name it. Consequence, enforced in code: **exact driver-version membership**. The guest driver version (`DriverAbiTable::driver_version()`, the Windows build keyed as its twin tag) must have a row, and the matrix's measured GPUMON size must equal the derived one, or the control is not claimed (it reaches the ledger and is refused as today).

## 3. The host source

One unprivileged host RM control on the existing session: `kf_host::HostRm::raw_control(subdevice, 0x20802096, payload)`, flags `0x50008` (NON_PRIVILEGED), the same call `nvidia-smi` makes on bare metal as an ordinary user. The request is **fixed and host-authored**, the shape the RM's own accounting uses (`gpu_acct.c:497-502`): zeroed buffer, `type = 2`, `bufSize = sizeof(samples)`, `tracker = 0`, `count = 0`. No byte of any guest message reaches it, and the reply is parsed by this crate, never forwarded. It goes through `HostAbi::control_carry` like every host control: a new `HOST_CONTROLS` row (`MeasuredOpaque`, size from the generated table; valid in the encoded interval `[580.65.06, 581)` and at the listed host tags whose layout the generator probed and whose size equals it, a unit test checks each listed tag against its receipt). A host outside that set gets `NoHeader` by name and the feature reports "no host source" (logged once, the guest sees `[N/A]` exactly as today). A host with MIG/SMC enabled answers `NV_ERR_NOT_SUPPORTED` (the header says "not supported with SMC enabled"): the same outcome. **At realize** (one reading on the realize thread, never a vCPU) the device learns whether the host has a source at all: a permanent refusal (`NV_ERR_NOT_SUPPORTED`, insufficient permissions, a host driver whose layout was not derived) logs one line and the device behaves exactly as with the property off; a transient failure or an empty first reading keeps the feature on.

If the host refuses the control, or returns a ring with no sample, **no unprivileged source exists on that host and the feature stays off for it** (not invented, not zero-filled). That is the STOP condition in the task; it is not met here because the control is non-privileged by its flags [ogkm], but whether a GSP-RM host actually fills the ring for a client that never started accounting is **[not measured]** (section 9, falsifier F1).

## 4. Sampling: a background sampler, never a host call on a vCPU or in a request

- One thread, `kf3-util`, per device with the flag on. Period 250 ms; the code enforces a floor of 100 ms between two host calls (`SAMPLE_PERIOD_MIN`), whatever a caller asks. The host call is made with **no lock held** (the result is stored under a short `Mutex` that only the register drainer and this thread take; no vCPU thread touches it, and the trap path never sees it).
- **Cadence follows asking.** While a guest asked within the last 10 s (a GPUMON request, or an active RUSD poll with a linked page) the sampler reads every 250 ms; otherwise every 1 s, so that a one-shot `nvidia-smi` is answered from a cache at most a second old (a cache that is 3 s old is not served). A host read therefore happens at most 4 times a second and at least once a second, **independent of how often or how fast the guest asks**: the guest controls only which of the two rates applies, and there is no guest-reachable path to a host call (the chain holds no host handle). That is the per-guest rate limit, structurally.
- The reply to a guest request is built from the cached snapshot (up to 72 of our own samples, the newest at most 3 s old); a stale or empty ring is refused as today. GPUMON requests are additionally limited to 16 replies per second (token bucket), an excess is refused `0x56` and counted: the reply is 55,888 bytes and a flood must not make the drainer build thousands of them.
- RUSD publication runs on the **register drainer** (never a vCPU) at the sampler's cadence, after the drainer's own heartbeat pattern: an atomic compare when nothing is due; the write is 56 bytes (below) with `RamMap::write_gpa` (guarded, refuses anything that is not registered guest RAM). The drainer never calls the host for this.
- The host sample is accepted only if its own timestamp advanced; a host RM that stops producing samples makes the snapshot age out (3 s): GPUMON then refuses, and a RUSD record already written is invalidated (its timestamp word set back to `RUSD_TIMESTAMP_INVALID`, once), so the guest sees N/A, not a frozen number (security review of PR #459, F3). A host timestamp that goes BACKWARDS is a host timer restart (a host GPU reset) and is accepted as a new baseline; only an equal one is a stall.

## 5. What is exposed

- **Exposed:** the physical GPU's whole-device load, quantised to whole percent, clamped to 0..100: graphics/compute engine busy (`gpu`, from `gr.util`), memory-bandwidth busy (`memory`, from `fb.util`), and the NVENC / NVDEC / NVJPG / NVOFA engine busy values. Units: GPUMON carries pct x 100 (a multiple of 100 here), RUSD carries percent. Sampling period for the RUSD engine records is our own (250 000 us).
- **Not exposed, ever:** any process id, name or OS pid pointer of the host's samples (`procId`/`subProcessID` are the control's own "no process" value `NV2080_GPUMON_PID_INVALID`, names zero, pointers zero), the host's timestamps (our own monotonic ns), vGPU scale (0), power, clocks, P-state, thermals (their RUSD timestamps stay `RUSD_TIMESTAMP_INVALID`, the header's own "not available or not supported on this platform").
- **Unavailable is encoded as the control's own "not available", never as zero:** RUSD: the record's `lastModifiedTimestamp` stays `0`; GPUMON: the control is not answered (refused `0x56`, what the guest already handles). A per-engine zero means "the host reports 0", and the control has no distinct per-engine "absent" encoding to use; an engine the guest's own engine list does not contain is not queried by NVML [inferred].
- ⚠ **Plainly: on a shared physical GPU this is a cross-tenant load side channel.** Every VM on the GPU sees the same whole-device numbers, which move with what other tenants run: it tells a guest when a neighbour is busy, at 4 samples per second, 1 % resolution, up to 6 engines. That is why the flag exists and why it is a device property the host operator controls (the guest cannot turn it on or off). The numbers are the physical GPU's, **not this VM's own**: this reverses the earlier open direction (`OWNER_RULINGS.md` §W bullet "RUSD and `utilization.gpu`": "this VM's own, never host-wide"), by the owner's 2026-11-17 decision, for utilisation only. Operators who share a GPU between tenants may prefer `report-utilization=off`; for isolated GPU sandboxes `on` is fine (owner, 2026-11-17: it rarely weakens multi-tenancy, and the default stays on).

## 6. The flag, the plumbing, the ABI, and OFF

- Device property `report-utilization=on|off`, `DEFINE_PROP_BOOL`, **default on**, declared in `qemu/hw/misc/kf3/kf3.c` next to `windows-support`; `kf3_realize` gains `report_utilization` after `windows_support`; **KF3_ABI 33 -> 34** (`kf3.h`, `ffi_unsafe.rs`, mirrored and pinned by `crates/kf-qemu/tests/wire_mirror.rs`); `Config::report_utilization`. Never an environment variable, never read from the guest.
- ON: the chain seats `utilization::UtilizationPolicy` (kf-rm) with a shared `UtilizationState`; the device starts the sampler thread and gives the drainer the publisher. OFF: `ObjectLinks::utilization` is `None`, no thread is started, no host call is ever made, and the three controls are not claimed, so `0x20802096`, `0x20800afe` and `0x20800aff` reach `InitTablePolicy`/the ledger exactly as before (refused `0x56`, counted in the unserviced ledger). A test builds the real chain both ways and compares the replies byte for byte.
- No new CLI, no env flag. Documented in `docs/howto/installing.md` (property table + a "GPU utilisation in the guest" paragraph); no design notes there.
- W349REFUSE and the derived-row rule: the link claims only the ids derived from ogkm for a guest version that has a generated row; for a size it does not know, a serialized envelope, a wrong type, or a stale ring it returns `None`, i.e. exactly the refusal path of today. Nothing else changes: the siblings `0x20802087` (video perfmon), `0x2080a097`, `0x20810108` stay refused (tests).

## 7. Hostile-guest analysis (for the security review)

Assume the guest userspace and the guest root are hostile, and that the guest can send any bytes in any GSP message (a modified kernel module is enough).

| surface | what the guest controls | bound / why it is safe |
|---|---|---|
| `0x20802096` request | the envelope, `type`, `bufSize`, `count`, `tracker` and the whole 55,888-byte buffer | `type` and `bufSize` must equal the generated constants or the request is refused; `count`, `tracker` and every other byte are **never read**. The reply params are rebuilt from zero by kayfabe (fixed size = the request's own declared size; no field is echoed). The reply is built from the cached snapshot: **no host call happens in response to a request.** Rate: 16/s token bucket |
| `0x20800afe` INIT | `bInit` (0 or 1 only, else refused), `physAddr` | `physAddr` is stored, never dereferenced at INIT. It must be non-zero, 4 KiB aligned and below 2^52, else refused (`None`). Publication only ever writes `[physAddr + perfDevUtil, +48)` inside the first page (generated offsets: 1976 or 1992 + 48 < 4096, a test pins it for every row) through `RamMap::write_gpa`, which refuses anything that is not registered guest RAM and splits nothing past a block. A guest can therefore make kayfabe write **at most 56 bytes of utilisation numbers, 4 times a second, into a guest RAM page it named**: guest-owned memory the guest could already write; no host address, no device state, no other VM. Re-INIT replaces the address; INIT with `bInit=0` clears it and stops publication |
| `0x20800aff` POLL | `polledDataMask` (u64), the interval | only bit `NV00DE_RUSD_POLL_PERF` is ever consulted; every other bit is accepted and ignored (their RUSD records stay "invalid", nothing is written for them). The interval is ignored: the cadence is ours |
| flood / replay | any of the three, any rate | INIT/POLL are O(1) atomic stores; GPUMON is rate limited; the sampler's cadence is 250 ms or 1 s with a 100 ms floor in code, so the host sees at most 4 calls/s as configured (10/s is the floor's bound) whatever the guest does; replay of an old INIT after `bInit=0` just re-arms a write into a page the guest named |
| what is emitted to the guest | 6 percentages, our timestamps, constants | fixed-size, bounded; no host pointer, pid, name or uuid; no value the guest chose |
| what reaches the host | **nothing from the guest.** The one host request is a constant | the host reply is parsed field by field (offsets from the generated table, `timeStamp` and `util` of the newest sample only), clamped, and discarded; the rest of the 55 KiB reply is dropped |
| locks / threads | none | the chain runs on the drainer (as every link); the sampler holds no kf lock across the host call; no vCPU thread reaches any of it; a panic of the sampler thread only ages the snapshot out (it is not a fail-closed service thread, and it is not needed for anything else) |
| a lying identity | a guest can claim any driver version at fn 1 | with `guest-driver` DECLARED the link is keyed on that version. With it UNDECLARED (defaulted) the fn-1 re-selection rebuilds the chain, and with it the link, for the version the GUEST claims, so the guest picks which generated row applies. That is bounded, not refused: the choice is only among rows that exist (exact membership; an unknown claim gets no link), both RUSD offsets (1976 and 1992) lie inside the first page of guest RAM the guest named (`rusd_is_coherent`, pinned for every row), and a wrong claim only moves a 56-byte write inside the guest's own page. Refusing when the claim differs from the host's own driver version was considered and not done: a guest driver older or newer than the host's is the supported case. A reset or a rebuild for a version without a row clears the link before anything else (F1) |

Residual risks, stated: (1) the side channel above is real and is the point of the flag; (2) the sampler's host call takes the host RM API lock briefly (the control is not `API_LOCK_READONLY`): one short acquisition per second for the whole life of a VM with the property on (the idle cadence), and 4 per second for as long as a guest is asking or has a linked, polled RUSD page (the page counts as asking until it is unlinked or reset); its cost to map/channel verbs on the host is **[not measured]** (F2); (3) RUSD publication relies on `memdescGetPhysAddr(AT_GPU)` being a guest-physical address, true today (no guest vIOMMU: `mem.rs` "the vIOMMU seam"; the device refuses to start behind one), to be re-checked if a vIOMMU lands.

## 9. Hardware confirmation plan (NOT run; nothing was rented)

One Vast KVM box (`vms_enabled=true`, KVM image, check `df -h /`), an RTX 4090 or 3070 as in the earlier gates; strictly serial; Linux guest first.

0. **Which carrier does NVML read?** Flag ON, guest idle then `nvidia-smi dmon -s u -c 20` and `nvidia-smi --query-gpu=utilization.gpu,utilization.memory,utilization.encoder,utilization.decoder --format=csv -l 1` while `gpu_burn`/`cuda_ladder.sh` runs on the *host side of the same GPU* and then in the guest; record the kf3 log lines (`rpc-trace fn=76`, the new `UTIL` counters) and `strace -f -e ioctl` of nvidia-smi is not available in the box payload, so the discriminator is the census: which of `0x20800aff`+RUSD page reads, `0x20802096` or a still-refused id appears per query.
1. Flag ON, CUDA load in the guest (`cuda_ladder.sh` stage with a long kernel), host `nvidia-smi dmon` alongside: guest `utilization.gpu` must track the host's within 10 percentage points after 3 s, rise above 80 under a saturating kernel, and fall to under 10 within 3 s of stopping. Repeat with the load on a second VM on the same GPU: the first VM's reading must rise too (the side channel exists as documented; this confirms the flag's reason).
2. NVML probe (python-pynvml or a 20-line C program against `libnvidia-ml`): `nvmlDeviceGetUtilizationRates`, `...GetEncoderUtilization`, `...GetDecoderUtilization` while a CUDA load runs, flag ON; flag OFF run: all four `NVML_ERROR_NOT_SUPPORTED`/`N/A` and the kf3 log shows `0x20802096`, `0x20800afe`, `0x20800aff` refused and counted, **no `kf3-util` thread, zero host `0x20802096` calls** (the sampler counters: `util[...]` on the 2 s status line is absent).
3. `nvidia-smi -q` diff between flag ON and OFF: only utilisation fields (and no field that was N/A may become a wrong value: power, clocks, thermals, P-state stay N/A).
4. Windows lane (`windows_gate.sh` then `nvidia-smi.exe --query-gpu=utilization.gpu`), same two arms.
5. Safety measurements: vCPU exit latency histogram and CUDA ladder wall time ON vs OFF (the sampler must not move them beyond noise), host `0x20802096` call latency distribution, drainer pass time with the publisher.

**Falsifiers (any one falsifies the design as stated):**
- F1 the host `0x20802096` returns `NV_ERR_NOT_SUPPORTED`, or a ring with no sample, or `gr.util` stuck at 0 during a saturating host kernel: **no usable unprivileged host source on that host; stop and report, do not invent** (the code already degrades to N/A).
- F2 the host sampler stalls a vCPU or delays a doorbell/map: any increase of the p99 exit latency or of the `cuda_ladder.sh` wall time beyond the box's run-to-run spread with the flag ON versus OFF; or a host RM call above 50 ms.
- F3 the guest reads 0 or N/A under load with the flag ON on Linux: then NVML does not read A or B for `utilization.gpu` and this design does not deliver utilisation there (no harm, but the owner's goal is not met; next step is decoding the closed path, carrier C, with the VFIO capture).
- F4 any guest-visible field other than the six percentages changes between ON and OFF, or a value above 100, or a process id appears.
- F5 with the flag OFF any host `0x20802096` is made, any new log line other than the one boot notice appears, or a reply differs from today's.
- F6 the Windows guest still shows N/A with the flag ON: carrier C (`0x2080a097`, `0x20810108`) is what its NVML needs; the feature does not deliver it there.

## 10. What is NOT done, and the open question

Carrier C (`0x2080a097`, `0x20810108` with class `0x2081`, `0x00800294`) has no header, no layout and no host-side meaning we can derive; it stays refused (and counted), which is today's behaviour; a hand-typed layout would break derive-never-capture. The pure-Windows outcome therefore depends on F6. The RUSD publisher fills only `perfDevUtil`; the other polled records (clocks, P-state, power, thermals, memory ECC, PCIe, fans) stay "invalid". Guest versions without a generated row (570.x, anything not probed) get nothing. The GPUMON reply is built from our own sample history, not the host's ring order. `nvmlDeviceGetProcessUtilization` / per-process figures are not served (no pids, by design).
