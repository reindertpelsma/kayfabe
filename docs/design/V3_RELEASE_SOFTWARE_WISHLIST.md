# Release software wishlist and image-size planning (SPEC excluded)

**Research conclusion:** a complete installed size for this wishlist is **UNKNOWN** from the public vendor statements retrieved here. Required disk space, installer staging, workstation storage recommendations and downloadable bytes are different quantities. No unsupported installed-size guess fills a gap. The tables preserve those distinctions, including obsolete or inaccessible sources. **INFERRED recommendation:** evaluate one immutable Windows base plus one independently built pack per lane, with large models/media on separate data disks; do not build an all-software monolith.

**Marking:** **VENDOR-STATED** describes a public publisher/vendor statement, not a measurement by kayfabe. **UNKNOWN** means no usable figure found in the bounded public-document search, not that a figure cannot exist. **MEASURED** below is a prior observation explicitly supplied in the lane instructions or read at the pinned capture revision. **CODE READ** refers to this repository. **INFERRED** marks arithmetic, scenarios, workload candidates and proposed designs. An inference is not a compatibility result. This vocabulary follows the repository [AGENTS.md](../../AGENTS.md) and the dated owner task.

**Research scope, 2026-11-07:** only public vendor/project documentation, official technical product notes, and publisher model-file metadata were read. The Forza requirements JPEG was read as documentation; no software, model or installer was downloaded. No login, registration form, account or gated download was used. No third-party size report is substituted; the CSV supports `THIRD-PARTY-REPORTED` as a schema tag but has no such size row. SPEC is excluded from sizes, sets and proposed packs.

## 2. Estimator, assumptions and projections

**CODE READ:** [image_size_estimate.py](../../scripts/ci/image_size_estimate.py) uses only Python's standard library and reads the CSV offline. It rejects malformed schemas, duplicates, incomplete or unordered ranges, negative/nonfinite quantities and invalid options. Blank or `UNKNOWN` numeric fields mean missing information. It prints low/typical/high installed GB, compressed GB, transfer minutes at both supplied rates, inbound USD at both supplied prices, and host disk planning GB. When any selected incremental component is unknown, **every complete-total field is UNKNOWN** (`null` in JSON); separately labelled `known_*` fields are component subtotals. Exit zero means the research query ran, not that an image is sized or admitted.

**INFERRED set definitions:** `all` selects every row for the chosen platform plus shared weights. `free-only` selects the CSV's conservative `free=1` subset: zero-fee obtain routes, including account-bound freeware, but excluding conditional commercial/editor seats, restricted student/trial editions and add-ons requiring a paid host/base game. This is a proposed cost subset, not a complete dependency closure or redistribution entitlement. `minimal` on Windows selects CUDA already in the base, Blender, OBS and Sunshine; on Linux it selects Ollama, OptiX SDK and Video Codec SDK. Linux means **additions only**, with no measured Linux OS/driver base; it must not be added to a Windows image total or described as a complete Linux boot image. The Linux base is unmeasured.

**MEASURED input provenance (prior work, not rerun by SZ1):** [PR #300](https://github.com/reindertpelsma/kayfabe/pull/300), branch `claude/winimage-skeleton-20261107`, was read at `09d469e195171eefbaeff9a2a5370f1eaceaf79d`. Its [capture document at that exact revision](https://github.com/reindertpelsma/kayfabe/blob/09d469e195171eefbaeff9a2a5370f1eaceaf79d/docs/design/V3_WINDOWS_IMAGE_CAPTURE.md) section 3 records a zstd -3 stream of 19,089,671,297 bytes; section 4 records about 35 GB used after Windows + driver + CUDA, and 35.4 GB nonzero data after sparsification. The estimator uses the lane's rounded **35 GB used / 19.09 GB compressed** observation, once. This is not a measured release base with every proposed small tool, nor an allocation of CUDA's separate installed size. **UNKNOWN:** the capture does not identify the toolkit version/components; CUDA 13.0 is only the catalog's public-documentation reference. **INFERRED:** the scenario retains the captured CUDA variant, not an unmeasured upgrade to 13.0; any different toolkit selection needs a new footprint input.

**MEASURED input, owner-reported in the SZ1 task, 2026-11-07:** dev-box R2 downloads achieved **55.6 MB/s** single-stream and **223 MB/s aggregate across eight streams**. Raw traces for those rates were not supplied with the task and were not independently verified by SZ1; these remain owner-reported inputs. No Worker/Cloudflare/R2 endpoint was contacted by SZ1. **INFERRED:** applying either rate to a Vast box predicts transfer time only, not decompression, hashing, boot, staging or test time. Eight-stream throughput is already aggregate; it is not multiplied by eight again. The capture's slower ssh pull is a different path and is not used as the R2 rate.

**INFERRED arithmetic and scenario assumptions:**

- Apps compress to **0.55** of installed bytes; games and model payloads to **0.95**. Neither ratio was measured for this wishlist. The base uses its own observed compressed bytes, not either guessed ratio. Overlays may copy changed Windows blocks and include metadata, so app-level arithmetic is not a measured qcow2 allocation.
- Fixed-file weight scenarios retain one vendor-displayed, rounded SDXL/model blob unchanged on disk; low/typical/high are equal for that one chosen file. They exclude filesystem rounding, manifests and runtime environments. TensorRT's **2.5 GB** typical point is the arithmetic midpoint of its vendor **2-3 GB** approximate footprint, not a measured typical installation.
- `--basis installed` uses only explicit installed scenario cells. `--basis required-space-proxy` additionally treats numeric `REQUIRED SPACE` endpoints as hypothetical installed budgets, with the midpoint as typical. This is **sensitivity arithmetic, not an installed-size forecast, lower bound, upper bound or confidence interval**. No download automatically expands into installed bytes. Absent, obsolete, ambiguous-unit, purely temporary and nonadditive suite-context figures are not filled with guesses.
- Default host disk scenario: retain compressed download alongside expanded image, reserve **50 GB** for writable guest delta/workspace, add **20%** headroom and round **up to 25 GB**. All three defaults are INFERRED planning choices and adjustable except the documented rounding quantum. Host Linux/toolchains, extra images, extra overlays, installer caches, pagefile growth, recordings, game updates and model compilation can require more. Unknown components make the final disk request UNKNOWN.
- Supplied inbound prices **0.004** and **0.02 USD/GB** are owner-requested price scenarios, not a live tariff lookup. Costs apply to compressed bytes transferred, not expanded/virtual disk capacity; they exclude rental, storage, retries and other traffic.

**INFERRED formulae** (decimal GB and MB/s; apply separately to low, typical and high scenarios):

```text
installed = platform_base_used + sum(selected known incremental installed GB)
compressed = platform_base_compressed + sum(app_GB * 0.55 + game/model_GB * 0.95)
single_minutes = compressed_GB * 1000 / 55.6 / 60
eight_stream_minutes = compressed_GB * 1000 / 223 / 60
inbound_USD = compressed_GB * selected_USD_per_GB
host_disk_GB = ceil(((installed_GB + compressed_GB + 50) * 1.20) / 25) * 25
```

## 3. Recommendation and layered design to evaluate

**OWNER CONSTRAINT (SZ1 task, 2026-11-07):** everything in one image does not fit the **300-minute** box limit. **INFERRED recommendation:** do not bake `all` into one image, and do not treat `free-only` as a small common image: it includes simulation frameworks, SDKs and heavy weights and still has unknown footprints. Neither a fast transfer estimate nor a small compression ratio establishes that native reference, guest boot, tests, recovery and evidence collection fit the box limit. This lane did not measure installation, first-launch/shader compilation or test walls, and does not manufacture a stronger numerical proof of that constraint. SPEC's unrelated timing/size evidence is not used here.

**DESIGN to evaluate:** an immutable base containing Windows, one pinned NVIDIA driver, the chosen CUDA components and measured small common tools; each lane installs its selected software into a fresh child of the exact same base. Seal each resulting pack, then give each run a fresh writable child of that pack. Download only the base and that lane's pack (and its explicitly selected data), not every sibling pack. **NOT MEASURED:** these software packs have not been built or booted by SZ1.

```text
immutable base B (content hash, OS/driver/tool manifest)
  +-- media pack M -> fresh per-run writable child
  +-- CAD pack C   -> fresh per-run writable child
  +-- game pack G  -> fresh per-run writable child
```

**VENDOR-STATED mechanism:** QEMU supports a qcow2 backing file; unchanged sectors can be read from it, and `qemu-img` provides backing-chain inspection. See [disk-image formats](https://www.qemu.org/docs/master/system/images.html) and [qemu-img](https://www.qemu.org/docs/master/tools/qemu-img.html), retrieved 2026-11-07. **INFERRED design consequence:** independently installed sibling packs are alternatives, not composable filesystem packages. Never stack `B -> M -> C` when `C` was built against `B`: both can change the same Windows/NTFS blocks. A combined lane needs a combined pack installed from `B`, or separately mounted data disks plus explicit OS integration. A new base invalidates the old pack/base identity until rebuilt and validated; changing the recorded backing pathname is not proof of content compatibility.

**INFERRED evaluation comparison:**

| Design | What it needs | Benefit to test | Limitation to test |
|---|---|---|---|
| Exact-base qcow2 software pack | Base content hash, explicit backing format/path, pack hash and manifest, same virtual disk geometry, clean shutdown/capture, read-only sealed artifacts, fresh writable child, licence/activation at run time | Preserves Windows registry/services/plugins with the installation; base downloaded once per lane; avoids repeated GUI setup | Changed OS blocks and updates can enlarge pack; no arbitrary sibling union; all packs depend on exact base; actual allocated/compressed bytes and cold boot unmeasured |
| Separate data disk for models/media/portable trees | Pinned disk content and checksums, filesystem/drive letter/mount contract, permissions, application paths, per-run writable child where needed | Weights/scenes/recording data can have an independent update cadence; OS image need not churn with each model | Cannot assume copying Program Files installs CAD/renderers: registry, services, shared runtimes, plugins and entitlement may still need a small OS pack; portability per product unverified |
| Flattened full image for one lane | Complete independently captured lane image, its hashes/manifests, all OS/app state, run delta | Simpler artifact identity and no backing-chain lookup | Duplicates base storage/transfer across lanes; rebuild/update every affected lane; size and wall time unmeasured |

|---|---|---|

**DESIGN evidence before selecting a pack:** record installer/version/component list and permitted obtain route; measure clean installed used bytes, retained caches, changed-block allocation and zstd bytes; pin base/pack/data hashes and dependency manifests; record cold/warm download, decompression/hash, boot, activation, shader/model setup, native reference, guest execution and teardown walls. Refuse a base-hash mismatch, missing pack/data, checksum mismatch, incomplete sizing or insufficient disk/time rather than silently omitting workloads.
