## 2. Reproducibility design (STANDARD mode)

1. **Pins (DESIGN):** PTS at tag `v10.8.4` (`f0365737...`). Alternate if a profile refuses: master `1bc6fc9c...` (10.8.6); the S2 profiles were written by PTS 10.8.5 (`results-definition.xml` header, CODE READ), which is newer than the newest tag, so a refusal is possible: first-run item 2. Profiles: the 14 directories of section 1 copied from S2 `d2f1a150` into the lane's own tree and **hash-listed** (sha256 of every file, in the manifest). PTS looks profiles up under its user path; whether pre-placed profiles stop it from asking OpenBenchmarking is **INFERRED** (`pts_openbenchmarking::is_test_profile_downloaded` exists, behaviour not read): first-run item 1 runs with the network blocked.
2. **Download cache zip (S3: `make-download-cache`; code `pts-core/commands/make_download_cache.php`):** the command refreshes the OpenBenchmarking repository lists first (so the BUILD of the cache needs network), copies each profile's files into `~/.phoronix-test-suite/download-cache/` (or `PTS_DOWNLOAD_CACHE_OVERRIDE`), and writes a JSON index. `NO_DOWNLOAD_CACHE` and `NO_FILE_HASH_CHECKS` exist (S3); **the lane never sets `NO_FILE_HASH_CHECKS`**, PTS checks each file against `downloads.xml`. Cache zip `kf-pts-cache-<pts8>-<prof8>-<os>.zip` is built once by a trusted job, sha256 pinned in R2 metadata and in the manifest. Size (INFERRED, sum of the sizes above): about 2.4 GB for the Linux set (xonotic 1.24 GB, blender 0.9 GB), plus Windows zips (the Blender Windows zip size was not read). At the measured median 37 MB/s (`V3_BOX_DOWNLOADER_AND_SUPPLY_CHAIN.md` section 0) that is about 65 s, at the 4.3 MB/s minimum about 9 min (INFERRED division); it rides the downloader, overlapped with `provision`.
3. **Manifest (box_downloader schema `kayfabe.download-manifest/1`, CODE READ on the PR #425 branch):** one item per cache zip and per PTS source archive: `{name, dest, sha256, size, needed_by: "pts_gpu", sources: [signed R2, mirror upstream URL from downloads.xml]}`; sha256 and size pinned in the manifest, never taken from a server. The zip's contents are re-checked against each profile's `downloads.xml` hash by PTS itself (second, independent check).
4. **Fixed options:** run the lane from a **local suite** (S3 line 1262 prefers a local test suite over `PRESET_OPTIONS`; `PRESET_OPTIONS='test.option=Entry'` is the fallback, option identifiers to be copied from each `test-definition.xml`, e.g. blender's `blend`). Fixed: resolution 1920x1080 for glmark2/vkmark/xonotic (`$VIDEO_WIDTH x $VIDEO_HEIGHT` option), vkmark present mode **open** (Immediate avoids vsync pacing; Mailbox is the profile's NVIDIA-compatibility hint, unmeasured here), Blender CUDA and OptiX each on all four scenes, `FORCE_TIMES_TO_RUN=3` (glmark2 defaults to 1, forced to 3), `LIMIT_ELAPSED_TEST_TIME` as a hang guard, `SKIP_TESTS` empty.
5. **Reading results:** PTS writes `~/.phoronix-test-suite/test-results/<name>/composite.xml`; `result-file-to-json` (S3 line 454; `OUTPUT_DIR`, `OUTPUT_FILE`) is the machine read. The lane reads the per-run values, not PTS's averages. Per (profile, option) ratio = guest/host for HIB (`Proportion` HIB), host/guest for LIB (Blender Seconds); lane figure = geometric mean of ratios and the minimum, both reported next to the per-test table. **A ratio above 1.0 is kept as measured** (a kayfabe guest can beat its native reference on a different host).
6. **Seeds:** none are set by PTS or by us. Xonotic plays a fixed demo; hashcat and clpeak are synthetic; Cycles render noise depends on the scene's stored seed (INFERRED, not read). Run-to-run noise is measured, not seeded away: relative std dev above 5 percent flags the row (design threshold, unmeasured).
7. **Record per run (DESIGN):** PTS commit, profiles commit, cache sha256, manifest sha256, profile file hashes, `nvidia-smi` GPU model, driver, VBIOS, memory total, power limit, persistence mode, clocks sampled every second during each test (`--query-gpu=clocks.sm,clocks.mem,temperature.gpu,power.draw`), peak `memory.used` (fills the "GPU memory" column), CPU model and vCPU count (the Heaven native run on Vast was CPU-bound, inventory section 2), kernel, QEMU revision for the guest arm. **No GPU UUID** in any record (`scripts/ci/no_gpu_uuids.py` ratchet).

## 3. Host-versus-guest ratio method

- **Linux (same box):** host run, guest run, host run again (bracket: the two host runs bound drift and thermals; the ratio uses their mean and the spread is reported). Same PTS pin, same cache zip (copied into the guest; the guest needs no internet), same driver version, same `FORCE_TIMES_TO_RUN`, host pinned (`taskset`) to the guest's vCPU count so CPU-side work is equal (INFERRED need: Blender, Xonotic and OpenCL host code use the CPU). Same display path on both arms (Xvfb plus VirtualGL for GL and Vulkan windows, `docs/howto/linux-guest.md`); a different path invalidates a graphics ratio. Method follows `llm_parity.sh` (one runner, two lanes, separate processes per row, outside timing).
- **Windows:** the native arm is a Windows-on-Vast box (recipe `reindertpelsma/windows-on-vast` at `93b65b3`, LTSC 2024 Evaluation, driver 580.88; used for the SPEC native runs, inventory section 4) and the guest arm is the kayfabe Windows guest on a **same-model** box (die and driver equal; host CPU not controlled). **Nesting caveat (INFERRED):** a Vast box is itself a KVM guest, so the native arm runs one virtualization level deep and the kayfabe guest two (CLAUDE.md: a nested VM exit costs about 10 to 40 times bare metal); CPU-bound rows (Xonotic, anything with many driver calls) are biased low for the guest. §AP Q8 ("nesting cost is VFIO-guest only") is an owner design clarification that gives no timing data. Hence: repeat on at least two box pairs, report the spread, and mark the ratio "same-model, different-host" (inventory: SPEC file verification differed 803 s versus 1611 s between boxes). A bare-metal or VFIO reference on the same host (the owner's PC when up) is better where it exists and is labelled as such.
- **Parity reading (OWNER):** below 0.90 is reported as "below goal", at or above 0.95 as "goal met"; it never fails the stage (section 6 row fields).

## 4. STANDALONE use (a third party, no Worker, no run token)

DESIGN. A third party needs three things from us: the manifest, the cache zip (or network access to the upstream URLs listed in it), and the pinned profile directory. Nothing else of kayfabe, and no token (the downloader reads none, CODE READ).
1. `git clone https://github.com/phoronix-test-suite/phoronix-test-suite && git checkout f0365737ae42c2a4ae80c28491a8c0ac22a10f3c`; PHP CLI from the OS (S1 README: PHP 5.3+ CLI is the only dependency).
2. `python3 scripts/ci/box_downloader.py fetch pts_gpu.manifest.json --dest ./pts-media` (stdlib only; `--pin NAME=PATH` for files already present; with no R2 access the upstream `mirror` sources are used and every sha256 is still checked). Or `curl` plus `sha256sum -c` by hand.
3. Unpack the cache into `~/.phoronix-test-suite/download-cache/`, place the profile directories, then `phoronix-test-suite batch-install <suite>` and `phoronix-test-suite batch-run <suite>` with `FORCE_TIMES_TO_RUN=3` (set `batch-setup` once; `batch_*` commands exist in `pts-core/commands/`).
4. **From scratch, Linux:** any distro with a NVIDIA driver, `build-essential`, `cmake`, `meson`, OpenCL and Vulkan headers (`vulkan-development`, `opencl` are the profiles' own external dependency tags, which PTS installs through the distro package manager).
5. **From scratch, Windows LTSC with internet (OWNER: this is the open-probe lane):** `phoronix-test-suite.bat` downloads PHP 7.4.2 from `http://phoronix-test-suite.com/benchmark-files/php-7.4.2-Win32-vc15-x64.zip` (**plain http, no hash in the script**, line 39) and `VC_redist.x64.exe` from `https://aka.ms/vs/16/release/VC_redist.x64.exe` (line 44), and PTS sets up Cygwin under `C:\cygwin64` (S3 "Windows Setup"). **Three trust points that git does not cover**; in strict mode they are pre-staged from the manifest (PHP zip, Cygwin `setup` and its package set) and the `.bat` is run with them present. The Windows profiles unpack vendor zips and call `.exe` files (`install_windows.sh` for vkpeak, vkfft, hashcat, blender, CODE READ), so no compiler is needed in STANDARD mode.
6. Output is the same result directory and `result-file-to-json`; a standalone run reports a ratio only if it ran both arms.
