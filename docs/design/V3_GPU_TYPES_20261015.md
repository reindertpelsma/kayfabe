# V3 GPU types: what is wired per die, what is refused, and what each die still needs

**STATUS: LIVE, 2026-10-15 (branch `claude/gpu-types-20261015`, draft PR against master; GPU-free tests only: nothing in this document was run on a
GPU by this branch).** Inputs: `V3_CONSTANT_MATRIX_20261014.md` (the tiers T1..T4, F-1..F-8, D-1..D-4), `V3_DIE_SWEEP_20261014.md`,
`V3_DISPLAY_CAPS_DERIVATION_20261014.md`, `OWNER_RULINGS.md` §AF/§AH. Labels: **[M]** measured (a file in the repo shows it), **[R]** read in
source (file named), **[I]** inferred. An inference is never written as evidence. Cells that say `not run` were not run.

## 0. The one rule, and where it lives

A per-die value a guest can see is served by exactly one of: **T1** derived (ogkm / kayfabe state), **T2** the host's own unprivileged control
(asked at realize), **T3** a row of the published table `kf_rm::consttab` measured on THIS (die, driver branch), or **AUTHORED** where the matrix
says so (labelled and counted), else **REFUSED** by name with a counted notice. A neighbour die's row, a neighbour branch's row and an authored
guess presented as measured are never served. Code: `crates/kf-rm/src/consttab.rs` (table, board-specific registry), `rowserve.rs` (what each
`rm.*` key means), `zbc.rs` (ZBC defaults). Tests: `crates/kf-rm/tests/gpu_types_wiring.rs`, `zbc_defaults_per_die.rs`, `consttab::tests`.

**Falsifier of the rule** (stated before the tests were written): a test that finds a (die, branch) for which `lookup` returns a row whose die or
branch differs (`no_row_is_ever_served_across_dies`, and `no_die_is_served_another_dies_defaults` for ZBC). **Mutation check [M, run on the host]:**
changing `lookup_in` so an exact-die lookup matches ANY die's row made `no_row_is_ever_served_across_dies`, `a_miss_serves_the_authored_value...`,
`a_wrong_branch_is_a_miss...` and `the_group_p_scalars...` fail (4 of 11); the original was restored.

## 1. Wiring of the `rm.*` rows (the 42 rows that were "consumed by no code")

The 42 rows are 6 keys x GA106 (570, 575, 580, 590, 595, 610) + GA104 (595). Every key now has a decision in `rowserve::USES`; a test fails if a
table key has none (`every_rm_key_of_the_table_has_a_wiring_decision...`) and if this table says something else than the code
(`the_design_doc_states_the_same_wiring_as_the_code`).

| key | use | what it is, and what a hit / a miss does |
|---|---|---|
| `rm.0x20800a59` | serve, authored fallback | GMMU static info. Hit (GA106 570..610, GA104 595): the measured sizes, validated by the encoder. Miss: the AUTHORED sizes (`authored::GMMU_STATIC`, matrix says AUTHORED), served with a counted `W349AUTHORED` notice naming key, die and branch. No AD104 row is published (owner decision D-1, below), so on AD104 the authored value is served exactly as before. |
| `rm.0x20802a08` | serve, authored fallback | CE fault-method buffer size, same rule. |
| `rm.0x20802806` | serve, refuse on a miss | Group P scalar (`{3}` -> `{0}`). Hit: served for exactly the measured request. Miss: falls through UNCHANGED to the refusal it got before; counted `W349REFUSE`. **New behaviour on GA106/GA104 only, never run under a Windows guest.** |
| `rm.0x20802801` | serve, refuse on a miss | Group P scalar (`{3}` -> `{2}`), same rule. |
| `rm.0x2080121f` | withheld | GFX_POOL_QUERY_SIZE. Rows exist (GA106, GA104 differ: the pool is die-sized) but `kf_abi::gfxpool` states the pool is a VIRTUAL design with no captured per-die sizes and host preemption storage stays host-owned: serving the Windows GSP's numbers is an owner decision. Counted `W349WITHHELD`; behaviour unchanged (refused). |
| `rm.0x50700709` | withheld | NV5070 caps table (display object). Semantics unread, display-state dependent. Counted, unchanged. |

**D-1 (owner).** The AD104 states other GMMU numbers (0x54000 / 0x220c20, [M] from the AD104 Windows 580.88 captures, summarised in
`tier_checks/tier2_compute_host.md` section 3.2; the capture files themselves are host-only). Serving them is the one change here that would alter
what the only die that ran Windows sees. It needs a Windows A/B on the AD104 first (the matrix's recommendation); it is a one-row change
(`rm.0x20800a59 AD104 580`) plus the same for `rm.0x20802a08` if it differs. Not done: VM 2990 is not touched by this branch.

## 2. F-6: board-specific values (the table key (die, branch) is too coarse)

`crates/kf-rm/data/board_specific.tsv` lists the (key, die) pairs on which two boards of one die answered differently. A listed pair is refused by
`consttab::lookup` on every branch (`Refusal::BoardSpecific`, counted) and may have NO table row (`parse_board_specific` fails the build otherwise).
The only source for such a pair is the host's own answer to the identical request (tier 2, `gssreplay`, unchanged). The registry is DERIVED:
`the_board_specific_registry_equals_the_contradictions_in_the_tier2_summary` mines `tier2_summary.tsv` and requires the registry to equal the set
of (key, die) with disagreeing boards, for the four GSS keys the kit asks.

BOARD-SPECIFIC: `cudart.0x20809001 AD104`, `cudart.0x2080a001 AD104`, `gss.0x20808162 GA102`

- `0x20809001`, `0x2080a001` on AD104 [M]: RTX 4070 / RTX 4500 Ada give `0x03fc007f` / `{1,5,2,0x11}`, the L4 gives `0x003c0037` / `{1,2,2,0x11}`.
  **The two AD104 rows that were in the table are removed.** Effect: on an AD104 whose host did not answer at realize, cudart's gate is refused
  (D4 of the matrix: libcudart then fails); the host path answered on every measured host driver (580 interval and 595.91.07), so this is reached
  only on an unmeasured host driver.
- `0x20808162` on GA102 [M]: RTX 3090 (570.86.15) `01`, RTX A5000 (580.126.09) `00`. There was no GA102 row; the registry makes sure none appears.
- Single-board rows that remain (GA106 8162 = 01, AD104 8162 = 00, cudart rows of GA106/AD103) are consistent over every board measured so far
  [M, tier2_summary]; "consistent so far" is not a mechanism, so they are last-resort fallbacks after the host, as built.

## 3. F-1: ZBC defaults per die

The old code served ONE GA102 capture to every die. Measured on 13 dies of idle rentals [M, `KF_PROBE_ZBC=1`, `traces/constants_measure_20261014b/tier2/`]:
Ampere, Ada and Blackwell dies equal the old capture, **Turing differs** (colour formats 1/2/4, colorDS `{0,1.0,1.0}`). Now: `zbc.color`, `zbc.depth`,
`zbc.stencil` rows, one set per measured die, source `measured:<DIE>,<host driver>,2026-10-14`; `ZbcPolicy::new(.., die)` serves the die's own
entries; **a die without a row starts with an EMPTY table** (`valid = 0`; RM adds entries on demand), with a counted `W349REFUSE zbc defaults`.

ZBC-MEASURED: AD102 AD103 AD104 AD106 GA102 GA104 GA106 GB202 GB203 GB206 TU102 TU106 TU116

- **The one exception to "a measurement is never a wildcard"** (decision, owner may veto): `zbc.*` rows have branch `*`
  (`consttab::HOST_STATE_PREFIXES`). The defaults are installed by the HOST's physical RM in hardware; no driver the guest runs changes them, and the
  `HostFacts` carry no host-driver version to key on without touching 19 constructors. The die stays exact. Rows of every other key keep the exact
  (die, branch) rule (`a_zbc_row_is_per_die_with_a_wildcard_branch_only_in_the_host_state_namespace`).
- **[I] "the first 3 colour / 2 depth / 3 stencil valid entries are the defaults"** is a selection rule inferred from 13 idle dies where it holds
  (the host table is GPU-global and shared by earlier renters: AD106 had 30 colour entries, GA104 4; the extra entries are not copied). Falsifier: a
  die whose idle table has fewer or other defaults (the row builder asserts indices 1..K are valid).
- Impact today is none [R]: every host-twin mapping is an uncompressed kind, so no ROP resolves a ZBC index (module docs of `zbc.rs`).
- Behaviour change to check on hardware: Linux guests on GB205 (no ZBC row) now see an empty default table. [I] harmless; **not run** (needs a
  Linux guest on a Blackwell die; the host GPU is shared with VM 2990).

## 4. F-2 and F-3 (T1 code fixes)

- **F-2 fixed.** `SET_NOTIFY_A.ADDRESS_UPPER` and `SET_REPORT_SEMAPHORE_A.OFFSET_UPPER` are 24:0 in `clcb97.h` (Hopper 3D) and `clcdc0.h`
  (Blackwell compute A) and 7:0 in the Turing/Ampere/Ada 3D and compute headers; `grtables::address_upper_bits(class)` states it per class, anything
  else keeps 8 bits and is REFUSED above 0xff, never truncated (Blackwell 3D `clcd97/clce97`, Hopper compute `clcbc0`, `clc9c0`, `clcec0` name only the
  class id). The emitted window address is still below 2^40 (`put_gr_address`), so only the guest-side check widened. Tests:
  `the_notify_upper_field_is_as_wide_as_the_class_header_says`, and `the_notify_upper_width_matches_the_ogkm_class_headers`, which reads the ogkm
  class headers when a tree is present (`KF_OGKM_DIR`, or the bench host's copies) and skips loudly otherwise.
- **F-3 fixed for the cases with a behaviour: the Blackwell FSP boot gate.** `FspRow::BLACKWELL` carried GB20x's `0xAD00BC` for GB10x too;
  `FspRow::BLACKWELL_GB10X` (`0x200BC`, header `blackwell/gb100/dev_therm.h:27`) and `Family::gsp_model_for_arch` (used by `kf-qemu`) split it; the
  old ratchet test is replaced by an assertion against the generated header table for both die groups. The other 6 hand literals per group listed
  in `V3_HW_BOUNDARY_INVENTORY.md` (PD2 256 GiB leaf, VER3 PCF, read-exit page 0x840000, XAL window width, PBDMA ids, runlist ids) are NOT changed:
  they are CUDA-walk, memory-map or authored-topology design items, none of which a GPU-free test can validate, and no GB10x/GB20x Windows or CUDA
  run exists to test a change against. They stay in the inventory as `c✗`.

## 7. What hardware is still needed (the second measurement round)

1. **Display caps word `0x00c` per die** (`tools/read_display_caps_page.py`, root, a board with a head or the display object): AD106, AD103, GA104, then
   every die that should show a Windows desktop. Without it the die gets the authored page and the sweep showed the Windows display fails on AD106 and GA104.
2. **Windows captures (kfwc) on Blackwell GB202/GB203/GB205/GB206, AD102, GA102, and Turing**: GMMU/CE/2806/2801 and `Win-S` shapes per die. No KVM offer
   produced a Windows on these in the last round (matrix 5.3.6). Until then those dies take the authored GMMU/CE and the refusal for the group P scalars.
3. **The `0x2080852f` layout (844/776 B, uninitialised user pointers) and the 852f/b201 requests**: a T2 probe `{4=3, rest 0}` is queued in the kit
   (`rows_595_shapes.tsv`); no change needed in code before it returns.
4. **Windows A/B on the AD104** for D-1 (GMMU/CE as the die states them), and **a Linux guest on GB205/GB203** for the empty ZBC default table (section 3).
5. **Hopper/Blackwell 3D report semaphore and Hopper compute notify width**: the headers name only the class id; a trace from a Hopper or Blackwell
   Windows/CUDA guest is the evidence that would let `address_upper_bits` widen them.
6. **Windows matrix on the event-loop tip**: the merged `claude/userring-eventloop-20261014` batching (`bd079a8df` and later) has NOT been run through
   the Windows matrix.

## 8. Decisions for the owner

1. **D-1**: serve the AD104's GMMU/CE numbers (needs the Windows A/B, section 1) or keep the authored ones.
2. **ZBC branch wildcard** (section 3): accept the `zbc.*` host-state exception, or add the host driver version to `HostFacts` and key on (die, host branch).
3. **Withheld rows** (`121f` gfx pool, `0709` caps): keep withheld, or decide to serve the Windows GSP's per-die numbers.
4. **Group P scalars** (`2806`, `2801`): they are served on GA106/GA104 now; revert by deleting the rows if a Windows run regresses.
5. **Board-specific refusal of the AD104 cudart rows**: on an AD104 host driver the host path does not answer, cudart's gate is refused. Alternative: add a
   board class to the key (F-6 recommendation) once a second board per die is a product requirement.
6. **Blackwell GB10x/GB20x remaining `c✗` literals** (section 4): whether to schedule them before any GB10x/GB20x CUDA or Windows run exists.
