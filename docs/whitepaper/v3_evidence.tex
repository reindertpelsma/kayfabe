host Xid attributed to this VMM, no firmware restart during the application, and no listed

Edge video is FAIL, with recovery after about 7.3 minutes; idle is NOT RUN.
Heaven's Direct3D 11 rows completed at about \textbf{18.0 and 21.2 fps}: a correctness-oriented
PASS can coexist with poor speed. These settings differ from the later performance table.

\subsection{Linux speed: large batches and many small launches}

\reported On a rented nested RTX 3060 box with 580.159.04, a 2048-square matrix multiply at
\code{b5c9f717} gave \textbf{784 versus 786 GFLOPS}, ratio \textbf{0.997}. The CUDA ladder
record says one repetition; it supplies no between-boot timing spread. Its product claim is
content-checked large work, not launch latency.\src{linuxmerge}

\reported At \code{9d82f259}, the same class of nested RTX 3060 test host gave llama.cpp
prompt processing at \textbf{0.998} of host speed and token generation at \textbf{0.877}.
The committed logs specify two internal repetitions per benchmark ($n=2$ within each
recorded invocation); this is one application campaign, not multiple independent boots.
These batch-heavy results should be read beside eager decoding rather than replaced by it.
\src{llamahost}\src{llamaguest}
\src{linuxperf}

\reported For eager Qwen2-0.5B decoding at \code{e5ff45ff}, the nested AMD EPYC 7452 /
RTX 3060 record, using 580.159.04, gives for 512-token warm decode guest
\textbf{12.62 tokens/s [12.40, 12.94],
$n=3$} and same-box host \textbf{43.98 [43.59, 44.63], $n=3$}; ratio \textbf{0.287}, about
\textbf{0.29}. Its third reference lane on another Xeon box is \textbf{28.28 [27.96, 28.84],
$n=3$}; it is not the same-box denominator. The record identifies output equality separately.
The old die label is not independently confirmed for this campaign.\src{llmmethod}\src{llmdata}

\inferred The workload shape explains why both favourable and poor ratios matter. A large
batch amortises submission overhead; eager code repeatedly pays it. Nesting adds another
virtualisation layer to the rented host, so its guest/host ratio cannot predict physical-host
performance without a matched experiment. Placement in GPU memory versus host memory, clock
state, and the control's own variability also remain part of the experiment.
\src{linuxperf}\src{old}

\subsection{The GPU CI gate and its trust limit}

\doc A Cloudflare Worker authorises a GitHub workflow/run attempt and tested commit, while
a Durable Object ledger records rentals, deadlines and reserved spending. The provider key
stays outside the runner and rented machine. The rented operator and its reports are untrusted;
a valid callback authenticates a run capability, not honest GPU execution. The result is a
regression tripwire, not release provenance or a security audit.\src{broker}\src{threat}

\doc The October 27 policy sends new PRs to \code{next}, requiring CI there and CI plus the
GPU check on a final batch to \code{master}. Older PRs retain feature-branch or master bases;
those stacks predate this rule. The refreshed companion snapshot records every base and
known parent PR rather than implying the current policy describes all historical PRs.
\src{rules}

\attack{Admission binds the approved SHA and cleanup acts on ledger-owned instances.}
{Broker tests and recorded provider campaigns target identity, accounting, result binding,
retries and cleanup. Their status belongs to their own revisions.\src{broker}\src{threat}}
{A fake Worker or provider can report a PASS without executing the proposed code. Node doubles
also miss platform-specific fetch behaviour. Neither is a release-attestation mechanism.}
