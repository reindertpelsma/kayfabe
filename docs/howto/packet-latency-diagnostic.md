# Packet latency diagnostic

Set `KF3_DIAG_LATENCY=1` before starting QEMU to record native USER publications and Translated/private completion-tail publications. It is off by default and never changes admission, marker contents, scheduling, or interrupt policy. The process profiles its first device only; other device threads and IRQ paths do not enter that recorder. Native object/stream identities separate rebirth from retries.

`LATENCY` in the heartbeat reports stage counts/maxima, pending/eviction/loss counters, and a `host_ns` / `unix_ns` clock pair. `host_ns` uses the profiled device heartbeat's monotonic origin. `LATENCY SLOW` records carry demand observation, successful publication, covering receipt, first receipt observation and eligible logical-vector notification timestamps, plus bounded gate intervals and worker/VA/act activity. The physical notification line is 0. Notifications are GPU-wide opportunities, not proof of which packet caused an interrupt; an earlier notification remains explicit instead of being clamped into a later timestamp.

Current USER references and private sequence fences contain no GPU timestamp. Their records therefore say `marker_gpu_ns=None`; GPU-write-to-observation lag is unknown. With a genuine GPU timestamp, the decomposition can use that timestamp and report observation lag separately. Without it, publication-to-observed-receipt includes that unknown delay. Worker loop gaps and named RM/lock activity are diagnostic context, not an invented GPU finish time.

The recorder retains at most 512 pending publications, 64 slow publications, eight wait intervals per demand, four activity spans per slow record, 64 registered threads/vectors and 256 events per atomic journal. The first slow sample and shutdown produce bounded dumps; fast publications produce no packet log lines. Missing markers, masked/failed notifications, metadata contention and journal overflow remain visible as incomplete coverage or loss. The diagnostic does not guarantee delivery or repair a stalled driver.
