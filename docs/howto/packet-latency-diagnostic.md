# Packet latency diagnostic

Set `KF3_DIAG_LATENCY=1` before starting QEMU to record native USER publications and Translated/private completion-tail publications. It is off by default and never changes admission, marker contents, scheduling, or interrupt policy. The process profiles its first device only; other device threads and IRQ paths do not enter that recorder. Native object/stream identities separate rebirth from retries.

`LATENCY` in the heartbeat reports stage counts/maxima, pending/eviction/loss counters, and a `host_ns` / `unix_ns` clock pair. `host_ns` uses the profiled device heartbeat's monotonic origin. `LATENCY SLOW` records carry demand observation, successful publication, covering receipt, first receipt observation and eligible logical-vector notification timestamps, plus bounded gate intervals and worker/VA/act activity. The physical notification line is 0. Notifications are GPU-wide opportunities, not proof of which packet caused an interrupt; an earlier notification remains explicit instead of being clamped into a later timestamp.

Current USER references and private sequence fences contain no GPU timestamp. Their records therefore say `marker_gpu_ns=None`; GPU-write-to-observation lag is unknown. With a genuine GPU timestamp, the decomposition can use that timestamp and report observation lag separately. Without it, publication-to-observed-receipt includes that unknown delay. Worker loop gaps and named RM/lock activity are diagnostic context, not an invented GPU finish time.

The recorder retains at most 512 pending publications, 64 slow publications, a separate 512 pending/64 slow split history, eight wait intervals per demand, four activity spans per slow record, 64 registered threads/vectors and 256 events per atomic journal. The first slow sample and shutdown produce bounded dumps; fast publications produce no packet log lines. Missing markers, masked/failed notifications, metadata contention and journal overflow remain visible as incomplete coverage or loss. The diagnostic does not guarantee delivery or repair a stalled driver.

`LATENCY SPLIT` follows real Translated MEM_OP and USER/gated split tickets: request, queue admission, successful walk submission, apply end, result readiness, gate/result release and worker resumption. It includes guest token, requested PDB/space, resolved last target, shared walk ID/count, wall time, RM verb deltas and diff/map counts. `rm_calls_by_verb` is ordered as reserve VA, other allocation, free, map, unmap, control, invalidate, other. Cost is shared-walk attribution: never sum one shared walk's costs across its tickets. The split heartbeat's `queue_walk` starts at request, while the slow record retains queue admission separately. `walk_ready` includes apply and required invalidate. The bounded history updates when later milestones arrive, including after the first dump.

The existing metadata probe runs at 100 ms when latency recording alone is enabled, so it can dump an incomplete slow event while workers are blocked. It drains only diagnostic metadata unless the separate completion probe is enabled. USER tagged references and private sequence fences are observed through their existing readers; a covering marker can represent several native publications. Demand observation is the worker's first observed demand/PUT in that visit, not an independently captured vCPU-doorbell time or a Windows DMA-packet identifier. No new vCPU lock is taken.

Registered row/PT owners and RM control/verb spans identify observed contention and operations. Thread roles are `1=worker`, `2=VA`, `3=act`, `4=probe`; a thread ID is a recorder identity, not an OS thread ID. Up to four matching spans prioritize specific blockers over enclosing worker/VA loop visits. The operation journal retains 256 completed scopes plus current thread activity; overwritten history, missing registration, failed metadata acquisition and first-observation ambiguity remain limitations. `notification_source` distinguishes normal writes from diagnostic storm writes. An eligible logical-vector mask is sampled before the physical line-0 write; it describes that opportunity, not a guarantee that Windows handled it.

See the [ten-line host runbook](ens11-host-runbook.md). No hardware validation is included in the GPU-free implementation.
